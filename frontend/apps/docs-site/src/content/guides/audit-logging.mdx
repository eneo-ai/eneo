# Audit Logging Guide

import { Callout, Tabs } from 'nextra/components'

Audit logging helps organizations track sensitive actions, meet compliance requirements, and investigate incidents. This guide explains how to enable, configure, and use audit logs in Eneo.

For developer-focused details, see [Audit Logging (Technical)](/docs/audit-logging).

## What audit logging covers

Audit logs capture actions such as:

- User and role management (create, update, delete)
- Assistant, space, and app changes
- Security classification and access updates
- File and integration events
- Audit log access and exports
- Space oversight by organisation administrators: members added, removed or given another role, and joining or leaving a space
- Web widget publishing: activation requests and withdrawals, requests sent back, activation, pausing and archiving

Logs are stored in PostgreSQL and are scoped to your tenant.

## Enable audit logging

Audit logging can be turned on or off globally in the admin UI.

- Go to **Admin** and use the **Audit logging** toggle on the admin overview page to enable or disable logging for your tenant
- The logs themselves, the per-category and per-action configuration, exports, and the retention setting live under **Admin → Analytics & logs → Audit Logs**

When disabled, no new audit logs are created, except for the [always-logged actions](#always-logged-actions).

## Configure what gets logged

You can fine-tune logging in two levels:

1. **Category toggles** — enable/disable entire groups of actions (e.g., Administrator actions).
2. **Action toggles** — enable/disable specific actions within a category (e.g., `user_created`).

Changes apply immediately for new events. Historical logs remain unchanged.

### Always-logged actions

Some actions are always logged and cannot be turned off:

- **Space oversight**: Joined a space through oversight, Left a space (oversight), Member added by organisation administrator, Role changed by organisation administrator, and Member removed by organisation administrator.
- **Web widget publishing**: Widget activation request sent back, and activating, pausing and archiving a widget.

These actions are recorded even when audit logging is turned off, whatever the category and action toggles say. In the configuration their switches are locked and marked **Always logged**, each category shows how many of its actions are always logged, and switching a whole category off leaves them on. Each entry is saved together with the change it records: if the entry cannot be saved, the change is not made. The normal retention period and exports apply to them.

An organisation may reduce the logging of ordinary activity, but not of access and changes made without membership, or of publishing to the open web. The administrators who could make such changes can also change the audit settings, so a record they could switch off would not be a control.

The reason an administrator gives for joining a space, and the message sent back with a widget request, are stored in the entry's JSON metadata, not in its description. To review who has joined which spaces, filter on the action **Joined a space through oversight**. See [Space Oversight](/guides/space-oversight#what-the-audit-log-records) for what each entry records.

## Viewing audit logs

Access to audit logs requires an **access justification**. This ensures you can track who accessed logs and why.

When you enter the audit log view, you will be prompted to:

- Select a reason category (e.g., GDPR request, investigation)
- Provide a written justification

The access event itself is logged and included in the audit trail.

### Filters and search

You can filter logs by:

- **Action** (multi-select)
- **Date range**
- **User** (the actor, found by searching on email)

The search box has two scopes: **User** searches for an actor by email, and **Entity** is a free-text search (at least three characters) that matches the log description. If you want a name or identifier to be searchable, include it in the log description or metadata.

### Log details and JSON

Each log row expands into a detail view with:

- Full timestamp and status (success/failure)
- Human-readable description
- JSON metadata (copyable)

This metadata includes actor and target snapshots for reliable investigation even if data changes later.

## Retention policies

Audit log retention is configured per tenant, in days, on the Audit Logs page and enforced by a daily purge job. Logs older than the retention period are permanently deleted.

Conversation data (questions and app runs) has its own retention hierarchy, set per space, assistant, or app. See [Retention](/docs/audit-logging#retention) on the technical page for the hierarchy, its limits, and the API.

## Exporting audit logs

Audit logs can be exported from the UI for compliance or incident response.

- **Formats**: CSV or JSON Lines (`.jsonl`)
- **Large exports**: handled asynchronously for performance and stability

Exported files are retained for 24 hours before cleanup.

## Best practices

- Keep audit logging enabled for production tenants.
- Use action-level toggles instead of disabling whole categories.
- Set retention policies that align with regulatory requirements.
- Use async exports for large time ranges.
