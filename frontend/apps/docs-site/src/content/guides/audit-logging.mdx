# Audit Logging Guide

import { Callout, Tabs } from "nextra/components";

Audit logging helps organizations track sensitive actions, meet compliance requirements, and investigate incidents. This guide explains how to enable, configure, and use audit logs in Eneo.

For developer-focused details, see [Audit Logging (Technical)](/docs/audit-logging).

## What audit logging covers

Audit logs capture actions such as:

- User and role management (create, update, delete)
- Assistant, space, and app changes
- Security classification and access updates
- File and integration events
- Audit log access and exports

Logs are stored in PostgreSQL and are scoped to your tenant.

## Flow audit guarantees

Flow events use different guarantees based on what could be exposed or changed:

| Guarantee                         | Used for                                                                                                                                                          | What happens if audit storage is unavailable                                                                                                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Required in the state transaction | Run creation and terminal/review transitions, redispatch, runtime input upload or deletion, run-history policy changes, package import, and future purge receipts | The protected database change does not commit.                                                                                                                    |
| Required before access            | Run input/result detail, active review payloads, evidence and provider-call views or exports, template/run-file download URLs, and Flow package export            | Eneo returns `503` and does not return protected content, package bytes, or a signed URL.                                                                         |
| Configurable and asynchronous     | Routine Flow authoring and most tenant Flow-setting changes                                                                                                       | The action can succeed when its configured audit event is disabled or the audit queue is temporarily unavailable.                                                 |
| Operational, best effort          | Executed Flow HTTP and transcription audit summaries                                                                                                              | Runtime step/attempt state, webhook delivery state, and provider-call evidence remain the durable records. The additional admin audit summary may be unavailable. |

Required Flow events are safety records. They bypass the global, category, and
action toggles, so an administrator cannot accidentally disable the record while
performing the protected action. The toggles control configurable events only.

Audit metadata contains identifiers, bounded counts, classifications, and status.
It does not contain prompts, document or audio content, credentials, signed URLs,
authorization headers, or raw provider request and response bodies. Routine run
status polling and history use content-free summaries, so they are not audited.
Opening run input/result detail or an active review payload is audited and fails
with `503` if the required record cannot be committed.

The Flow authoring screen's **Test HTTP request** action is not a runtime Flow
step. It creates a configurable asynchronous audit event after the external
request, but no step, attempt, or webhook-delivery record. A temporary audit-queue
failure does not suppress the test result, so this action is not durable HTTP
evidence. Execute the published Flow when durable runtime evidence is required.

## Enable audit logging

Configurable audit logging can be turned on or off globally in the admin UI.

- Go to **Organization → Granskningsloggar (Audit Logs)**
- Use the global toggle to enable or disable logging for your tenant

When disabled, configurable events are not created. Required Flow safety events
described above still record the protected action or deny it if the record cannot
be persisted.

## Configure what gets logged

You can fine-tune logging in two levels:

1. **Category toggles** — enable/disable entire groups of actions (e.g., Administrator actions).
2. **Action toggles** — enable/disable specific actions within a category (e.g., `user_created`).

Changes apply immediately for new events. Historical logs remain unchanged.

## Viewing audit logs

Access to audit logs requires an **access justification**. This ensures you can track who accessed logs and why.

When you enter the audit log view, you will be prompted to:

- Select a reason category (e.g., GDPR request, investigation)
- Provide a written justification

The access event itself is logged and included in the audit trail.

### Filters and search

You can filter logs by:

- **Entity** (e.g., user, assistant, app)
- **Action** (multi-select)
- **Date range**
- **Actor** (user search)

Free-text search matches the log description. If you want a name or identifier to be searchable, include it in the log description or metadata.

### Log details and JSON

Each log row expands into a detail view with:

- Full timestamp and status (success/failure)
- Human-readable description
- JSON metadata (copyable)

This metadata includes actor and target snapshots for reliable investigation even if data changes later.

## Retention policies

### Audit log retention

Audit log retention is configured per tenant and enforced by a daily purge job. Logs older than the retention period are permanently deleted.

### Conversation retention hierarchy

Conversation data (questions and app runs) follows a hierarchy that can be tuned per space, assistant, or app:

1. Assistant or App `data_retention_days` (if set)
2. Space `data_retention_days`
3. Tenant-level conversation retention (if enabled internally)
4. no effective policy means keep indefinitely

**How to use it:**

- Set retention at the **space** level to give all new assistants/apps a default policy.
- Override retention at the **assistant** or **app** level when a specific workflow needs shorter retention.
- Set `data_retention_days` to `null` to remove a child override and fall back to its parent.

The shared daily retention worker removes conversation data after its effective configured period. Under the current model, Flow AI Builder conversation sessions can also follow Space/conversation retention. This is separate from Flow run-history policy.

Flow run and step history is never deleted by that scheduled worker. Its dedicated Organization → Space → Flow policy only sets eligibility or a human-review queue. See [Data retention and deletion](/guides/data-retention).

## Exporting audit logs

Audit logs can be exported from the UI for compliance or incident response.

- **Formats**: CSV or JSON Lines (`.jsonl`)
- **Large exports**: handled asynchronously for performance and stability

Exported files are retained for 24 hours before cleanup.

## Best practices

- Keep audit logging enabled for production tenants.
- Use action-level toggles instead of disabling whole categories.
- Set retention policies that align with regulatory requirements.
- Use async exports for large time ranges.

## Roadmap

We plan to support external audit sinks (e.g., SIEM or analytics pipelines) so long-term storage can be moved out of the primary database when needed.
