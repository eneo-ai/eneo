# Multi-Tenant OIDC Federation

Set up OIDC authentication where each tenant (organization, municipality, company) uses their own identity provider.

import { Callout, Steps, Tabs } from 'nextra/components'

<Callout type="warning">
  Single-tenant is the recommended setup. Support for several organisations in one installation will be phased out and is basic only. It does not guarantee that the organisations' data is kept apart, because they share the same database.
</Callout>

---

## Overview

Multi-tenant federation allows each tenant in your Eneo deployment to authenticate against their own IdP. This is ideal for:

- **SaaS platforms** serving multiple customers
- **Municipal deployments** where each municipality has their own Azure AD
- **Enterprise deployments** with subsidiary companies

## Prerequisites

Before starting, ensure you have:

- [ ] Eneo backend deployed and running
- [ ] Redis running (required: each sign-in is a one-time transaction stored there)
- [ ] Super Admin API key (`ENEO_SUPER_API_KEY` configured)
- [ ] HTTPS enabled on every origin users reach Eneo through
- [ ] For each tenant, the public origin its users will use (the same origin for all tenants, or a dedicated hostname per tenant - Eneo does not derive the tenant from the hostname)

<Callout type="warning">
  Multi-tenant federation **requires** `FEDERATION_ENABLED=true`. In this mode the `OIDC_*` environment variables are ignored - every tenant must be configured through the sysadmin API, and a tenant without a configuration cannot sign in.
</Callout>

## Setup

<Steps>
### Enable federation mode

Add these environment variables to your backend `.env`:

```bash
# Enable federation (per-tenant IdP configuration via the sysadmin API)
FEDERATION_ENABLED=true

# Encryption key for storing client secrets securely (backend refuses to start without it)
ENCRYPTION_KEY=your-fernet-encryption-key

# Super admin API key for management endpoints
ENEO_SUPER_API_KEY=your-super-admin-api-key
```

Generate an encryption key:

```bash
uv run python -m eneo.cli.generate_encryption_key
```

Restart the backend:

```bash
docker compose restart backend
```

<Callout type="info">
  `FEDERATION_PER_TENANT_ENABLED` is a deprecated alias for `FEDERATION_ENABLED`. It still works but logs a warning at startup; when both are set, `FEDERATION_ENABLED` wins.
</Callout>

### Prepare tenants

Each tenant needs a URL-safe slug (`a-z`, `0-9`, `-`). The slug identifies the tenant in the login URL (`/login?tenant={slug}`) and in the tenant selector. If you have existing tenants without slugs, run:

```bash
cd backend
uv run python -m eneo.cli.backfill_tenant_slugs
```

This derives slugs from the tenant names.

### Register the application in each tenant's IdP

For each tenant, register Eneo as an application in their IdP. The redirect URI is the tenant's public origin plus `/login/callback`:

<Tabs items={['Azure Entra ID', 'MobilityGuard']}>
  <Tabs.Tab>
    1. Go to [Azure Portal](https://portal.azure.com) → **Azure Active Directory** → **App registrations**
    2. Click **New registration**
    3. Enter a name (e.g., "Eneo SSO")
    4. Set **Redirect URI** (type **Web**) to the tenant's callback:
       ```
       https://eneo.your-domain.com/login/callback
       ```
    5. Click **Register**
    6. Note the **Application (client) ID** and **Directory (tenant) ID**
    7. Go to **Certificates & secrets** → **New client secret**
    8. Copy the secret value immediately
    9. Go to **API permissions** → Add `openid`, `profile`, `email`, `User.Read`
    10. Click **Grant admin consent**
    11. Go to **Token configuration** → **Add optional claim** → **ID** and add `email` and `xms_edov`. Entra ID does not send `email_verified` for organisational accounts; `xms_edov` is the claim Eneo accepts instead for JIT account creation.

    **Discovery URL for Azure:**
    ```
    https://login.microsoftonline.com/{directory-tenant-id}/v2.0/.well-known/openid-configuration
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    1. Log in to the tenant's MobilityGuard admin console
    2. Navigate to **Applications** → **Add Application**
    3. Select **OpenID Connect**
    4. Set **Redirect URI** to:
       ```
       https://eneo.your-domain.com/login/callback
       ```
    5. Save and note the **Client ID** and **Client Secret**

    **Discovery URL for MobilityGuard:**
    ```
    https://tenant-mobilityguard.com/.well-known/openid-configuration
    ```
  </Tabs.Tab>
</Tabs>

If a tenant is reached through more than one origin (for example a proxy URL and a clean URL), register every callback URL in the IdP and list the extra ones in `additional_redirect_uris` below.

### Configure the tenant via API

Use the federation API to provide the tenant's OIDC configuration. `PUT` is the full-definition endpoint for a new federation setup or a full replacement of the current one. The backend fetches the discovery document immediately and checks the configuration with the rules sign-in uses. It rejects the request with `502` if the document cannot be read, and with `400`, naming the reason, if sign-in could not use the configuration.

<Tabs items={['Azure Entra ID', 'MobilityGuard']}>
  <Tabs.Tab>
    ```bash
    curl -X PUT "https://eneo.your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation" \
      -H "X-API-Key: your-super-admin-api-key" \
      -H "Content-Type: application/json" \
      -d '{
        "provider": "entra_id",
        "canonical_public_origin": "https://eneo.your-domain.com",
        "discovery_endpoint": "https://login.microsoftonline.com/{azure-tenant-id}/v2.0/.well-known/openid-configuration",
        "client_id": "azure-application-id",
        "client_secret": "azure-client-secret",
        "allowed_domains": ["sundsvall.se"]
      }'
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    ```bash
    curl -X PUT "https://eneo.your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation" \
      -H "X-API-Key: your-super-admin-api-key" \
      -H "Content-Type: application/json" \
      -d '{
        "provider": "mobilityguard",
        "canonical_public_origin": "https://eneo.your-domain.com",
        "discovery_endpoint": "https://sundsvall-mg.com/.well-known/openid-configuration",
        "client_id": "mg-client-id",
        "client_secret": "mg-client-secret",
        "allowed_domains": ["sundsvall.se"]
      }'
    ```
  </Tabs.Tab>
</Tabs>

**Request fields:**
| Field | Required | Description |
|-------|----------|-------------|
| `provider` | Yes | Label for the IdP (e.g., `entra_id`, `mobilityguard`, `okta`, `auth0`) |
| `discovery_endpoint` | Yes | The IdP's OIDC discovery URL |
| `client_id` | Yes | OAuth client ID |
| `client_secret` | Yes | OAuth client secret (at least 8 characters, encrypted at rest) |
| `allowed_domains` | No | Email domains allowed to authenticate. Empty means no domain filter for existing members; a non-empty list is required for JIT account creation |
| `canonical_public_origin` | No | The URL where this tenant's users access Eneo; used to build the redirect URI. Falls back to the backend's `PUBLIC_ORIGIN` when omitted |
| `redirect_path` | No | Callback path, default `/login/callback` |
| `additional_redirect_uris` | No | Extra fully-qualified callback URLs accepted for this tenant (each must also be registered in the IdP) |
| `signing_algorithms` | No | ID token algorithms to accept; default from discovery, else `RS256`. See the [provider contract](/guides/oidc-federation#provider-contract) |
| `email_verified_claims` | No | Claims that say the email is verified, in order; default `["email_verified", "xms_edov"]` |
| `allowed_endpoint_hosts` | No | Other hosts the provider's token endpoint and JWKS may be on; default none, so they must be on the discovery host. See the [provider contract](/guides/oidc-federation#provider-contract) |

Scopes are fixed to `openid email profile` and cannot be set through the API.

### Test the configuration

Verify the IdP connection before users try to log in:

```bash
curl -X POST "https://eneo.your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation/test" \
  -H "X-API-Key: your-super-admin-api-key"
```

This test:
- Fetches the IdP's discovery document from the stored `discovery_endpoint` (`502` if it cannot be read)
- Checks the stored configuration against it with the rules sign-in uses: issuer and endpoints, signing algorithms and claims mapping (`400`, naming the reason, if sign-in could not use it)
- Returns `{"success": true, "message": "Federation config is valid and IdP is reachable", "issuer": "…"}`

<Callout type="info">
  The test does **not** fetch the JWKS, attempt actual authentication or validate client credentials - it only checks that sign-in could use the configuration with the provider's discovery document.
</Callout>

### Test login

Open the tenant's login URL and test the flow:

```
https://eneo.your-domain.com/login?tenant={tenant-slug}
```

You are redirected to the tenant's IdP. Authenticate with a user from that IdP; on return, Eneo issues a session for the matching Eneo user. Without the `tenant` parameter the login page shows the tenant selector instead.

</Steps>

## Tenant Resolution

When federation is enabled and more than one active tenant exists, the login page determines which tenant's IdP to use in this order:

| Priority | Method | Description |
|----------|--------|-------------|
| 1 | **`tenant` query parameter** | `/login?tenant={slug}` starts the flow for that tenant immediately. Use this for direct links from intranets or portals |
| 2 | **Remembered slug** | The last slug used in this browser session (stored in `sessionStorage`) stays the active tenant: the selector is skipped and the sign-in form is shown with a **Choose another organisation** link, and after a failed callback a **Try logging in again** button restarts the flow for that tenant. It does not start the IdP redirect by itself - use `?tenant={slug}` for that |
| 3 | **Tenant selector** | The login page fetches `GET /api/v1/auth/tenants` and shows a selector. When exactly one tenant is returned it is selected automatically |

Eneo does **not** resolve tenants from subdomains or hostnames. A dedicated hostname per tenant is optional (set it as that tenant's `canonical_public_origin`); the tenant is always carried explicitly via the slug and the signed state.

### Tenant Selector

With federation enabled, the selector lists **active tenants that have a slug and an IdP configuration** with a discovery endpoint, a client ID and a client secret. Tenants without an IdP are omitted. When only one tenant is eligible, it is selected automatically. Configure an organisation's IdP before directing its users to the selector.

## Managing Tenants

### View tenant configuration

```bash
curl "https://eneo.your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation" \
  -H "X-API-Key: your-super-admin-api-key"
```

The response contains `provider`, `client_id`, `masked_secret`, `issuer`, `allowed_domains`, `additional_redirect_uris`, `allowed_endpoint_hosts`, `signing_algorithms`, `email_verified_claims`, `configured_at` and `encryption_status`. The two optional provider keys are `null` when not set, so the defaults apply.

<Callout type="info">
  Client secrets are always masked in responses for security.
</Callout>

### Update tenant configuration

Use the `PATCH` endpoint to update the current federation setup without resending every field. Omitted fields stay unchanged. Use `PUT` only when you want to provide a full new federation configuration.

```bash
curl -X PATCH "https://eneo.your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation" \
  -H "X-API-Key: your-super-admin-api-key" \
  -H "Content-Type: application/json" \
  -d '{
    "allowed_domains": ["sundsvall.se", "new-domain.se"]
  }'
```

Each tenant's administrators can also change its display name, client ID, client secret and allowed email domains themselves under **Administration › Sign-in (SSO)**, as described in [Change the settings in Eneo](/guides/oidc-federation/single-tenant#change-the-settings-in-eneo).

`PATCH` requires an existing configuration (`404 No federation config found for tenant` otherwise) and does not accept `null` for `provider`, `discovery_endpoint`, `client_id` or `client_secret`. Changing `discovery_endpoint` re-fetches the discovery document and stores the new provider's issuer, endpoints and client authentication method; any other change is checked with the same rules without contacting the provider. To replace the whole federation definition, continue to use `PUT` and send the full required payload.

### Remove tenant federation

To disable OIDC for a tenant:

```bash
curl -X DELETE "https://eneo.your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation" \
  -H "X-API-Key: your-super-admin-api-key"
```

While `FEDERATION_ENABLED=true` there is no fallback to the `OIDC_*` environment variables, so the tenant's users cannot sign in through OIDC until a new configuration is provided.

## Adding a New Tenant

To onboard a new organization:

1. **Create the tenant** in Eneo (via the sysadmin API)
2. **Ensure the tenant has a slug** for the login URL and selector
3. **Register Eneo** in their IdP with the callback URL `{canonical_public_origin}/login/callback`
4. **Configure via API** with their IdP details
5. **Test** the configuration
6. **Provision users through SCIM**, or create/invite them, and keep tenant `provisioning: false`. For deployments without SCIM, optionally enable JIT (`POST /api/v1/sysadmin/tenants/{tenant_id}/` with `{"provisioning": true}` and a `default_role_id`), configure a non-empty `allowed_domains`, and ensure the ID token provides `email_verified: true` for `email` (the strings `"true"` and `"1"` are also accepted). Microsoft Entra ID sends `xms_edov: true` (email domain owner verified) instead of `email_verified`; Eneo accepts it for the standard `email` claim once it is added as an optional ID-token claim.

An existing active tenant member can sign in without an `email_verified` claim. Creating a new member requires all JIT conditions above. A custom email claims mapping can be used for existing accounts, but JIT only accepts verification when the selected address equals the token's standard `email` address. Missing verification is not an implied approval. Use SCIM or administrative provisioning when your IdP does not provide this guarantee.

JIT never restores inactive or removed accounts. SCIM or an administrator must reactivate the original account. Enabling SCIM does not automatically change `provisioning`; explicitly keep it `false` when SCIM manages membership.

## Troubleshooting

### "Email domain … is not allowed for this organization"

The user's email domain isn't in the tenant's `allowed_domains` list (`403`).

**Fix:** Add the domain with `PATCH`:
```bash
curl -X PATCH "https://eneo.your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation" \
  -H "X-API-Key: your-super-admin-api-key" \
  -H "Content-Type: application/json" \
  -d '{"allowed_domains": ["domain1.com", "domain2.com"]}'
```

### "User not found. Provision the account through SCIM or contact your administrator for access."

The user authenticated successfully with the IdP but doesn't exist in Eneo and the tenant has JIT provisioning disabled (`403`).

**Fix:** Either:
- Create or invite the user in the tenant first
- For deployments without SCIM, enable JIT (`provisioning: true`), configure a non-empty `allowed_domains`, require `email_verified: true` from the IdP (`"true"` and `"1"` are also accepted; Entra ID's `xms_edov: true` counts as well), and set a `default_role_id`. Otherwise auto-created users have no permissions. Do not enable JIT to bypass a SCIM provisioning failure.

### "Authorization session is invalid or has expired"

The sign-in's one-time transaction was not found or no longer fits the configuration (`400`, code `oidc_transaction_invalid`): the callback was replayed, Redis was restarted or evicted the key mid-flow, or the provider's issuer changed during the sign-in (the backend logs `oidc_transaction_refused` with `issuer_changed`). A state older than 10 minutes is rejected earlier with `400 Authorization session expired. Please try logging in again.`, and a sign-in started before an upgrade with `400 Invalid state parameter`.

**Fix:** Start the sign-in flow again. If it recurs, check the Redis logs and the `oidc_state_ttl_seconds` setting.

### "Sign-in is temporarily unavailable"

Redis could not store or return the sign-in transaction, or did not answer within 2 seconds (`503`, code `oidc_login_unavailable`). Sign-in is refused rather than continued without it, and no session or user row is written. The backend logs `oidc_transaction_store_failed`.

**Fix:** Verify Redis is running and accessible:
```bash
redis-cli ping
```

### "The sign-in response could not be verified"

The provider's response failed a check of the [provider contract](/guides/oidc-federation#provider-contract) (`401`, code `oidc_response_not_verified`). The backend logs `oidc_response_refused` with the reason, for example `issuer_mismatch`, `nonce_mismatch` or `algorithm_not_allowed`.

**Fix:** Search the logs for the correlation ID. For `issuer_mismatch`, compare the ID token's `iss` with the `issuer` in the provider's discovery document: a placeholder such as `{tenantid}` there means the discovery URL is a shared one, so set `discovery_endpoint` to your organisation's own. Otherwise check the token's `aud` against the configured `client_id`, the provider's signing algorithm against `signing_algorithms`, and that the server clocks agree.

### "The provider signs with no algorithm Eneo accepts"

Sign-in answers `500` when none of the algorithms Eneo would accept for this provider is allowed: the configured `signing_algorithms`, else the provider's `id_token_signing_alg_values_supported`, else `RS256`. Only the algorithms in the [provider contract](/guides/oidc-federation#provider-contract) are allowed.

**Fix:** Set `signing_algorithms` through the federation API to an allowed algorithm the provider signs with, or have the provider sign with one.

### "The token endpoint is on …, which is neither the discovery host nor in allowed_endpoint_hosts"

Saving or testing the federation config answers `400`, and sign-in `500`, when the provider's token endpoint or JWKS is on another host than its discovery document. A visitor sees only that sign-in is not available; the reason is in the backend log.

**Fix:** Check that the host belongs to your provider, then add it with `PATCH`:
```bash
curl -X PATCH "https://eneo.your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation" \
  -H "X-API-Key: your-super-admin-api-key" \
  -H "Content-Type: application/json" \
  -d '{"allowed_endpoint_hosts": ["oauth2.googleapis.com", "www.googleapis.com"]}'
```

A save that answers `Failed to fetch discovery document: …` names why the request failed: for example a redirect, an answer that is not a JSON object, or an address that is not allowed. When it says the provider could not be reached, run `curl --noproxy '*'` against the discovery URL from inside the backend container: Eneo does not use `HTTPS_PROXY` for its requests to the provider. See [Eneo's requests to the provider](/guides/oidc-federation#provider-contract).

### Debug mode

For complex issues across multiple tenants:

```bash
curl -X POST "https://eneo.your-domain.com/api/v1/sysadmin/observability/oidc-debug/" \
  -H "X-API-Key: your-super-admin-api-key" \
  -H "Content-Type: application/json" \
  -d '{"enabled": true, "duration_minutes": 10, "reason": "Multi-tenant debug"}'
```

Then search logs for the user's **correlation ID** (shown on error screens):

```bash
docker compose logs backend | grep "correlation_id.*abc123"
```

Remember to disable debug mode after:
```bash
curl -X POST "https://eneo.your-domain.com/api/v1/sysadmin/observability/oidc-debug/" \
  -H "X-API-Key: your-super-admin-api-key" \
  -H "Content-Type: application/json" \
  -d '{"enabled": false}'
```

## Correlation ID Tracking

Every authentication request is assigned a unique **correlation ID** for end-to-end tracing. This ID follows the request through the entire OIDC flow and appears in all related log entries.

### Format

The correlation ID is a 16-character hexadecimal string generated using `secrets.token_hex(8)`:

```
Example: a1b2c3d4e5f67890
```

### Using Correlation IDs for Debugging

1. **User-facing errors** display the correlation ID on error screens
2. **Search logs** using the correlation ID to trace the complete flow:

```bash
docker compose logs backend | grep "correlation_id.*a1b2c3d4e5f67890"
```

3. **All OIDC events** are logged with the correlation ID, including:
   - Authentication initiation
   - State token creation
   - Callback processing
   - Token exchange
   - User resolution

<Callout type="info">
  When users report authentication issues, ask them for the correlation ID shown on the error screen. This allows you to quickly locate all related log entries.
</Callout>

## Sign-in Transactions in Redis

Each sign-in stores a one-time transaction in Redis under `oidc:transaction:{id}`. It holds the `nonce`, the PKCE verifier, the server-computed `redirect_uri` and the tenant with its configuration version. The signed `state` only names it.

- It expires after `oidc_state_ttl_seconds` (10 minutes by default).
- The callback removes it as it reads it, so a callback cannot be replayed.
- A missing transaction ends the sign-in with `400`; an unreachable Redis with `503`.

To see how many sign-ins are in progress (requires Redis CLI access):

```bash
redis-cli --scan --pattern "oidc:transaction:*" | wc -l
```

<Callout type="warning">
  Never modify or copy transaction entries: they contain the PKCE verifier. Deleting one ends that user's sign-in.
</Callout>

## Security Considerations

### Client Secret Encryption

Client secrets are encrypted using **Fernet** (AES-128-CBC + HMAC-SHA256) before being stored in the database.

<Callout type="warning">
  **Back up your `ENCRYPTION_KEY`** securely. If you lose it, you'll need to re-register all tenant IdPs and reconfigure their client secrets.
</Callout>

### Domain Restrictions

Always configure `allowed_domains` for each tenant. This ensures only users from authorized email domains can authenticate - even if they have valid credentials in the IdP.

### State Token Protection

Authentication requests use signed state tokens (JWT with HS256) to prevent CSRF attacks. Tokens expire after 10 minutes. Each request also carries a `nonce` and a PKCE `S256` challenge, which bind the ID token and the authorization code to this one sign-in.
