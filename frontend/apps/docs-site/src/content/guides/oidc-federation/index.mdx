## Supported Identity Providers

Eneo works with any OIDC-compliant identity provider that supports discovery (`/.well-known/openid-configuration`) and the Authorization Code Flow. Common examples:

- **Azure Entra ID** (formerly Azure AD)
- **MobilityGuard**
- **Keycloak**
- **Auth0**
- **Okta**

<Callout type="info">
  The guides walk through Azure Entra ID, Keycloak, Auth0 and MobilityGuard as examples. The same principles apply to other OIDC providers.
</Callout>

## Before You Begin

Make sure you have:

- Admin access to your Identity Provider
- HTTPS enabled on your Eneo domain
- Access to the Eneo backend configuration (`.env`)

**For the sysadmin API (single-tenant API setup and multi-tenant):**
- `FEDERATION_ENABLED=true`, an `ENCRYPTION_KEY` and an `ENEO_SUPER_API_KEY` in the backend `.env`

**For every setup:** Redis. Each sign-in keeps its one-time transaction there; without Redis, sign-in is refused.

## How OIDC Works with Eneo

Eneo uses the **OAuth 2.0 Authorization Code Flow** with OpenID Connect:

1. User opens Eneo and is sent to the login page
2. Eneo asks the backend for an authorization URL (`GET /api/v1/auth/initiate`) and redirects to your Identity Provider
3. User authenticates with their credentials
4. IdP redirects back to `{origin}/login/callback` with an authorization code
5. Eneo exchanges the code for tokens, validates the ID token and matches the user by email
6. User is logged in

For technical details, see [Authentication Architecture](/docs/authentication-architecture). To keep users and groups in sync from your directory, see [SCIM Provisioning](/guides/scim-provisioning).

## Provider Contract

What Eneo expects from any OIDC provider on the generic sign-in (`/api/v1/auth/initiate` and `/api/v1/auth/callback`), whichever setup you use.

**Eneo sends** `state`, `nonce` and a PKCE `code_challenge` with method `S256` on every authorization request, and the matching `code_verifier` with the token request. A provider that ignores PKCE still signs users in; Eneo then relies on `state`, `nonce` and the client secret, so such a provider does not give you PKCE protection.

**Eneo checks**, before anyone is signed in:

- The ID token's signature against the provider's JWKS, using only the allowed algorithms (never `none` or a symmetric algorithm)
- `iss` equals the issuer the sign-in started with. If the provider's issuer changes during a sign-in, that sign-in ends with `400` (`oidc_transaction_invalid`) before the code is sent anywhere. When the provider's discovery said at the start that it sends the `iss` parameter on its redirect ([RFC 9207](https://www.rfc-editor.org/rfc/rfc9207)), that parameter must be present and equal too; otherwise it may be missing, but one that is sent must be equal
- `aud` contains Eneo's client ID; `azp`, when present, equals it, and it is required when `aud` names several clients
- `exp`, `iat` and `sub` are present, the token has not expired, and `iat` and `auth_time` are not in the future (`oidc_clock_leeway_seconds`, default 120 seconds, allows for clock skew)
- `nonce` equals the one Eneo sent for this sign-in

A response that fails any check ends the sign-in with `401` (`oidc_response_not_verified`); nothing falls back to a weaker check.

The provider-bound Zitadel login in the Svelte frontend keeps its own requests: it sends PKCE but no `nonce`.

**Optional provider settings.** Set them through the [federation API](/guides/oidc-federation/multi-tenant#configure-the-tenant-via-api), which also serves a single-tenant setup made through the API. Leave them out to keep the defaults. With the `OIDC_*` environment variables the defaults always apply; to change them, configure the provider through the API (`FEDERATION_ENABLED=true`).

| Field | Default | Meaning |
|-------|---------|---------|
| `signing_algorithms` | The provider's `id_token_signing_alg_values_supported`, else `["RS256"]` | ID token algorithms to accept. Only `RS256`/`384`/`512`, `PS256`/`384`/`512`, `ES256`/`384`/`512` and `EdDSA` (Ed25519 keys) are allowed |
| `email_verified_claims` | `["email_verified", "xms_edov"]` | Claims that say the email is verified, in order. The first one present decides, so an explicit `false` is never overridden by a later claim |

### Upgrading

- Redis is required for sign-in.
- The ID token's `iss` must equal the provider's issuer: the one Eneo stored from discovery when the federation config was saved, else the one discovery gives at sign-in (always so with the `OIDC_*` variables). A `PATCH` that includes the organisation's own `discovery_endpoint` stores the issuer again. A shared discovery URL whose issuer contains a placeholder (for example `{tenantid}`) is refused: saving such a federation config answers `400`, and a sign-in with one already stored or set in `OIDC_DISCOVERY_ENDPOINT` answers `500` before anyone is sent to the provider. Switch to your organisation's own discovery URL before upgrading (`discovery_endpoint` in the federation config, or `OIDC_DISCOVERY_ENDPOINT`).
- PKCE (`S256`) and `nonce` are always sent. A provider that ignores PKCE keeps working.
- The provider must return the `nonce` in the ID token ([OpenID Connect Core 3.1.3.7](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)). With a provider that does not, every sign-in is refused with `oidc_response_not_verified` (`nonce_mismatch`).
- The provider's discovery document must stay reachable. Each backend process caches it for `oidc_jwks_cache_ttl_seconds` (default one hour) with no stale copy to fall back on: when the cache has expired and the document cannot be fetched, sign-in answers `500`.
- A sign-in started before the upgrade must be started again: its state is refused with `400 Invalid state parameter`, or its transaction with `oidc_transaction_invalid`. In a rolling deploy, replace all backend instances together, or accept that sign-ins which cross versions fail until the switch is done; people only need to start the sign-in again.
- Upgrade the frontend together with the backend: the older frontend does not forward the provider's `iss` parameter. Any other client that calls `POST /api/v1/auth/callback`, through eneo-js or directly, must forward the redirect's `iss` query parameter whenever the provider sends one: Eneo requires it when the provider's discovery announced it, and refuses one that differs.
- With `OIDC_RESOURCE_SERVER_ENABLED=true`, Eneo also accepts the provider's access tokens as bearer tokens. Such a token must be a JWT signed with `RS256`, `RS384` or `RS512` that names its key (`kid`) and carries `sub`, `email`, `exp`, `iss` equal to `OIDC_ACCEPTED_ISSUER` and `aud` containing `OIDC_ACCEPTED_AUDIENCE`. The person is admitted by the same rules as at sign-in, to the tenant `OIDC_TENANT_ID` names, else to the first active tenant.

### Migrate from the MobilityGuard settings

Eneo has no sign-in of its own for MobilityGuard any more. MobilityGuard signs people in through the OIDC settings, like every other provider. A client that posted codes to `POST /api/v1/users/login/openid-connect/mobilityguard/` now gets `404`, whatever the variables are called; it must sign in through `/api/v1/auth/initiate` and `/api/v1/auth/callback` instead. Rename or remove the old variables:

| Old variable | Where | Use instead |
|--------------|-------|-------------|
| `MOBILITYGUARD_DISCOVERY_ENDPOINT` | backend | `OIDC_DISCOVERY_ENDPOINT` |
| `MOBILITYGUARD_CLIENT_ID` | backend | `OIDC_CLIENT_ID` |
| `MOBILITYGUARD_CLIENT_SECRET` | backend | `OIDC_CLIENT_SECRET` |
| `MOBILITYGUARD_TENANT_ID` | backend | `OIDC_TENANT_ID` |
| `MOBILITY_GUARD_AUTH` | frontend | Nothing: the backend reads the authorization endpoint from discovery |
| `MOBILITYGUARD_CLIENT_ID` | frontend | Nothing: the backend's `OIDC_CLIENT_ID` is used |

The backend does not start while a `MOBILITYGUARD_*` variable is set without its `OIDC_*` name. Its log names the variable to use, for example:

```text
MOBILITYGUARD_CLIENT_ID is no longer read. Rename it to OIDC_CLIENT_ID.
```

When both names are set, the `OIDC_*` value is used and the backend logs a warning to remove the old one. The frontend logs a warning at startup while `MOBILITY_GUARD_AUTH` or `MOBILITYGUARD_CLIENT_ID` is set.

At the provider, check these differences from the old sign-in:

- The redirect URI stays `{PUBLIC_ORIGIN}/login/callback`, from the backend's `PUBLIC_ORIGIN`. If people reach Eneo at more than one address, the old sign-in could follow one of the organisation's allowed origins; the OIDC settings always use `PUBLIC_ORIGIN`.
- Eneo asks for the scopes `openid`, `email` and `profile`; the old sign-in asked for `openid` and `email`.
- Eneo sends the client secret in the request body (`client_secret_post`), or with HTTP Basic when the provider's discovery lists `client_secret_basic` and not `client_secret_post`. The old sign-in always used HTTP Basic.
- Eneo sends a `nonce`, and the ID token must carry it back (see the contract above). The old sign-in sent none.

**How to check.** Open the login page and sign in. If the page says "Signing in through your organisation is not available right now. Contact your administrator.", the frontend still has `MOBILITY_GUARD_AUTH` while the backend reports no OIDC sign-in: check that the backend has the `OIDC_*` variables and has started. A sign-in begun on the old MobilityGuard link before the upgrade ends on the login page; start it again.
