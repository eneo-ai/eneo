# Single-Tenant OIDC Setup

Set up OIDC authentication when all your users authenticate against a single identity provider.

## Choose Where the Settings Live

<Cards>
  <Cards.Card title="Settings stored in Eneo (recommended)" href="#api-configuration">
    `FEDERATION_ENABLED=true` with `ENCRYPTION_KEY` and `ENEO_SUPER_API_KEY`. The operator registers the identity provider once through the sysadmin API. After that the organisation's administrators change the client ID, client secret and allowed email domains under **Administration › Sign-in (SSO)**, without a restart, and every change is audited.
  </Cards.Card>
  <Cards.Card title="Settings in the server configuration" href="#environment-variable-configuration">
    `OIDC_*` variables in the backend `.env`, for configuration as code. Their shape is fixed, every change needs a restart, and administrators cannot change anything in Eneo.
  </Cards.Card>
</Cards>

<Callout type="info">
  New installations should store the settings in Eneo. Existing installations keep working unchanged on upgrade; to switch, [move the settings into Eneo](#move-the-settings-into-eneo).
</Callout>

Both modes use the same login flow: the login page redirects straight to your IdP, and the IdP sends the user back to `{PUBLIC_ORIGIN}/login/callback`.

### How the two modes differ

- `FEDERATION_ENABLED` alone chooses the mode. The backend reads it at startup, so changing it needs a restart. Eneo never combines the two modes or falls back from one to the other.
- **Stored in Eneo** (`FEDERATION_ENABLED=true`): browser sign-in uses only the provider stored on the tenant. `OIDC_DISCOVERY_ENDPOINT`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` and `OIDC_ALLOWED_DOMAINS` are ignored, and the backend logs the names of any that are still set when it starts. Until the operator registers a provider, the login page offers only the username and password form.
- **Server configuration** (`FEDERATION_ENABLED=false`, the default in code): browser sign-in uses only the `OIDC_*` variables and ignores anything stored on the tenant. The Sign-in page says that the operator manages sign-in in the server configuration.
- Both modes use `PUBLIC_ORIGIN` for the redirect URI, and the `OIDC_RESOURCE_SERVER_*`, `OIDC_ACCEPTED_*`, `OIDC_TENANT_ID` and TTL settings. In stored mode a stored `canonical_public_origin` takes precedence and the stored `additional_redirect_uris` are accepted too; in server configuration only `{PUBLIC_ORIGIN}/login/callback` is.
- Access tokens accepted with `OIDC_RESOURCE_SERVER_ENABLED` follow the mode as well. In stored mode they use the stored subject claim and allowed domains, and an empty stored list never falls back to `OIDC_ALLOWED_DOMAINS`; in server configuration they use `sub` and `OIDC_ALLOWED_DOMAINS`. A token therefore meets the same domain rules as browser sign-in. Tokens are also accepted where browser sign-in is not offered (the selected settings lack a discovery URL, client ID or secret). In stored mode with no provider stored, a token then creates no account but admits every existing account in the organisation whose email matches; see [Upgrading](/guides/oidc-federation#upgrading).
- Deleting the stored settings (`DELETE /api/v1/sysadmin/tenants/{tenant_id}/federation`) turns single sign-on off for the organisation. Eneo does not fall back to the `OIDC_*` variables.

<Callout type="info">
  If single sign-on stops working in either mode, people with a local password can still sign in at `/login?showUsernameAndPassword=true`. `init_db.py` creates the first owner with a local password, and password sign-in does not depend on these settings. With the settings stored in Eneo, an administrator can then correct them on the Sign-in page, or the operator through the [sysadmin API](#updating-the-api-configuration).
</Callout>

## Environment Variable Configuration

Use environment variables to keep the identity provider in the server configuration, for example when it is managed as code. This is the default in code (`FEDERATION_ENABLED=false`) and there is no separate enable flag: OIDC is active as soon as `OIDC_DISCOVERY_ENDPOINT`, `OIDC_CLIENT_ID` and `OIDC_CLIENT_SECRET` are all set. With one of them missing, the login page offers only the username and password form.

### Prerequisites

- Admin access to your Identity Provider
- Access to your Eneo backend `.env` file
- HTTPS enabled on your Eneo domain (`PUBLIC_ORIGIN` must be `https://`, except `http://localhost` for development)
- Redis running (each sign-in is a one-time transaction stored there; without it, sign-in is refused)


### Configure backend environment variables

Add to your backend `.env` file:

```bash
# Your Eneo origin - used to compute the redirect URI as {PUBLIC_ORIGIN}/login/callback
# https:// only (http://localhost allowed for development), no path, no trailing slash
PUBLIC_ORIGIN=https://your-domain.com

# Identity provider (OIDC discovery auto-configures the authorization/token/JWKS endpoints)
OIDC_DISCOVERY_ENDPOINT=https://login.microsoftonline.com/{tenant-id}/v2.0/.well-known/openid-configuration
OIDC_CLIENT_ID=your-client-id
OIDC_CLIENT_SECRET=your-client-secret

# Optional: Eneo tenant ID (not the IdP's tenant ID) for access tokens accepted
# with OIDC_RESOURCE_SERVER_ENABLED; without it, the first active tenant.
# Find it with GET /api/v1/sysadmin/tenants/ using the super admin API key
OIDC_TENANT_ID=your-eneo-tenant-uuid

# Keep the default
FEDERATION_ENABLED=false
```

The frontend environment template (`env_frontend.template`) carries `PUBLIC_ORIGIN` as well - set it to the same value.

<Callout type="warning">
  `PUBLIC_ORIGIN` must match what you registered in your IdP exactly (including `https://`). The backend rejects a `PUBLIC_ORIGIN` that is not `https://` (or `http://localhost`) or that contains a path, query or fragment.
</Callout>

### Restart and test

```bash
docker compose restart backend
```

Visit your Eneo instance. The login page detects the OIDC configuration and redirects you to your IdP automatically; after signing in you land back in Eneo. To reach the username/password form instead, open `/login?showUsernameAndPassword=true`.

</Steps>

### Changing environment-variable configuration

To update your OIDC settings:

1. Edit the `OIDC_*` variables in your `.env` file
2. Restart the backend: `docker compose restart backend`

If you need to change settings without restarting, use the [API configuration](#api-configuration) instead. To let the organisation's administrators change the client ID, client secret and allowed email domains themselves, [move the settings into Eneo](#move-the-settings-into-eneo).

<Callout type="info">
  Set `OIDC_ALLOWED_DOMAINS` to a JSON array such as `["your-company.com"]` to restrict global OIDC logins by email domain. The default `[]` applies no domain filter to existing active members, but prevents creation of new accounts through JIT.
</Callout>

## API Configuration

Store the settings in Eneo, the recommended mode for new installations. The operator registers the identity provider once through the sysadmin API; after that the organisation's administrators [change the settings in Eneo](#change-the-settings-in-eneo) without a restart. This is the same mechanism as [multi-tenant federation](/guides/oidc-federation/multi-tenant), used with a single tenant.

### Prerequisites

- All prerequisites from the environment-variable method
- Super Admin API key (`ENEO_SUPER_API_KEY` set in the backend `.env`)
- Your tenant ID (`GET /api/v1/sysadmin/tenants/` with the super admin key)

<Steps>
### Enable federation mode

Add to your backend `.env` file:

```bash
# Enable API-based federation config
FEDERATION_ENABLED=true

# Required for encrypting client secrets in the database (backend refuses to start without it)
ENCRYPTION_KEY=your-fernet-encryption-key

# Super admin API key for management endpoints
ENEO_SUPER_API_KEY=your-super-admin-api-key

# Still used as the redirect origin unless the tenant sets canonical_public_origin
PUBLIC_ORIGIN=https://your-domain.com
```

Generate an encryption key:

```bash
uv run python -m eneo.cli.generate_encryption_key
```

Restart the backend after setting these variables. With `FEDERATION_ENABLED=true` the `OIDC_*` sign-in variables are ignored, as described in [How the two modes differ](#how-the-two-modes-differ).

### Register your application in the IdP

Follow the same steps as in [Register your application in the IdP](#register-your-application-in-the-idp).

### Configure via API

Use the federation API endpoint to set your OIDC configuration. The backend fetches the discovery document immediately and checks the configuration with the rules sign-in uses. It rejects the request with `502` if the document cannot be read, and with `400`, naming the reason, if sign-in could not use the configuration (for example, discovery lacks an endpoint or the provider signs with no algorithm Eneo accepts):

```bash
curl -X PUT "https://your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation" \
  -H "X-API-Key: your-super-admin-api-key" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "entra_id",
    "canonical_public_origin": "https://your-domain.com",
    "discovery_endpoint": "https://login.microsoftonline.com/{azure-tenant-id}/v2.0/.well-known/openid-configuration",
    "client_id": "your-application-client-id",
    "client_secret": "your-client-secret",
    "allowed_domains": ["your-company.com"]
  }'
```

### Test the configuration

Verify your setup works before users try to log in:

```bash
curl -X POST "https://your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation/test" \
  -H "X-API-Key: your-super-admin-api-key"
```

This fetches the discovery document and checks the stored configuration with the rules sign-in uses: it answers `502` if the document cannot be read and `400`, naming the reason, if sign-in could not use the configuration. It does not fetch the JWKS or validate the client credentials.

### Test login

Visit your Eneo instance. With exactly one active tenant the login page redirects to your IdP automatically, exactly as in the environment-variable setup. If you later add a second active tenant, Eneo switches to the [multi-tenant login flow](/guides/oidc-federation/multi-tenant#tenant-resolution) (tenant selector or `?tenant={slug}`).

From now on, the organisation's administrators can [change the settings in Eneo](#change-the-settings-in-eneo).

</Steps>

### Updating the API configuration

Use `PATCH` to change individual fields; omitted fields stay unchanged and changes take effect immediately - no restart needed.

```bash
# Example: Update allowed domains
curl -X PATCH "https://your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation" \
  -H "X-API-Key: your-super-admin-api-key" \
  -H "Content-Type: application/json" \
  -d '{
    "allowed_domains": ["company.com", "subsidiary.com"]
  }'
```

`PUT` replaces the whole configuration and requires all mandatory fields again.

### View current configuration

```bash
curl "https://your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation" \
  -H "X-API-Key: your-super-admin-api-key"
```

<Callout type="info">
  Client secrets are never returned in GET responses - they're masked for security.
</Callout>

## Change the settings in Eneo

With the settings stored in Eneo, the organisation's administrators open **Administration › Sign-in (SSO)**. The page always applies to their own organisation.

- **Shown, set by the operator:** the discovery URL, issuer, redirect URIs (each with a copy button, to register at the identity provider), scopes and client authentication method. The operator changes the discovery URL and the redirect settings through the [sysadmin API](#configure-via-api); the issuer and client authentication method come from the provider's discovery document, and the scopes are Eneo's defaults.
- **Changed by the administrator:** the provider's display name, client ID, client secret and allowed email domains, one per line. The secret is never shown: the page says when it was saved, and **Replace secret** opens an empty field. Under the domains the page says whether new accounts are created at first sign-in ([JIT](#user-provisioning)) and links to that setting on the administration overview.

Next to **Save changes** the page names the settings changed but not saved, and **Undo changes** restores the saved values. Saving asks for confirmation:

- A new display name only is confirmed plainly: it appears in the [audit log](/guides/audit-logging) and does not change sign-in.
- A new client ID, secret or domain list is flagged, because a wrong value can stop people signing in through SSO, and the confirmation says what each change does. If the provider gives each client its own user IDs, [open a migration window](/guides/oidc-federation#changing-the-client-id) from the old client ID to the new one before saving a new client ID; otherwise existing accounts are refused. Through the window, Eneo finds each account by the email address the new client sends. Replacing the secret is the routine change. A new secret must already be valid at the identity provider. For the domains it names the ones added and removed: removed domains can no longer sign in, and active accounts in added ones can, and where [JIT](#user-provisioning) is on, a person there with a verified email address gets an account at first sign-in. A first list refuses everyone outside it and lets JIT create accounts inside it; an empty list checks no domain, so every active member can sign in, and JIT creates no accounts.

Each saved change is written to the audit log. The change applies from the next sign-in, and people already signed in stay signed in; after a change to who can sign in, the page suggests trying SSO in a private window before signing out. If another administrator saved in the meantime, the save is refused and the page offers to load their values.

While sign-in is configured with `OIDC_*` variables, the page only says that the operator manages it in the server configuration, and links to [Move the settings into Eneo](#move-the-settings-into-eneo).

## Move the settings into Eneo

Nothing changes on upgrade: an installation configured with `OIDC_*` variables keeps signing in the same way. Moving the settings into Eneo, so that administrators can [change them themselves](#change-the-settings-in-eneo), is a manual step that the operator runs once; Eneo never runs it at startup.

<Steps>
### Turn on federation mode

Set `FEDERATION_ENABLED=true` and `ENCRYPTION_KEY` as in [Enable federation mode](#enable-federation-mode), keep the `OIDC_*` variables, and restart the backend. OIDC sign-in has no configuration until the next step has run.

### Run the move

From `backend/`, with the backend's environment:

```bash
uv run python scripts/migrate_env_oidc_to_tenant_federation.py
```

The move stores the settings through the same checks, encryption and audit as the [sysadmin API](#configure-via-api), but never contacts the identity provider: sign-in reads the issuer and endpoints from the discovery document, as it did with the `OIDC_*` variables, so the move also works while the provider is unreachable. `Federation migration applied.` means that `OIDC_DISCOVERY_ENDPOINT`, `OIDC_CLIENT_ID`, the encrypted `OIDC_CLIENT_SECRET` and `OIDC_ALLOWED_DOMAINS` are stored on the only active tenant, with any redirect origin or path it already had, and the change is in the audit log. The same people can sign in, and JIT creates accounts for the same domains, as before. The provider's display name starts as `default`.

`Federation migration skipped.` means nothing changed: federation is off, an `OIDC_*` value is missing, there is not exactly one active tenant, or the tenant already has a federation configuration.

`Federation migration failed:` stores nothing and says why, never with the client secret: a value is refused as it would be by the API, for example a client secret shorter than 8 characters or an invalid domain, or other settings were stored while the move ran.

### Check sign-in

Sign in through your IdP. The `OIDC_*` sign-in variables are now ignored and can be removed.

</Steps>

### Check a move made with an earlier version

Earlier versions of the move did not copy `OIDC_ALLOWED_DOMAINS`, so the stored domain list stayed empty: existing members could still sign in, but JIT stopped creating accounts. Running the move again does not repair this, because a tenant with settings is skipped. Check it by hand:

1. Read the stored list, under **Administration › Sign-in (SSO)** or with `GET /api/v1/sysadmin/tenants/{tenant_id}/federation` (`allowed_domains`).
2. Compare it with `OIDC_ALLOWED_DOMAINS` in the backend's environment, if you still have it.
3. If the stored list is empty and should not be, enter the domains on the Sign-in page or send them with [`PATCH`](#updating-the-api-configuration). Leave a list that an administrator has changed since the move; Eneo never changes it for you.

## User Provisioning

On the first sign-in, Eneo matches the signing-in user to an existing Eneo user by the `email` claim of the ID token and binds the account to the person's identity; after that, the identity decides and the email is not consulted (see [Account Binding](/guides/oidc-federation#account-binding)). By default a user who does not exist is rejected with `403 User not found. Provision the account through SCIM or contact your administrator for access.`

For deployments using SCIM, keep tenant `provisioning` set to `false` (the default). SCIM creates and manages accounts; OIDC signs users in to their existing active account. A user whose account has not arrived through SCIM must wait for provisioning. Enabling SCIM does not automatically change the tenant's JIT setting.

For deployments without SCIM, JIT can create a user on first sign-in only when all of these conditions hold:

- Tenant `provisioning` is explicitly `true`.
- A non-empty domain list admits the user's email domain: `OIDC_ALLOWED_DOMAINS` for environment-variable configuration, or `allowed_domains` for API configuration.
- The validated ID token carries the claim `email_verified: true` for its `email` address. For identity providers that can only send claims as text, the strings `"true"` and `"1"` (and the number `1`) are also accepted. Microsoft Entra ID does not send `email_verified` for organisational accounts; its optional claim `xms_edov: true` (email domain owner verified) is accepted in its place, so add `xms_edov` as an optional ID-token claim in the app registration. A missing claim or any other value does not satisfy this check.

Existing active accounts do not require `email_verified` to sign in. Inactive or removed accounts cannot be reactivated or recreated through JIT; SCIM or an administrator must restore them. If the IdP does not supply verified-email claims, provision accounts through SCIM or administration.

For environment-variable configuration, set for example:

```bash
OIDC_ALLOWED_DOMAINS=["your-company.com"]
```

Restart the backend after changing this variable. Then enable `provisioning` on the tenant and set a default role:

```bash
curl -X POST "https://your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/" \
  -H "X-API-Key: your-super-admin-api-key" \
  -H "Content-Type: application/json" \
  -d '{"provisioning": true, "default_role_id": "{role-uuid}"}'
```

<Callout type="warning">
  Without a `default_role_id`, auto-provisioned users are created with no roles and cannot use assistants, spaces or any other permission-gated feature until an admin assigns one.
</Callout>

For push-based provisioning from your directory (deactivation, groups), see [SCIM Provisioning](/guides/scim-provisioning).

## Configuration Reference

### Environment Variables

| Variable | Required | Description |
|----------|----------|-------------|
| `PUBLIC_ORIGIN` | Yes | Your Eneo origin; the redirect URI is `{PUBLIC_ORIGIN}/login/callback` |
| `OIDC_DISCOVERY_ENDPOINT` | Yes (env method) | IdP's OIDC discovery URL |
| `OIDC_CLIENT_ID` | Yes (env method) | OAuth client ID |
| `OIDC_CLIENT_SECRET` | Yes (env method) | OAuth client secret |
| `FEDERATION_ENABLED` | - | `true` (recommended for new installations) uses the settings stored in Eneo; `false` (default in code) uses the `OIDC_*` variables. Read at startup, so a change needs a restart. `FEDERATION_PER_TENANT_ENABLED` is a deprecated alias |
| `ENCRYPTION_KEY` | Yes (API method) | Fernet key for encrypting secrets |
| `ENEO_SUPER_API_KEY` | Yes (API method) | API key for the sysadmin endpoints, sent as `X-API-Key` |

### API Configuration Fields

| Field | Required | Description |
|-------|----------|-------------|
| `provider` | Yes | Label for the IdP (e.g., `entra_id`, `mobilityguard`, `okta`, `auth0`) |
| `discovery_endpoint` | Yes | IdP's OIDC discovery URL |
| `client_id` | Yes | OAuth client ID |
| `client_secret` | Yes | OAuth client secret (at least 8 characters) |
| `allowed_domains` | No | Email domains allowed to authenticate |
| `canonical_public_origin` | No | Origin used for the redirect URI; falls back to `PUBLIC_ORIGIN` |
| `redirect_path` | No | Callback path (default: `/login/callback`) |
| `additional_redirect_uris` | No | Extra fully-qualified callback URLs, each also registered in the IdP |
| `signing_algorithms` | No | ID token algorithms to accept; default from discovery, else `RS256`. See the [provider contract](/guides/oidc-federation#provider-contract) |
| `email_verified_claims` | No | Claims that say the email is verified, in order; default `["email_verified", "xms_edov"]` |
| `allowed_endpoint_hosts` | No | Other hosts the provider's token endpoint and JWKS may be on; default none, so they must be on the discovery host. See the [provider contract](/guides/oidc-federation#provider-contract) |
| `subject_claim` | No | The claim an account is bound to. Without it a `PUT` stores `sub`, so send the current claim to keep it; see [The subject claim](/guides/oidc-federation#the-subject-claim) |

Scopes are fixed to `openid email profile`.

## Troubleshooting

### Redirect URI mismatch

The IdP reports that the redirect URI is not registered, or Eneo rejects the callback with `400 Redirect URI mismatch - authentication flow invalid`.

**Fix:** Ensure both match exactly:
- **In IdP:** `https://your-domain.com/login/callback`
- **In Eneo:** `PUBLIC_ORIGIN=https://your-domain.com` (or the tenant's `canonical_public_origin`) - no trailing slash, same scheme, host and port

### "Email domain … is not allowed for this organization"

The user's email domain isn't in `allowed_domains` (API method only, `403`).

**Fix:** Add the domain:
```bash
curl -X PATCH "https://your-domain.com/api/v1/sysadmin/tenants/{tenant_id}/federation" \
  -H "X-API-Key: your-super-admin-api-key" \
  -H "Content-Type: application/json" \
  -d '{"allowed_domains": ["domain1.com", "domain2.com"]}'
```

### "User not found. Provision the account through SCIM or contact your administrator for access."

The user authenticated successfully but doesn't exist in Eneo (`403`).

**Fix:** Provision the account through SCIM, create or invite the user, or configure all [JIT requirements](#user-provisioning). Do not enable JIT as a workaround for a SCIM sync failure.

### "Automatic account creation requires a verified email address"

JIT is enabled and the domain is allowed, but the ID token carries no accepted verification claim (`403`).

**Fix:** Make the IdP send `email_verified: true` for the `email` claim. On Azure Entra ID, which never sends `email_verified` for organisational accounts, add `xms_edov` under **Token configuration** → **Add optional claim** → **ID** instead. Otherwise provision the account through SCIM or administration.

### "Email claim not found in ID token"

The ID token has no `email` claim (`401`). On Azure Entra ID this happens when the user has no `mail` attribute or the app registration does not emit the optional `email` claim - see the checklist in [SCIM Provisioning](/guides/scim-provisioning#sign-in-prerequisites-when-paired-with-oidc).

### "This account is already linked to another sign-in"

The account is bound to another identity than the one this sign-in presents (`403` `identity_conflict`), for example after a client ID or subject claim change.

**Fix:** Find the reason in the audit log and follow [Sign-in conflicts](/guides/oidc-federation#sign-in-conflicts).

### Invalid client

Token exchange fails with `401 Failed to exchange authorization code for tokens`.

**Fix:** Verify that the client ID and secret match the IdP registration and that the secret has not expired. The IdP's own error response is written to the backend log.

### Sign-in refused with a code

The refusals with a code are the same for one organisation as for several:

- `oidc_transaction_invalid`: [Authorization session is invalid or has expired](/guides/oidc-federation/multi-tenant#authorization-session-is-invalid-or-has-expired)
- `oidc_login_unavailable`: [Sign-in is temporarily unavailable](/guides/oidc-federation/multi-tenant#sign-in-is-temporarily-unavailable)
- `oidc_response_not_verified`: [The sign-in response could not be verified](/guides/oidc-federation/multi-tenant#the-sign-in-response-could-not-be-verified), including an issuer with a placeholder such as `{tenantid}`

### Debug mode

For complex issues, enable OIDC debug logging:

```bash
curl -X POST "https://your-domain.com/api/v1/sysadmin/observability/oidc-debug/" \
  -H "X-API-Key: your-super-admin-api-key" \
  -H "Content-Type: application/json" \
  -d '{"enabled": true, "duration_minutes": 10, "reason": "Debugging login issue"}'
```

Then check the backend logs for entries with `[OIDC DEBUG]` and the correlation ID shown on the error screen:

```bash
docker compose logs backend | grep "correlation_id.*a1b2c3d4e5f67890"
```

## Security Best Practices

1. **Use HTTPS**: `PUBLIC_ORIGIN` and the registered redirect URI must be `https://` in production
2. **Rotate secrets**: Regularly rotate client secrets (with the API method this needs no restart)
3. **Restrict domains**: Configure `allowed_domains` when using the API method
4. **Monitor access**: Review authentication logs and the [audit log](/guides/audit-logging) regularly
5. **Back up `ENCRYPTION_KEY`**: Losing it means re-entering every client secret
