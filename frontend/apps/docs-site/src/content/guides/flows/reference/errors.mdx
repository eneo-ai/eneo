# Flow error reference

This page is for teams turning Eneo Flows error codes into clear recovery paths, and it shows which failures belong to request handling and which belong to run execution.

Use this as the canonical consumer reference for `FlowApiErrorCode`. Task guides link here instead of repeating code lists.

## The error envelope

Errors that Eneo's own handlers answer for the Flow runtime API, including request validation, use this JSON envelope:

```json
{
  "message": "Flow must be published before a run can be created.",
  "code": "flow_not_published",
  "eneo_error_code": 9007,
  "context": { "flow_id": "00000000-0000-0000-0000-000000000001" },
  "request_id": "7796bdacde5f9f7536cdbf3a7e50b5c4"
}
```

- **`code` is the contract.** It is a stable string, present on every error in this envelope. Branch your client on this field and nothing else.
- **`message` is for humans.** It is not stable and must not drive control flow.
- **`context` carries recovery hints** for some codes, such as the `step_ids` that are missing a required upload, or `auth_layer` on an authentication or scope rejection.
- **`details` carries code-specific structured diagnostics**, such as field validation errors. It is optional.
- **`request_id` is for support.** Quote it, together with the run id, when reporting a problem.
- **`error_id` appears on unexpected server errors** and points support at the originating exception log. Log it whenever it is present.
- **`eneo_error_code` is a legacy numeric category, not an identifier.** It is derived from the exception class rather than from `code`, so it is many-to-one: most of the catalog below shares a single value, while a few codes carry a different one. It cannot distinguish two failures and must not drive control flow.

`message`, `code`, and `eneo_error_code` are required. The optional `context`, `request_id`, `error_id`, and `details` fields are omitted when they carry no value.

A few refusals are answered before a Flow handler runs, such as an unknown route or an endpoint-access check that carries no code, and use the framework's `{"detail": ...}` body instead. [API Reference: Errors](/docs/api#errors) lists those shapes.

For `flow_run_upload_pdf_exceeds_limit`, context contains `limit` (`pages`, `extracted_bytes`, or `seconds`), `measured`, and `ceiling`. The deployment settings `FLOW_PDF_MAX_PAGES`, `FLOW_PDF_MAX_EXTRACTED_BYTES`, and `FLOW_PDF_EXTRACTION_TIMEOUT_SECONDS` default to 2000 pages, 134217728 extracted UTF-8 bytes (128 MiB, including page markers and separators), and 900 seconds. See the [Flow limits table](/guides/flows/integrating-flows#execution-and-pdf-extraction). These defaults are provisional pending measurement and have no tenant overrides. They apply only to flow runtime uploads; other PDF uploads keep their existing extraction behavior. The byte ceiling applies to extracted text, not the uploaded file. A timeout kills the extraction process, whose own deadline remains active if the request worker exits.

Each server worker admits at most half its reported CPU count in concurrent PDF extraction processes, rounded down with a minimum of one (one when the CPU count is unavailable). Waiting for capacity counts against the same extraction timeout. If that wait exhausts the deadline, the response has `limit: "seconds"` and `reason: "extraction_capacity"` in its context, and no parser is started. Back off before retrying an upload refused for capacity. The process holds its slot until it has exited and been reaped, including when the request is cancelled.

## Stalled execution workers

`flow_worker_stalled` means the execution worker's heartbeat expired. Workers
renew every 30 seconds; the heartbeat expires after 180 seconds and recovery
runs every 60 seconds. A run normally becomes failed about 3–4 minutes after
its last renewal. A maintenance backlog or unavailable database or worker can
delay recovery. Health reports unhealthy when the heartbeat is older than
240 seconds. Runs waiting for pending outbound delivery are excluded.

The terminal run error includes typed recovery facts:

```json
{
  "code": "flow_worker_stalled",
  "message": "Flow execution heartbeat expired.",
  "source": "stale_running_reconciler",
  "retryable": false,
  "details": {
    "recovery": {
      "reason": "execution_heartbeat_expired",
      "heartbeat_at": "2026-09-20T18:00:00Z",
      "expires_at": "2026-09-20T18:03:00Z"
    }
  }
}
```

These timestamps use the database clock. Existing run history and provider
receipts remain available; unfinished provider calls have an unknown outcome.
Inspect that evidence before submitting a new run, since provider work may
already have happened.

## Abandoned waits

`flow_run_abandoned` means an approved review waited 30 days to resume, or a
queued run with exhausted dispatch attempts reached 30 days from
`dispatch_pending_since`. The maintenance sweep fails the run and keeps its
history and files. For an approved review, automatic abandonment cancels the
checkpoint as a system transition while preserving its approval timestamp and
decision actor.

The terminal error has `retryable: false` and `details.abandonment` containing
`wait` (`approved_review` or `exhausted_dispatch`), `anchor_at`, `deadline`, and
`checkpoint_id` for an approved review. These facts are separate from execution
heartbeat recovery. Inspect earlier external effects before submitting a new
run; abandonment does not establish that repeating the work is safe.

Before the sweep processes an overdue wait, resume and redrive requests return
`400 flow_run_abandoned` with the same facts in `context.abandonment`. They do not
terminalize the run; the sweep performs that transition, so the run may briefly
retain its waiting status after a refusal. After the sweep fails a run waiting
for review and cancels its approved checkpoint, resume returns
`400 flow_review_cancelled`.

| ----- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |

## How to handle codes

- Handle `Request path` codes from the failed API response before you create, edit, resume, or retry a failed run.
- Handle `Run execution` codes from `run.error.code` while polling or rendering a terminal failed run.
- Handle `Request path or run execution` codes in both places; the same logical failure can surface synchronously or after worker execution.
- Unknown codes should degrade gracefully: show a generic Flow failure message, keep the raw code for support, and avoid automatic destructive retries.
- Do not automatically retry an LLM request timeout or ambiguous step execution failure: provider work may or may not have started, and another run can duplicate provider work and spend.
- A failed `per_source` or `per_item` step has no partial continuation: retrying the failed run executes every source or item provider call in its unfinished mapped step, including calls that may already have completed.

[Retry a failed run](/guides/flows-api-guide#retry-a-failed-run-from-the-first-unfinished-step) creates a child run that reuses an eligible completed prefix and executes from the first unfinished step; it does not rerun an arbitrary step in place. It requires the same principal and current published version, so after changing the flow and republishing, start a new run.

## Transcription failures

For `typed_io_transcription_failed`, branch on
`error.details.transcription_failure_kind`. An admission refusal that exhausts
the step budget reports `flow_step_timeout` with kind `capacity`. The phase is
`transcription`.
`transcription_service_reason` contains at most 512 characters of service text
for display or support; do not parse it to decide how to recover.

| Kind        | Meaning                                                                                                     | Recovery                                                      |
| ----------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `input`     | The service rejected the audio or request, including HTTP 413 or 422.                                       | Correct the input before trying again.                        |
| `capacity`  | The service reported a capacity failure or refused admission with HTTP 429, or HTTP 503 with `Retry-After`. | Wait for capacity to recover and inspect earlier run effects. |
| `provider`  | The service failed, became unreachable, or supplied no more specific failure kind.                          | Check service health and the retained provider-call evidence. |
| `internal`  | Local transcription preparation failed, or the service reported an internal failure.                        | Ask an operator to investigate.                               |
| `cancelled` | The service reported that the accepted job was cancelled.                                                   | Check why it was cancelled before starting more work.         |

These kinds describe the failure, not whether repeating the flow is safe.
`typed_io_transcription_failed` still has `retryable: false`: earlier steps may
have produced effects. Eneo does not classify failures by searching service text.
Until the service supplies `failure_kind`, a failed job is classified as `provider`.

The last observed stage and queue position, when available, are retained in
`error.details.transcription_stage` and `transcription_queue_position` on
transcription failures and step timeouts. A missing queue position is unknown.

## Live transcription socket codes

The live transcription WebSocket reports a failure as an event, not as an HTTP
response, and closes the socket after it:

```json
{
  "type": "error",
  "code": "upstream_unavailable",
  "message": "The transcription server could not be reached.",
  "retryable": true
}
```

Branch on `code`. The failure affects only the preview: the run transcribes the
uploaded recording. `retryable` alone does not decide the next step, because a
new ticket starts a fresh session and cannot recover text after `stop`. See
[When a session ends with an error](/guides/flows/integrating-flows#when-a-session-ends-with-an-error)
for what to do while the recording runs and after it stops.

| `code`                                                 | When                                                                                                                                                            | `retryable` |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| `idle_timeout`                                         | No audio arrived within the idle timeout (default 300 seconds)                                                                                                  | `false`     |
| `invalid_audio_frame`                                  | A binary frame was empty, larger than 64 KiB, or had an odd number of bytes                                                                                     | `false`     |
| `invalid_message`                                      | A text frame other than `{"type": "stop"}` arrived                                                                                                              | `false`     |
| `duration_exceeded`                                    | The audio passed the session's `max_seconds`                                                                                                                    | `false`     |
| `model_unavailable`                                    | When the socket opened, the model was no longer usable for live transcription: switched off for live use, disabled, or on an inactive or misconfigured provider | `false`     |
| `upstream_unavailable`                                 | Eneo could not reach the model server                                                                                                                           | `true`      |
| `upstream_timeout`                                     | The model server stopped reading audio, or did not send the final text in time after `stop`                                                                     | `true`      |
| `upstream_closed`                                      | The model server closed the session                                                                                                                             | `true`      |
| `capacity_exceeded`, `falling_behind`, `model_loading` | The model server is full, behind, or still loading its model                                                                                                    | `true`      |
| `finalize_timeout`                                     | The model server could not send the final text within its own time limit after `stop`                                                                           | `true`      |
| `internal_error`                                       | The session failed unexpectedly                                                                                                                                 | `false`     |
| Any other code                                         | The model server reported an error of its own, passed through; `upstream_error` when it sent no code                                                            | `false`     |

A handshake that Eneo refuses sends no event: the upgrade request gets HTTP
`403`. The ticket request itself fails with the HTTP codes in the catalog
below, such as `flow_live_transcription_unavailable`.

## Catalog

Run admission measures file metadata across all steps before loading file content, including files retained by per-source previews. Extracted text and inline input share the inline text ceiling; binary documents and audio use their respective upload ceilings. A null file-count policy resolves to `FLOW_INPUT_MAX_FILES_COUNT` (1,000). The aggregate count cannot exceed that ceiling or the sum of the step limits.

Structured output uses the inline byte ceiling for both single calls and mapped steps. Mapped output includes runtime source fields and JSON framing in its UTF-8 byte count. An oversized result fails without a consumable partial output or a structured-output spill file. Completed provider evidence remains recorded. The error context reports `completed_items`, `total_items`, `measured_bytes`, and `ceiling_bytes`; terminal run errors retain these fields in `details`. Reduce the workload before starting a new run, since completed calls will repeat.
