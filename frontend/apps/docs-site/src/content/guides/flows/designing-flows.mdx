# Designing Flows

This page is for teams shaping a published Eneo Flow before integration work begins, and it helps you choose supported steps, inputs, review points, and artifact outputs.

You are in the design step of the consumer journey, where the flow shape is settled before the runtime endpoints are wired.

The reference guide keeps the full field catalog: [Flows API Guide](/guides/flows-api-guide).

## Building blocks

A Flow is a published graph of steps. Each step declares `input_source`, `input_type`, `output_type`, and `output_mode`.

Flow input can use HTTP GET, but Flow does not support HTTP POST input or MCP servers and tools. Terminal HTTP POST output remains available through the durable webhook outbox.

| Input mode | Output artifact | Output types | Output modes                | Use it when                                                                       |
| ---------- | --------------- | ------------ | --------------------------- | --------------------------------------------------------------------------------- |
| text       | structured_text | text         | pass_through                | Use for form fields, pasted text, and final text answers.                         |
| text       | structured_json | json         | pass_through                | Use when later steps or your app need structured fields.                          |
| documents  | structured_text | text         | pass_through                | Use for summaries, analyses, and human-readable reports.                          |
| documents  | structured_json | json         | pass_through                | Use for extraction before comparison, review, or artifacts.                       |
| documents  | pdf_document    | pdf          | pass_through                | Use when the final result should be a generated PDF artifact.                     |
| documents  | docx_document   | docx         | pass_through, template_fill | Use generated DOCX for free-form documents and template fill for fixed templates. |
| audio      | structured_text | text         | transcribe_only             | Use for transcription before later text, JSON, or artifact steps.                 |

<Callout type="warning">

**Not supported: Image input.**

Image input is not supported by the Flow runtime today.

Closest supported alternative: Convert the image into a supported document or text input before starting the run.

</Callout>

## Inputs done right

Use runtime uploads for files, form fields for caller choices, and pasted text for small text inputs.

Reserved `input_payload_json` keys stay owned by the backend; do not create form fields with reserved names.

```json
{
  "input_payload_json": {
    "case_type": "intake",
    "priority": "normal"
  },
  "step_inputs": {
    "STEP_ID": {
      "file_ids": ["RUNTIME_FILE_ID"]
    }
  }
}
```

### Design from the published contract

Before building a UI, inspect the runtime paths and run contract for the published flow version.

1. Call `GET /api/v1/flows/{id}/published/` to get runtime-safe paths for service-key or user clients.
2. Call `GET runtime_paths.run_contract` to get required form fields, file inputs, review steps, and final output.
3. Call `GET runtime_paths.graph` to get the published topology your app can show before a run.
4. Use `published_flow_version` as the version pin when your app creates a run.

Endpoint facts:

| Endpoint                           | Method | Success  | Operation                    |
| ---------------------------------- | ------ | -------- | ---------------------------- |
| `/api/v1/flows/{id}/run-contract/` | `GET`  | `200 OK` | `get_flow_run_contract`      |
| `/api/v1/flows/{id}/graph/`        | `GET`  | `200 OK` | `get_flow_graph`             |
| `/api/v1/flows/{id}/published/`    | `GET`  | `200 OK` | `get_published_flow_runtime` |

Contract coverage: These endpoints are contract-tested.

Errors you must handle: `flow_not_published`, `flow_deleted`, `flow_run_stale_version`.

## Chaining steps

Prefer targeted references such as `{{step_a.output.structured.fields}}` over broad all-previous-step prose.

Use JSON steps when another step or your app needs stable fields. Use text steps for human-facing prose.

## Knowledge, models, and artifacts

Attach knowledge only to the step that needs it. Different steps may use different model choices when the published Flow exposes that design.

Use DOCX template fill for fixed placeholders, DOCX create for generated documents, and PDF when the result is a final read-only artifact.

## Review design

Mark the step that needs human judgment for review. The run pauses at that step; arbitrary mid-run pause is not the supported model.

## Anti-patterns

<Callout type="warning">

**Anti-pattern: One giant step.**

One broad instruction hides which part failed and makes review harder.

Better design: split extraction, reasoning, review, and artifact rendering into separate steps.

</Callout>

Avoid chaining only through prose when a JSON contract would give your app stable fields.

Avoid baking runtime data into instructions. Put caller data in form fields or runtime file bindings.

## Worked scenarios

### Speech to structured report

Goal: Turn an audio upload into structured sections and a filled DOCX template.

| Step             | Input                | Output                          | Bindings                                | Knowledge      |
| ---------------- | -------------------- | ------------------------------- | --------------------------------------- | -------------- |
| Transcribe audio | Runtime audio upload | Text transcript                 | `step_inputs[transcribe].file_ids`      | None           |
| Extract sections | Transcript text      | JSON section headers            | `{{step_a.output.text}}`                | None           |
| Compose report   | Section JSON         | Report text                     | `{{step_b.output.structured.sections}}` | Step knowledge |
| Fill template    | Report text          | DOCX artifact (`template_fill`) | `{{step_c.output.text}}`                | Template asset |

The flow keeps speech, structure, prose, and template rendering in separate steps so each failure is visible and rerunnable.

Build coverage: This scenario is covered by the Flow AI Builder golden matrix.

### Document intake with human gate

Goal: Extract uploaded documents, pause for review, and produce a final artifact.

| Step            | Input                   | Output                  | Bindings                        | Knowledge         |
| --------------- | ----------------------- | ----------------------- | ------------------------------- | ----------------- |
| Extract upload  | Runtime document upload | JSON fields             | `step_inputs[extract].file_ids` | None              |
| Review fields   | Extracted JSON          | Approved or edited JSON | Review checkpoint               | Reviewer judgment |
| Create artifact | Approved JSON           | DOCX artifact           | `{{reviewed_fields}}`           | Template asset    |

The review checkpoint freezes the extracted fields before the artifact step consumes them.

Build coverage: This scenario is covered by the Flow AI Builder golden matrix.

### Compare and decide

Goal: Compare two uploads against caller-supplied criteria and return a recommendation.

| Step               | Input                           | Output              | Bindings                            | Knowledge |
| ------------------ | ------------------------------- | ------------------- | ----------------------------------- | --------- |
| Read first upload  | Runtime document upload         | JSON metrics        | `step_inputs[first].file_ids`       | None      |
| Read second upload | Runtime document upload         | JSON metrics        | `step_inputs[second].file_ids`      | None      |
| Recommend          | Both JSON outputs plus criteria | Text recommendation | `ALL_PREVIOUS_STEPS` and form field | None      |

The comparison step receives both structured extractions and a clear weighting field instead of prose-only chaining.

Build coverage: This scenario is covered by the Flow AI Builder golden matrix.

### Form intake to artifact

Goal: Use form fields to compose sections and generate a DOCX artifact.

| Step                  | Input               | Output        | Bindings                 | Knowledge               |
| --------------------- | ------------------- | ------------- | ------------------------ | ----------------------- |
| Collect sections      | Runtime form fields | Draft text    | `input_payload_json`     | None                    |
| Compose artifact body | Draft text          | Final text    | `{{step_a.output.text}}` | Optional step knowledge |
| Fill template         | Final text          | DOCX artifact | `{{step_b.output.text}}` | Template asset          |

The form-only path avoids fake uploads and makes every caller-provided value explicit in the run payload.

Build coverage: This scenario is covered by the Flow AI Builder golden matrix.
