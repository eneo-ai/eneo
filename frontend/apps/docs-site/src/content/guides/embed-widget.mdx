# Embed an Assistant on Your Website

import { Callout } from 'nextra/components'

A web widget puts a published assistant on an external website, for example a municipality's public site, as a chat bubble in the corner of every page. Visitors are anonymous: no Eneo account, no cookies, and nothing is stored until they send their first message.

This guide covers the editor's side (creating and publishing a widget), the operator's side (policy, templates, security and data protection) and what to publish in your accessibility statement.

## How it works

- Your site includes one small script (the *loader*, about 4 kB) from your Eneo installation. It renders a launcher button and, when opened, an `iframe` with Eneo's chat page.
- The chat runs entirely on the Eneo origin. The host site never sees the conversation, and the browser only allows the widget on the sites you have listed (`Content-Security-Policy: frame-ancestors`).
- Before the first message the visitor's browser solves an invisible proof of work (ALTCHA, self-hosted, no third party) and receives a short-lived visitor token. Rate limits per visitor and per IP address, a maximum question length and a daily token budget per widget cap the cost.
- Tools, MCP servers and file uploads are always off for visitors. The assistant answers from its instructions and knowledge only.

## For editors: publish a widget

You need the **widgets** permission and edit rights on the assistant.

1. Publish the assistant in its space (Assistant → **Publishing**).
2. On the same page, open **Web widget**. Create the widget, optionally from one of the organisation's templates.
3. Configure it. Every change is saved automatically. The page is organised in the order you work:
   - **Content**: name and language, then the texts visitors read: title, welcome message, suggested questions (added one by one, at most five), the required description under the title (by default an AI disclosure) and a footer note with an optional link (a data-handling reminder, a "powered by" line, whatever fits).
   - **Appearance**: start from one of the organisation's templates if you like, then the primary colour (a contrast check tells you when it is too light), an optional header colour and logo (Eneo's logo marks the spot until you set your own), colour scheme, position and corner radius. Text on your colours is chosen automatically for contrast. Colours chosen for a light page rarely work on a dark one, so **Dark mode** can have its own primary and header colour (checked against the dark panel); leave them empty and dark mode keeps the light-mode colours. The chat button on your site takes the widget's colour too. The live preview follows the theme you are using in Eneo unless the widget pins light or dark.
   - **Rules**: the websites that may show the widget (one origin per line, for example `https://www.kommun.se` or `https://*.kommun.se`; at least one is required), limits, privacy (retention in days; `0` stores nothing after the answer) and protection.
   - **Publish**: the activation checklist, the install snippet, "Test in Eneo" and usage.
4. Check the **Preview** (the real chat page) and, if you like, **Test in Eneo**, which mounts the real widget on the admin page so you can try the button, keyboard navigation and the chat before anything is installed on your site.
5. When the status bar shows no blockers, a tenant admin activates the widget. Until then the widget is a draft and shows nothing on your site.
6. Copy the **install snippet** and place it once on the website, preferably just before `</body>`:

```html
<script
  async
  src="https://eneo.example.se/widget/v1/eneo.js"
  data-widget-id="wgt_…"
></script>
```

The floating `v1` address follows Eneo releases. Sites that require Subresource Integrity can copy the pinned variant instead; it must be replaced after each Eneo release.

**Pause** stops the widget immediately for every visitor; any editor can pause. **Archive** (admins) is permanent.

### Optional attributes and API

| Attribute                                         | Effect                                          |
| ------------------------------------------------- | ----------------------------------------------- |
| `data-lang="sv"` / `"en"`                         | Fixed interface language (default: the page's)  |
| `data-position="bottom-left"`                     | Launcher on the left                            |
| `data-color-scheme="light"` / `"dark"`            | Fixed colour scheme (default: follows the site) |
| `data-launcher="none"`                            | No button; the site opens the chat itself      |
| `data-auto-open="true"`                           | Open the panel on page load                     |

The loader also exposes `window.Eneo`, which queues calls made before the script has loaded:

```html
<script>
  window.Eneo = window.Eneo || function () { (window.Eneo.q = window.Eneo.q || []).push(arguments); };
  Eneo("on", "conversation_started", function () { /* analytics */ });
</script>
<button onclick="Eneo('open')">Ask us</button>
```

Commands: `open`, `close`, `toggle`, `on(event, listener)`, `off(event, listener)`, `setContext({ page_url, page_title })`. Page context is only sent when the site calls `setContext`.

A stand-alone version of the chat is available at `/embed/<widget id>?mode=full` for sites that cannot run scripts.

## For operators: policy, templates and security

### Tenant policy

Under **Admin → Web widgets** a tenant admin sees every widget in the organisation (where it lives, whether it is active, questions and tokens over the last 7 and 30 days, blocked requests, today's budget) and sets the ceilings every widget must stay within: the highest daily token budget, the allowed retention range and whether widgets may run without bot protection (off by default). Editors see policy violations as activation blockers. There is no cap on the number of widgets; each activation is still an admin decision and the overview keeps the public surface visible.

### Templates

Templates hold the organisation's house style: texts, colours, logo, shape and language. Admins create them under **Admin → Web widgets → Templates** and preview them in light and dark mode; at most one template is the default that editors get preselected (switch it off and nothing is preselected). Applying a template copies its values onto the widget, so later template edits never change a live widget. Suggested questions are not part of a template: they depend on the assistant and are set per widget.

### Security properties

- **Who may frame the chat** is enforced by the visitor's browser from the widget's allowed origins. A site that is not listed gets a blank frame.
- **Visitor tokens** are JWTs bound to one widget and one pseudonymous visitor id, valid for 15 minutes and rotated silently. Pausing the widget or changing its origins, limits or privacy settings invalidates every outstanding token.
- **ALTCHA** is a self-hosted proof of work; no CAPTCHA provider, no cookies, no fingerprinting. Widgets without it require the tenant policy to allow it.
- **Limits fail closed.** If Redis is unavailable, the public endpoints answer `503` instead of letting traffic through unmetered.
- **The loader** is served from your Eneo origin with `nosniff`, open CORS (required for `integrity`) and an ETag; the pinned variant is immutable.
- The embed page sends `Referrer-Policy: strict-origin-when-cross-origin`, a restrictive `Permissions-Policy` and a CSP without `unsafe-inline` scripts.

### Personal data and cookies

The widget sets **no cookies**. The visitor's browser keeps a small record in the iframe's own storage (a random visitor id, the current token and the id of the last conversation) so the conversation survives a page reload on the same site. Nothing is written before the first message, and the storage is partitioned per site by the browser.

Suggested sentence for your cookie or privacy page: *"The chat assistant uses no cookies. Your browser stores a random identifier and the current conversation locally so you can continue it while browsing our site. Conversations are stored by [organisation] for [N] days."*

### DPIA checklist

Before activating a widget on a public site, confirm that:

- the description under the title says that visitors are talking to an AI assistant, and the footer links to your privacy policy;
- the retention period matches your records schedule (`0` if conversations must not be kept);
- free-text feedback is only stored if you have a purpose for it (off by default);
- the assistant's instructions tell visitors not to enter personal data and how to reach a human;
- the assistant's knowledge contains no personal data or internal material;
- the daily token budget reflects the cost you accept, and the usage view is reviewed regularly;
- audit logging is enabled: widget creation, changes, activation, pausing, archiving and budget exhaustion are logged.

## Accessibility

The widget is built for WCAG 2.1 AA: the launcher is a real button with an accessible name and a visible focus ring, the panel is a labelled `iframe`, opening moves focus into the chat, `Escape` closes it and returns focus, answers are announced to screen readers, everything works with the keyboard, colours meet contrast requirements and the panel becomes full-screen on small screens. Editors get a contrast check on the colour they choose.

### Accessibility statement template

Add a section like this to the website's accessibility statement (the template is available in Swedish and English; adapt the bracketed parts):

**Chattassistent**

Webbplatsen innehåller en chattassistent som drivs av [organisationens namn]s AI-plattform. Chatten öppnas med en knapp som går att nå med tangentbord och skärmläsare.
