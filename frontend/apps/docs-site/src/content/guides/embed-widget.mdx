# Embed an Assistant on Your Website

import { Callout } from "nextra/components";

A web widget puts a published assistant on an external website, for example a municipality's public site, as a chat bubble in the corner of every page. Visitors are anonymous: they need no Eneo account, the widget sets no cookies, and it stores no visitor identity until they send their first message.

This guide covers what visitors can reach, the editor's side (creating and publishing a widget), the website team's side (installing it), the operator's side (policy, templates, server settings, security and data protection) and what to publish in your accessibility statement.

## How it works

- Your site includes one small script (the _loader_, about 6 kB compressed) from your Eneo installation. Before it shows the launcher button, it reads the widget's saved language, position and colours from Eneo, so later edits reach the site without a new snippet. When opened, it shows an `iframe` with Eneo's chat page.
- The chat runs entirely on the Eneo origin. The host site never sees the conversation, and the browser only allows the widget on the sites you have listed (`Content-Security-Policy: frame-ancestors`).
- Before the first message the visitor's browser solves an invisible proof of work (ALTCHA, self-hosted, no third party) and receives a short-lived visitor token. Rate limits per visitor and per IP address, a maximum question length and a daily token budget per widget limit usage.
- Visitors talk to the assistant as it is configured, within fixed limits; see [What visitors can reach](#what-visitors-can-reach).

## What visitors can reach

A widget publishes the assistant as it is configured. There is no separate tool setting per widget. A visitor gets:

- **Knowledge**: the assistant's collections and websites, in the assistant's knowledge mode. In _On demand (search tool)_ the assistant searches them with Eneo's knowledge tool, which runs with the visitor's restricted widget identity and needs no Eneo account; otherwise relevant passages are retrieved and added to the question.
- **The assistant's own MCP servers**: those enabled on the assistant that the space's security classification allows, with their tools as configured. Visitors are anonymous: a server set to forward user identity receives no identity headers, and no tool call waits for anyone's approval. For servers outside Eneo, activation asks the tenant admin to acknowledge this, the overview shows which widgets have them, every call a visitor's turn runs on one is written to the audit log, and the tenant policy can forbid them; see [MCP servers outside Eneo](#external-mcp-servers).
- **Web search**, when both the space and the assistant have it switched on and the model can call tools. Web search runs on the organisation's external search server (see [Web search and image generation](/guides/capabilities)).

Never available to visitors, whatever the assistant's configuration: image generation, file analysis, file creation and charts, file uploads, built-in function providers, and images or files that a tool returns. Their content is dropped and the widget shows neither, though with **Show sources** on the title and address of an image a tool links to can still reach the visitor's browser. Visitors also get no tool for reading attachments, so an attachment set to _Open with tool_ is given to the model as text instead, like any other attachment. If the assistant's attachments then do not fit the model's context window, visitors' questions are refused and the server logs a warning; make the attachments fit or choose a model with a larger window. Only publish knowledge and tools that are appropriate for anonymous visitors.

<Callout type="warning">
  Changing the assistant's MCP servers or functions changes what an active
  widget exposes, immediately and without a new activation. Anything a server's
  tools can read or do, an anonymous visitor can ask the assistant to use. While
  an active widget publishes the assistant, its edit page says so at the top of
  the **Tools** section ("Published as a web widget") for everyone who can edit
  the assistant, with a link to the widget for those who manage widgets.
</Callout>

The widget's **Publish** tab lists what visitors get from the assistant as it is configured right now.

Every answer and restored conversation passes one filter on the server. The filter removes internal metadata about the model, reasoning, the assistants and Skills behind an answer, raw tool results and the contents of tool resources. The **Show sources** and **Show tool activity** switches decide which source references and details of tool calls are sent to the visitor; see [Sources, tool activity and feedback](#sources-tool-activity-and-feedback).

The switches do not filter the model's answer text. The assistant can repeat information from knowledge sources and tools in its answer, so publish only material and tools that suit anonymous visitors.

## For editors: publish a widget

You need the **widgets** permission and edit rights on the assistant.

1. Publish the assistant in its space (Assistant → **Publishing**).
2. On the same page, open **Web widget**. Create the widget, optionally from one of the organisation's templates. Use an assistant in a shared space. Organisation spaces cannot host widgets because anonymous visitors cannot read their assistants, and personal spaces are not supported yet: a widget belongs to the organisation, not to one account, and a widget through which a signed-in person reaches their own personal assistant is a separate, planned feature.
3. Configure it. Every change is saved automatically. The page is organised in the order you work:
   - **Content**: name and language, the **Show sources** and **Show tool activity** switches, then the texts visitors read: title, welcome message, suggested questions (added one by one, at most four), the required description under the title (by default an AI disclosure) and a footer note with an optional link (a data-handling reminder, a "powered by" line, whatever fits).
     The widget name is public, even with a separate title. Without a title, the chat uses the widget name as its heading.
   - **Persona** (also under Content): who answers. Give the chat a name (at most 30 characters, starting with a letter) and, if you like, an avatar: a square illustration or symbol, uploaded like an assistant icon, or copied from the assistant's icon. The header keeps your title; the welcome message becomes the persona's first message, under the same small byline (avatar, name and an **AI** marker) that every answer carries, and it stays at the top of the conversation. The marker is not a setting: a persona may be friendly, but visitors are always told they talk to an AI. Without an avatar the first letter of the name stands in. Leave the name empty and the chat answers without a sender, as before. **Show the avatar as the chat button** is off by default, because the button is the first thing visitors see, before the AI disclosure; switched on, the avatar replaces the chat bubble on your site, ringed in your colour with a small chat badge, and the button's accessible name becomes "Open chat with `<name>`, AI assistant". Do not use photos of real people.
   - **Appearance**: link the widget to one of the organisation's templates if you like (the parts the template locks are then read-only here until you detach it), then the primary colour (a contrast check tells you when it is too light), an optional header colour (the header shows your title; Eneo's own mark never appears there), colour scheme, position and corner radius. Text on your colours is chosen automatically for contrast. Colours chosen for a light page rarely work on a dark one, so **Dark mode** can have its own primary and header colour (checked against the dark panel); leave them empty and dark mode keeps the light-mode colours. The chat button on your site takes the widget's colour too, and its dark-mode colour on a dark page, from the moment it appears. The live preview follows the theme you are using in Eneo unless the widget pins light or dark.
   - **Rules**: the websites that may show the widget (one origin per line, for example `https://www.kommun.se` or `https://*.kommun.se`; at least one is required, at most 20; a wildcard needs at least two labels after the asterisk, so `https://*.se` is refused), limits, privacy (retention in days; `0` keeps no conversation after the answer, so the chat answers one question at a time without follow-ups or feedback; whether free-text feedback is stored) and protection. The organisation's policy bounds are shown at the fields they limit. While the widget is active, the websites, privacy and protection can only be changed by a tenant admin, because they are what the admin reviewed at activation; pause the widget to change them yourself.
   - **Publish**: the activation checklist, what visitors get access to, the install snippet, "Test in Eneo" and usage.
4. Check the **Preview** (the real chat page) and, if you like, **Test in Eneo**, which mounts the real widget on the admin page so you can try the button, keyboard navigation and the chat before anything is installed on your site. Both work for drafts and active widgets, not while the widget is paused: the pause closes every way into the chat page.
5. When the status bar shows no blockers, a tenant admin activates the widget. Until then the widget is a draft and shows nothing on your site. When the assistant uses MCP servers outside Eneo, activation first lists them with their tools and asks the admin to acknowledge that anonymous visitors can make the assistant call them ([MCP servers outside Eneo](#external-mcp-servers)).
6. Copy the **install snippet** and place it once on the website, preferably just before `</body>`:

```html
<script
  async
  src="https://eneo.example.se/widget/v1/eneo.js"
  data-widget-id="wgt_…"
></script>
```

The snippet carries nothing you can change later: the widget's saved language, position and colours reach every installed site within about a minute. The floating `v1` address follows Eneo releases. Sites that require Subresource Integrity can copy the pinned variant instead; it keeps loading its exact version after Eneo upgrades. Update the snippet when you want a newer loader (see [For the website team](#for-the-website-team)).

The editor checks each value against the rules the server applies before saving it: an allowed website must be an origin, not a page address; a name cannot be blank; values outside the organisation's policy are flagged at the field. A value the server still refuses stays on screen at its field with the reason and is held back while the rest of your changes keep saving; edit it to send it again. The status bar lists every change that was not saved.

On an active widget, the description under the title and the list of allowed websites cannot be emptied, so the live widget keeps serving. A field you empty stays on screen with the reason and is saved as soon as the widget is paused. An emptied list of allowed websites also counts as an unsaved change, so leaving the page asks first. If an active widget stops serving as configured, for example because the assistant was unpublished, the status bar, the **Publish** tab and the organisation's overview say what needs fixing. Newly loaded site pages hide its chat button; visitors with an already open chat see a short "not available" notice when they try to use it. The same reports appear when the assistant can no longer answer, for example because its model was removed from the space, but then the chat button stays: visitors who ask see the same notice. The notice never says what failed; the reason is in the server log.

If another editor changes the widget while you edit, autosave stops and keeps your unsaved values visible. Copy anything you want to keep, then choose **Reload and discard unsaved changes** before editing the latest version. A stale save cannot undo a pause or archive.

**Pause** stops the widget immediately for every visitor; any editor can pause. **Archive** (admins) is permanent.

While a widget is active, its allowed websites, privacy, bot protection and template link are a tenant admin's call: an editor's change to them is refused with a note at the field. Pause the widget to change them yourself; an admin then reviews the widget again when activating it. Detaching a template on an active widget is refused for the same reason, since the template's locks hold only while the widget follows it.

### Sources, tool activity and feedback

**Sources.** With **Show sources** on (the default), answers carry numbered citations and a collapsed source list ("3 sources") under the answer; a citation number opens the list at its source. Knowledge added to the question comes first, then what the answer cites from tools, one entry per document. Knowledge the assistant searched with its knowledge tool is listed like other knowledge: by the document the answer cites, never by passage. A web page links to the page, opening in a new tab. An uploaded document has no public link: the visitor can choose **Copy reference**, which copies the document's title and an Eneo address (`https://<eneo>/documents/<id>`), and is asked to send it to an administrator of the chat. Anyone signed in to Eneo who opens that address sees the document (its collection or website, its text and, when stored, the original file) if they may read it; everyone else is told it is not available to them, without learning whether it exists. A tool result without a web link is listed as coming from a service the assistant used. With **Show sources** off, the server sends no source titles, links, citation markers or source lists with the answer, so the widget shows no numbered citations. A step of Eneo's knowledge tool then shows its search terms at most, never a document or source. The model's answer text can still contain source titles and links.

**Tool activity.** With **Show tool activity** on (the default), visitors see which tools and MCP servers an answer uses while it is being written ("via TimeMCP"): the tool's catalog title, or its technical name when it has none, and one value the assistant passed to it. Eneo's own knowledge search and web search read as one sentence with the search terms, such as "Searched knowledge for “opening hours”", without a server name. Several steps fold into one line that opens to the list. Raw tool results are not sent to the visitor. With the switch off, no structured tool activity is sent to the visitor. The tools still run, and sources they return can still be listed when **Show sources** is on. The switch does not stop the model from naming a tool or service in its answer text.

**Feedback.** When the widget keeps conversations (retention above `0`), visitors can rate the whole conversation with a thumbs up or down. After a vote, the question and thumbs collapse into an acknowledgement and **Change rating**; follow-up questions keep that acknowledgement rather than asking again. Votes are counted in the widget's usage and the organisation overview on the day the conversation started, also when a vote is changed later. With **Store free-text feedback** on (off by default), a link follows the vote ("Want to tell us more?", or "Tell us what was missing" after a thumbs-down) and opens a dialog with a comment box (at most 2 000 characters), which the visitor can ignore. New comments are stored only while that setting is on. Switching it off stops new comments; previously stored comments follow the conversation's retention and are deleted with it. Changing the vote afterwards keeps the comment. **Edit comment** reopens the saved text and replaces it when submitted.

### Optional attributes and API

The copied snippet carries only `data-widget-id`. These optional attributes are for the website team:

| Attribute                              | Effect                                                                                                                                                                    |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data-lang="sv"` / `"en"`              | The host page's language, used while the widget's language is **Automatic** (default: the page's `lang`). A widget set to Swedish or English keeps it.                    |
| `data-position="bottom-left"`          | Fallback only, used when the saved settings cannot be read. Otherwise the widget's saved position applies.                                                                |
| `data-color-scheme="light"` / `"dark"` | The host page's colour scheme, used while the widget's colour scheme is automatic (default: the visitor's system setting)                                                 |
| `data-launcher="none"`                 | No button; the site opens the chat itself                                                                                                                                 |
| `data-launcher="static"`               | Keep the button in place on phones; by default it tucks into the edge while the page scrolls down (see below)                                                             |
| `data-auto-open="true"`                | Open the panel on page load                                                                                                                                               |
| `data-label="…"`                       | Accessible name of the button (default "Öppna chatt" / "Open chat", or "Öppna chatt med `<name>`, AI-assistent" / "Open chat with `<name>`, AI assistant" with a persona) |
| `data-frame-title="…"`                 | Accessible name of the chat frame (default "Chatt" / "Chat")                                                                                                              |

**On phones** (viewports up to 40em wide) the button is 48 px instead of 56 px, keeps 16 px from the edges plus the device's safe area, and tucks halfway into the edge while the visitor scrolls down, so it does not cover the text being read. It comes back when they scroll up, stop for a second, move keyboard focus to it, open the chat, or when a reply is waiting. It is the same button throughout, so keyboard and screen reader users are not affected. `data-launcher="static"` turns the tucking off; a site with reduced motion gets the moves without animation.

**Size and placement from the site's CSS.** The loader reads these custom properties from the `<eneo-widget>` element or `:root`: `--eneo-widget-size` (the button's diameter), `--eneo-widget-offset-x` and `--eneo-widget-offset-y` (distance from the corner), `--eneo-widget-z`, `--eneo-widget-radius` (the panel's corners) and `--eneo-widget-color` / `--eneo-widget-on-color` (override the widget's own colour, which also switches off its contrast check). The button and the panel are exposed as `::part(launcher)` and `::part(panel)`, for example `eneo-widget { --eneo-widget-size: 44px; --eneo-widget-offset-y: 80px; }` to clear a sticky footer. A site that wants no floating button at all uses `data-launcher="none"` with its own link.

The loader also exposes `window.Eneo`, which queues calls made before the script has loaded. To open the chat from your own button, add the button and a script file from your own site:

```html
<button type="button" data-eneo-open>Ask us</button>
<script defer src="/assets/eneo-chat.js"></script>
```

Contents of the site's `/assets/eneo-chat.js`:

```js
window.Eneo =
  window.Eneo ||
  function () {
    (window.Eneo.q = window.Eneo.q || []).push(arguments);
  };

document.querySelectorAll("[data-eneo-open]").forEach((button) => {
  button.addEventListener("click", () => window.Eneo("open"));
});

window.Eneo("on", "conversation_started", () => {
  /* analytics */
});
```

The example needs no inline JavaScript, so it works with a strict Content Security Policy that allows the site's own script file. The widget's ordinary install snippet must also be on the page.

Commands: `open`, `close`, `toggle`, `on(event, listener)`, `off(event, listener)`. The loader also accepts `setContext({ page_url, page_title })`, but the chat does not use page context yet, so nothing about the page is sent.

A stand-alone version of the chat is available at `/embed/<widget id>?mode=full` for sites that cannot run scripts.

## For the website team

The editor in Eneo hands you the install snippet; this is what you need to know to put it on the site.

1. **Where to paste it.** Once per page template, ideally just before `</body>`. In SiteVision and Optimizely (Episerver) that is the site template's script slot; in WordPress a footer script block or a theme's `footer.php`; through Google Tag Manager a Custom HTML tag fired on all pages. The script is `async`, so it never blocks rendering.
2. **The address must match exactly.** The editor lists the sites that may show the widget under _Rules → Allowed websites_. Each entry is a full origin: scheme and host, for example `https://www.kommun.se`. `https://kommun.se` and `https://www.kommun.se` are two different origins, and `http` is not `https`. A wildcard covers subdomains: `https://*.kommun.se`. If the origin is missing, the button appears but the panel stays empty, because the browser refuses to frame the chat.
3. **Content Security Policy.** If the site sends a CSP, allow the Eneo origin in `script-src` (the loader), `style-src` (its external stylesheet), `connect-src` (saved settings from `/widget/settings/<widget id>`) and `frame-src` (the chat panel), for example `script-src 'self' https://eneo.kommun.se; style-src 'self' https://eneo.kommun.se; connect-src 'self' https://eneo.kommun.se; frame-src https://eneo.kommun.se`. If the policy sets `style-src-elem` separately, allow the Eneo origin there too. Without `style-src` the launcher and panel lack their layout; without `connect-src` the button falls back to its default position, language and colours, and the browser reports a CSP violation. The chat's own requests run inside the frame on Eneo's origin. A widget that shows its persona's avatar as the chat button also needs the Eneo API origin in `img-src` (the avatar is served from `/api/v1/icons/…` there); blocked, the button falls back to the chat bubble.
4. **Make the chat easy to find.** The loader adds its button at the end of the page, so keyboard and screen reader users reach it last. Add a visible link such as "Chat with us" early on the page, for example next to the contact details, that calls `Eneo('open')` (see _Optional attributes and API_ above). With `data-launcher="none"` that link replaces the floating button.
5. **Cookies and consent.** The widget sets no cookies. When the visitor sends their first message, the chat frame starts using `localStorage` for a pseudonymous visitor id, its credentials and the current conversation's id. Browser storage rules vary, so continuation across pages or visits is not guaranteed. Assess whether this storage requires consent on your site, including whether a strictly necessary exception applies, and describe it in the site's privacy information; see _Personal data and cookies_ below.
6. **Locked version (SRI).** If your policy requires Subresource Integrity, copy the pinned snippet with the `integrity` attribute instead of the floating one. Its address contains the loader's version, and that version's JavaScript and any associated stylesheet remain available with unchanged bytes after Eneo upgrades. The external stylesheet also carries an integrity check. The old snippet keeps loading; copy a newer one from **Publish** when you want loader fixes. The floating `v1` address follows releases automatically.
7. **Test before go-live.** Open a page with the snippet on a staging host that is on the allowed list, click the launcher, send a question, close with Escape and check that focus returns to the button. Also try it with the keyboard only, with a screen reader, on a phone and with the browser zoomed to 200 %. The editor can also use _Test in Eneo_ to try the real widget before your site has it.
8. **No JavaScript on the page?** Link to the stand-alone chat instead: `https://<eneo>/embed/<widget id>?mode=full`. It is the same chat as a full page and works from intranets and content that cannot run scripts.

## For operators: policy, templates and security

### Tenant policy

Under **Admin → Web widgets** a tenant admin sees every widget in the organisation (where it lives, whether it is active, questions and tokens over the last 7 and 30 days, blocked requests, today's budget) and, on the **Policy** tab, sets the ceilings every widget must stay within: the highest daily token budget (default 2 000 000, at most 2 000 000 000), the allowed retention range (default 0–365 days), whether widgets may run without bot protection (off by default) and whether widgets may publish assistants with MCP servers outside Eneo (on by default; see [MCP servers outside Eneo](#external-mcp-servers)). Only admins change the policy. Everyone with the widgets permission can read it, so the widget editor shows its bounds on the **Rules** tab and flags values outside them before saving; editors see remaining violations as activation blockers. There is no cap on the number of widgets; each activation is still an admin decision and the overview keeps the public surface visible.

The policy applies to existing widgets as it stands, not only to later edits:

- A daily budget above the maximum is capped to it for visitors, and usage figures show the budget that applies.
- The nightly retention job keeps each widget's conversations within the allowed range. A widget set to `0` still keeps no conversations, even when the minimum is higher.
- When widgets are no longer allowed to run without bot protection, those widgets require the proof of work again at once and their outstanding visitor tokens stop working. Editors who have such a widget open must reload before their next save.

The widget keeps its own saved values and shows them as policy violations to fix.

### Templates

Templates hold the organisation's house style: texts, colours, shape, language and persona (name, avatar and whether the avatar is the chat button). Admins create them under **Admin → Web widgets → Widget templates** and preview them in light and dark mode; at most one template is the default that editors get preselected (switch it off and nothing is preselected).

A template has a draft and a **published** version. Saving edits the draft (previewed on the template page, never pushed); **Publish** makes the draft the version widgets link to. A widget **follows** the template it was created from or linked to: linking copies the published texts, appearance and language onto the widget once. The template's **locked parts** then stay in step: every publication writes them onto all widgets that follow the template, in the same request, and those parts are read-only in the widget editor. Publishing to widgets that follow the template asks for confirmation first. Unlocked parts are starting values editors may change. The lockable parts are appearance, language, disclosure and footer, and wording (title, welcome message, placeholder); new templates lock appearance and language. Locking the disclosure requires the template to have one, so a live widget can never lose its AI disclosure through a template. Suggested questions are never part of a template: they depend on the assistant and are set per widget. Locked language and appearance reach installed sites like any other edit, without a new snippet.

The template page shows how many widgets follow it and whether the draft has unpublished changes; the template list marks templates that are not published yet. Only published templates are offered when a widget is created or linked, and the picker previews the published version, not a draft that may be ahead of it. Before a publication reaches followers, the confirmation lists which parts are replaced on the widgets, which locks are new or released, and which changed parts are unlocked and therefore stay as editors set them. A widget can **reapply** its template at any time, which copies the published version onto it again, unlocked parts included, or be **detached**; a detached widget keeps its current values and every part becomes editable again. A template that widgets still follow cannot be deleted. Editors with an open widget page are told to reload when the template changed their widget underneath them.

### When the assistant changes

- **Tools and functions.** A change to the assistant's MCP servers or functions reaches visitors at once; see [What visitors can reach](#what-visitors-can-reach).
- **Unpublishing** the assistant takes an active widget offline. Visitors see the "not available" notice, and the widget shows what needs fixing.
- **Moving** the assistant to another space archives its draft widgets and records each in the audit log. The move is refused while an active or paused widget serves the assistant, because the widget belongs to the assistant's space; an administrator archives that widget first.
- **Deleting** the assistant archives its widgets in the same step and records each in the audit log. A template those widgets followed can then be deleted.

### MCP servers outside Eneo [#external-mcp-servers]

A widget publishes the assistant with its MCP servers ([What visitors can reach](#what-visitors-can-reach)). For a server outside Eneo, that means:

- **Visitors are anonymous and their questions are untrusted input.** A question can carry instructions to the assistant (prompt injection is trivial on a public page), and no human approves a tool call in a visitor's turn: the approval step signed-in users get does not exist on the widget surface. Anything a tool can read or do, a visitor can make the assistant do, with arguments of the visitor's choosing.
- **Prefer tools that only read**, or servers that check what they are asked to do themselves. An MCP server reached from a widget must treat every argument as untrusted input: validate it, authorise the operation on its own side, and keep its own record of what it did.
- **Activation asks for an acknowledgement.** When the assistant has such servers, the widget's status bar says so, and **Activate** opens a dialog listing the servers with their tools. The tenant admin confirms that they understand and accept this before the widget goes online. The acknowledgement is stored on the widget with the servers it covered and recorded in the audit log. When the assistant's set of external servers changes afterwards, the status bar and the overview flag the active widget ("needs fixing"), and the next activation asks again. Resuming a paused widget whose servers are unchanged asks nothing new.
- **The overview shows which widgets reach outside Eneo**, with the servers' names, so the organisation's public surface can be reviewed without opening every widget.
- **Every tool a visitor's turn runs on such a server is written to the audit log** (`widget_external_tool_called`), whatever the widget's retention. The entry names the widget, the pseudonymous visitor id, the conversation, the server, the tool and whether the call succeeded, and the names of the arguments but not their values, which may carry the visitor's personal data. A write to an external system triggered by an anonymous visitor therefore leaves a trace even when the conversation itself is never stored.
- **The policy switch "Allow widgets with MCP servers outside Eneo"** (on by default) lets an organisation refuse this altogether: switched off, such a widget cannot be activated, and a live one is flagged in the overview until it is paused or its assistant loses the servers. The switch is on by default because an assistant whose purpose is to write to an external system (a case system, a booking) must still work as a widget; the acknowledgement, the flag and the audit trail are the guardrails for that choice.

Web search providers are not external servers in this sense: the organisation chose the provider for everyone, and it only reads. Eneo's own knowledge and files servers are not either.

### Security properties

- **Who may frame the chat** is enforced by the visitor's browser from the widget's allowed origins. A wildcard origin needs at least two labels after the asterisk (`https://*.kommun.se`); a wildcard over a whole top-level domain (`https://*.se`) is refused when saved, and one saved before this rule is reported as a blocker and never served. A site that is not listed gets a blank frame. A paused widget has no chat button on newly loaded pages. A chat opened before the pause shows a short "not available" notice on its next request. The chat page is the only part of Eneo that can be framed: every other page answers with `frame-ancestors 'none'` and `X-Frame-Options: DENY`, so an intranet portal that used to show Eneo in a frame has to link to it instead.
- **A suspended organisation's widgets** are treated as paused on the whole visitor surface: newly loaded pages hide the chat button, an already open chat shows the "not available" notice on its next request, and no challenge or visitor token is issued.
- **Protection against automatic requests to external addresses.** The chat page's Content Security Policy blocks external image requests and limits the page's network connections to Eneo's own addresses, so an external image address in an answer cannot automatically fetch an image from a third party. Answers can contain external links that the visitor chooses to open, and the assistant's configured tools can communicate with external services. Assess those services when you publish the assistant.
- **Visitor tokens** are JWTs bound to one widget and one pseudonymous visitor id, valid for 15 minutes and rotated silently. They are signed with a key of their own, derived from the backend's `JWT_SECRET`, so a visitor token is never accepted as a user's sign-in. Pausing the widget, or changing its origins, limits, privacy or bot protection, invalidates every outstanding token, as does a policy change that forbids running without bot protection. The preview token behind **Preview** and **Test in Eneo** is a visitor token too: it lives 15 minutes (the preview renews it), is minted for draft and active widgets but never for a paused one, and every mint is recorded in the audit log.
- **ALTCHA is a cost barrier, not bot protection.** It is a self-hosted proof of work; no CAPTCHA provider, no cookies, no fingerprinting. Widgets without it require the tenant policy to allow it. A challenge is signed for the widget that issued it, and only that widget accepts its solution, once.
  Proof of work makes each visitor identity cost a few hundred milliseconds of
  computation in a browser (about 16 000 hash iterations with the defaults,
  measured at 0.24 s per attempt in headless Chromium); a purpose-built client
  solves the same challenge in milliseconds. It stops naive scripts and nothing
  more: it does not prove that a visitor is human and does not authorise access
  to anything. The protection that holds against an adversary is the
  server-side rate limits and the daily token budget, which is what the
  defaults are built around; raise `WIDGET_ALTCHA_COST` and
  `WIDGET_ALTCHA_KEY_PREFIX` for an abused widget. Verification
  uses ALTCHA's solver in one same-origin worker, without a hidden form or a
  third-party service. The complete attempt has a 30-second deadline; errors
  let the visitor retry, and leaving the chat stops its worker.
- **The widget admin API is session-only.** Widgets, the tenant policy, templates (a publication writes onto every live widget) and the overview can be read and changed only from a signed-in browser session. No API key, however scoped, reaches any of it.
- **An active widget's governed settings are an admin's call.** Allowed websites, privacy, bot protection and the template link are what the tenant admin reviewed at activation; an editor changes them by pausing the widget first, which makes the next activation a new review.

- **Limits fail closed by default.** Redis protects request rates and challenge replays. The daily token budget and in-flight reservations are stored in PostgreSQL, so losing Redis data does not reset that budget.
- **Budget accounting** reserves tokens before a turn and replaces the reservation with that answer's measured usage exactly once, counting every round of tool calls. A failure before streaming releases the reservation. If a stream or process stops with uncertain usage, its reservation remains charged for that day. The reservation size is an admission estimate, not a hard maximum for a model response; actual usage can exceed it. A widget whose daily budget is below the reservation size reserves its whole budget instead, so it answers one question a day.
- **The loader** is served from your Eneo origin with `nosniff`, open CORS (required for `integrity`) and an ETag; the pinned variant is immutable. The saved settings it reads are the widget's public display settings and are cached for a minute.
- The embed page sends `Referrer-Policy: strict-origin-when-cross-origin`, a restrictive `Permissions-Policy` and a CSP without `unsafe-inline` scripts.

### Server settings

Operators can tune the visitor surface with backend environment variables. The defaults suit most installations.

| Variable                                 | Default            | Meaning                                                                                                                                                                                             |
| ---------------------------------------- | ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WIDGET_VISITOR_TOKEN_TTL_SECONDS`       | `900`              | Lifetime of a visitor token. The chat renews it silently.                                                                                                                                           |
| `WIDGET_VISITOR_TOKEN_GRACE_SECONDS`     | `900`              | How long after expiry a token can still prove the visitor's identity for a renewal without a new proof of work. At most the lifetime; a renewed token's predecessor stops working at once.          |
| `WIDGET_PREVIEW_TOKEN_TTL_SECONDS`       | `900`              | Lifetime of the token behind **Preview** and **Test in Eneo**. The preview gets a new token shortly before it expires; Test in Eneo does not, so remove the widget from the page and show it again. |
| `WIDGET_ALTCHA_COST`                     | `1000`             | Hash iterations per proof-of-work attempt (at least 1000). Raise it for an abused widget.                                                                                                           |
| `WIDGET_ALTCHA_KEY_PREFIX`               | `0`                | One to four hexadecimal characters each attempt must hit; every extra character makes a solve 16 times more expensive. The default keeps a first message under a few seconds on a phone; `00` would cost visitors about 4 s while a purpose-built client still solves it in milliseconds, so raise it per installation when a widget is abused, not as a default. |
| `WIDGET_ALTCHA_CHALLENGE_TTL_SECONDS`    | `300`              | How long a challenge stays valid.                                                                                                                                                                   |
| `WIDGET_CHALLENGE_RATE_LIMIT_PER_MINUTE` | `60`               | Challenge requests, and separately visitor-token requests, per widget and IP address per minute.                                                                                                    |
| `WIDGET_RATE_LIMIT_FAIL_OPEN`            | `false`            | What happens when Redis is unavailable: `false` refuses widget traffic (`503`); `true` skips the rate limits and the challenge replay check, so one solved proof of work can be reused meanwhile.   |
| `WIDGET_BUDGET_TIMEZONE`                 | `Europe/Stockholm` | Time zone whose midnight starts a new budget day.                                                                                                                                                   |
| `WIDGET_BUDGET_RESERVATION_TOKENS`       | `8000`             | Tokens reserved against the daily budget before each answer and settled to the measured usage afterwards. An admission estimate, not a cap on an answer.                                            |
| `WIDGET_RETRIEVAL_CHUNKS`                | `30`               | Knowledge passages retrieved for each visitor question.                                                                                                                                             |

The per-widget limits (messages per visitor and per IP address, question length, conversation length, daily budget) are set on each widget's **Rules** tab. The tenant policy caps the daily budget. The per-IP limit defaults to 60 messages an hour, at most 1 000, which matches one visitor's default allowance. A school, a library or a town hall can have many visitors sharing one public IP address, so set the limit to match the expected use and keep visitors from using up the shared allowance too quickly.

### Behind a reverse proxy

The IP-based limits (messages per IP address, challenge and visitor-token requests) are keyed on the client's IP address as Eneo sees it. Behind Traefik, Dokploy, nginx or any other reverse proxy that means the proxy's address unless the backend is told how many proxies stand in front of it: set `TRUSTED_PROXY_COUNT` (and, if your proxy uses another header than `X-Forwarded-For`, `TRUSTED_PROXY_HEADERS`) on the backend. Without it every visitor shares one bucket, and the whole site is throttled once the first visitors have used up the per-IP allowance.

The IP-based limits count an IPv4 address on its own and an IPv6 address by its /64 network, because one connection usually holds a whole /64 and could otherwise use a new address for every request.

### Personal data and cookies

The widget sets **no cookies**. When the visitor sends their first message, the iframe writes a small record to its own `localStorage`: a random visitor id issued by Eneo, a key that proves it, the current token with its expiry time and the id of the current conversation. The conversation text itself is not stored there. This can let the visitor continue after a page reload. With retention `0` the record holds no conversation id and the chat cannot be continued. Browsers may partition, clear or block third-party frame storage, so that continuation is not guaranteed. As soon as the chat page loads, the web framework also keeps the page's scroll position in the frame's `sessionStorage`, with no visitor identity or conversation content. Local storage can fall under the same consent rules as cookies; the site operator must assess its purpose and whether a strictly necessary exception applies.

Suggested text for your cookie or privacy page: _"The chat assistant uses no cookies. When you send your first message, the chat frame stores a random visitor identity, its credentials and the id of the current conversation in your browser's local storage. This may let you continue the chat while browsing our site. The conversation text itself is not stored in this local storage. Conversations are stored by [organisation] for [N] days."_

For a widget with retention `0`: _"The chat assistant uses no cookies. When you send your first message, the chat frame stores a random visitor identity and its credentials in your browser's local storage. The conversation is not kept on the server after the answer is finished, and the conversation text is not stored in this local storage."_

### Conversation retention

The worker removes expired widget conversations daily at 03:30 UTC, including their questions, source references, feedback and question-owned model logs. Each widget's own retention applies, held within the tenant policy's range; the conversation retention set for the assistant, the space or the organisation never deletes widget conversations. Knowledge sources and audit records have their own lifecycles. With retention set to `0`, the conversation is not kept after the answer is finished. Conversation data is handled temporarily in the server's database transaction and deleted before that transaction completes, including when budget settlement fails. The visitor is then offered a new question instead of a follow-up or feedback. Retention `0` covers what Eneo keeps: the question still goes to the model and the assistant's tools, and it does not turn off the browser's local storage of the visitor identity and token. Changing an existing widget to `0` also makes its earlier conversations eligible for the next scheduled purge.

Daily usage totals and budget receipts contain no conversation text or visitor identifier. Receipts expire after seven days; daily totals remain available for statistics.

### DPIA checklist

Before activating a widget on a public site, confirm that:

- the description under the title says that visitors are talking to an AI assistant, and the footer links to your privacy policy;
- the retention period matches your records schedule (`0` if conversations must not be kept);
- free-text feedback is only stored if you have a purpose for it (off by default);
- the assistant's instructions tell visitors not to enter personal data and how to reach a human;
- the assistant's knowledge contains no personal data or internal material;
- every MCP server and function the assistant uses is acceptable for anonymous public use: what its tools can read or do, a visitor can ask for, and later changes to the assistant apply at once ([What visitors can reach](#what-visitors-can-reach));
- for every MCP server outside Eneo, the acknowledgement given at activation is a decision you stand behind: its tools treat their arguments as untrusted input, prefer reading over writing, and the audit entries of their calls are reviewed ([MCP servers outside Eneo](#external-mcp-servers));
- the names of the assistant's MCP servers read well in public: visitors see them as the source of tool activity ("via TimeMCP"), and tools without a catalog title show their technical name. Turn off _Show tool activity_ to keep tool and server names internal; the tools still run;
- the daily token budget reflects the cost you accept, and the usage view is reviewed regularly;
- audit logging is enabled: widget creation, changes (with the settings before and after), activation (with the acknowledged external servers), pausing, archiving, budget exhaustion, every preview token minted and every tool a visitor's turn ran on an MCP server outside Eneo are logged.

## Accessibility

The widget is designed with the goal of meeting WCAG 2.2 level AA. These features support accessible use:

- The launcher is a real button with an accessible name and a visible focus ring, and every control in the chat shows a visible focus indicator. The panel is a labelled dialog, and the chat frame is named after the widget.
- Opening moves focus into the chat. `Escape` closes it, also when focus has moved on to the page; focus then returns to the button, or stays where the visitor moved to. In the enlarged layout the first `Escape` shrinks the chat and the next closes it. Choosing a suggested question keeps focus in the chat: on the input, or on the heading on a touch screen.
- Screen readers hear that a question was sent and then the finished answer, once, and are told when a reference is copied. The answer is never read word by word while it is written.
- Beside the page the panel is a non-modal dialog, so the page stays usable while the visitor chats. On phones it opens from the bottom as a rounded modal panel, keeping its rounded top corners when the keyboard opens; wide, short windows, such as a laptop screen zoomed to 200 %, use the full height. The page behind it cannot scroll and is hidden from screen readers and the keyboard until the chat is closed. The floating launcher is hidden while open, and a close button at the top remains available even while the chat loads. Closing restores the page's scroll position. Reduced-motion preferences disable the opening animation.
- On wider screens the chat's header offers **Enlarge chat**, which gives the same full-window modal dialog as on a phone; the same button, now **Shrink chat**, puts the panel back beside the page, and so does closing. Screen readers hear when the chat is enlarged or back to its usual size, and in a wide panel the conversation and the question field keep a readable column width.
- While the embedded page loads, a small indicator and a localized loading message appear; reduced-motion preferences disable the animation. An error page remains visible if the chat cannot start.
- Suggested questions sit below the welcome text in the scrollable conversation, rather than above the input. They disappear when the visitor starts typing. On touch screens they also hide while the input is focused, leaving room for the keyboard.
- The input stays at the bottom when the phone keyboard opens. Text can be enlarged: if the header, input and minimum reading area no longer fit, the whole panel scrolls so every control remains reachable.
- The chat follows the browser's settings for colour scheme and reduced motion. The focus ring takes the widget's own colour where it reads against the panel, and the launcher and buttons keep their edges in Windows contrast themes.
- The editor shows a contrast check for the chosen colours but does not stop an unsuitable choice. Check the contrast in both light and dark mode, especially if the site replaces the widget's colours with its own CSS.
- The description under the title is shown on two lines; a longer text gets a **Show all** control, so a long AI disclosure never pushes the conversation down on a phone. Screen readers get the whole text either way.
- The chat runs in its own frame on the Eneo origin, so the browser's own settings reach it (zoom, default font size, colour scheme, reduced motion, forced colours, screen readers and browser extensions) while the host site's own aids do not: a text-size control that changes the page's root font size, a contrast mode set by a class on the page, or a read-aloud service that reads the page's content stops at the frame. Say so in the accessibility statement and point to the browser's settings and the stand-alone page.

Check accessibility on the site where the widget is installed, with your own texts, colours, links and any customisations. Adapt the accessibility statement template to the results of your own review.
