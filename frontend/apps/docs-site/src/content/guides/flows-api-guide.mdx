# Flows API Guide

This guide is for developers building applications on top of published Eneo Flows, such as transcription services, municipality intake services, or other multi-step AI workflows.

It focuses on the **runtime** API. For the mental model behind drafts, steps, ownership, and evidence, start with <a href="/docs/flows">Flows</a>.

Reference owners: `FlowRuntimePathsPublic` defines runtime links, `FlowRunContractPublic` defines input/output fields, and `FlowApiErrorCode` defines machine-readable failures.

## Before you start

A few rules matter up front:

- only **published** flows can be run
- draft editing and AI Builder require a user principal
- a flow run is owned by the execution principal: a user principal or a service key
- service keys can run published flows, but they can access only **their own** runs and artifacts

### Authentication

Runtime examples in this guide use `Authorization: Bearer ...` for a user token. API keys use the API-key header instead:

```http
X-API-Key: $ENEO_API_KEY
```

Do not put an API key in the bearer-token header. Both user-owned and service-owned API keys authenticate through `X-API-Key`; their ownership, scope, top-level permission, and resource permissions determine which Flow operations are allowed.

For the underlying auth model, see:

- <a href="/docs/api-key-management">API Key Management</a>
- <a href="/guides/authentication">Authentication & OIDC</a>

<Callout type="warning">
  Service keys do not get broad operator access. If a service key needs access
  to its own run evidence, it needs <code>flows &gt;= read</code> plus the
  appropriate explicit <code>flow_evidence</code> capability on the key.
</Callout>

## Authentication and principal model

A Flow run is owned by the principal that created it.

- **Human user** → owns their own run
- **Service key** → owns the runs created with that key
- **Space owner / space admin** → trusted in-space operator for support/debug surfaces
- **Tenant admin** → trusted tenant-wide operator

### What “own run” means

An **own run** is a run created by the current principal. It does not mean “any run in my space”.

That distinction matters because service keys and ordinary human members are intentionally not cross-run operators.

## User-principal vs service-key runtime surfaces

### Endpoint families that require a user principal

| Endpoint family                           | Why it requires a user principal                                                        |
| ----------------------------------------- | --------------------------------------------------------------------------------------- |
| Draft CRUD (`POST/PATCH/DELETE /flows/…`) | Drafts are user-principal-owned authoring objects                                       |
| Publish / unpublish                       | Publishing is part of authoring governance                                              |
| Template management and inspection        | Template configuration belongs to draft authoring                                       |
| Flow-assistant authoring                  | Step-assistant configuration belongs to draft authoring                                 |
| AI Builder                                | Session-based user-principal drafting workflow                                          |
| `GET /api/v1/flows/{id}/`                 | Returns the current draft/current-definition view, not a service-key runtime projection |

### Service-key runtime endpoint families

| Endpoint family                           | Current service-key rule                                            |
| ----------------------------------------- | ------------------------------------------------------------------- |
| `GET /api/v1/flows/?space_id=...`         | Allowed for published-flow discovery in the key's scoped space      |
| `GET /api/v1/flows/{id}/published/`       | Allowed for a runtime-safe single-flow published projection         |
| `GET /run-contract/`                      | Allowed for published-flow runtime discovery                        |
| `GET /graph/`                             | Allowed for published/runtime-safe topology and own-run snapshots   |
| Runtime uploads and orphan upload cleanup | Allowed for published flows                                         |
| Run creation                              | Allowed for published flows                                         |
| List / get / cancel / redispatch runs     | Own runs only                                                       |
| Step outputs                              | Own runs only                                                       |
| Artifact downloads                        | Own runs only                                                       |
| Evidence                                  | Own runs only, and only when explicit evidence capability allows it |

## Transfer a Flow package

Flow package export, planning, and import are user-principal authoring
operations. Export produces a bounded `.eneopkg` file with media type
`application/vnd.eneo.package+zip` and manifest `kind: flow`, without local
resource identifiers. The receiving operator uploads that same file to the
target space's import-plan endpoint and reviews the required and optional model
and knowledge mappings. Every required model or knowledge dependency needs a
current, explicitly confirmed local mapping before import. Only a dependency
declared optional may be omitted; in that case, the imported draft omits only
that optional reference. Flow endpoints reject Assistant or App package kinds
before interpreting Flow-specific package entries.

Strict v1 provenance always contains `omissions`. Ordinary packages use an
empty list. When source-local MCP server or tool associations exist on Flow
step assistants, export still succeeds but omits those associations and records
one closed advisory: `{ "kind": "mcp_attachment", "count": N }`, where `N` is
the positive distinct-assistant count. MCP identities, configuration,
credentials, and content never enter the package. Because provenance is covered
by the content checksum, changing or deleting the advisory makes validation
fail. Validation and import-plan responses project the same required list; do
not supply a client-side compatibility default for older files.

| Purpose                        | Endpoint                                                    |
| ------------------------------ | ----------------------------------------------------------- |
| Validate package bytes         | `POST /api/v1/flow-packages/validate/`                      |
| Plan destination mappings      | `POST /api/v1/spaces/{space_id}/flow-packages/import-plan/` |
| Import as an unpublished draft | `POST /api/v1/spaces/{space_id}/flow-packages/imports/`     |
| Export a draft                 | `POST /api/v1/flows/{flow_id}/package-exports/`             |

An affected export response includes
`Eneo-Package-Omitted-Mcp-Assistant-Count`; an ordinary export omits the header.
`@eneo/eneo-js` returns the binary result as `FlowPackageExportResponse` and
projects the header into its generated `FlowPackageOmission[]` as `omissions`.
It performs the same single Blob request: no package base64 conversion,
preflight request, or client cache is required. Require the user to acknowledge
the omission before saving, and show the import plan's advisory again before
installation.

Knowledge guidance describes how a destination operator can replace a local
dependency without carrying source knowledge. `summary` and `setup_notes` are
limited to 4,000 characters; `recommended_sources` and `do_not_include` are
limited to 20 entries each; every normalized entry is limited to 1,000
characters. Do not put local knowledge configuration or content in these
fields.

When installing, send the plan's `content_checksum`, `target_state`, and the
exact confirmed mappings as `expected_content_checksum`,
`expected_target_state`, and `selected_bindings`. Eneo rejects a changed
package, missing resource, ineligible model, or changed audio-transcription
default before it creates anything. It does not silently select a replacement.
Create a fresh plan, review it, and retry after correcting one of those errors.
Branch on the typed error code:

- `flow_package_checksum_mismatch` means the submitted file no longer matches
  the reviewed plan. Create a new plan from that exact file.
- `flow_package_import_unavailable_local_resource` means a selected resource or
  the reviewed target default disappeared or changed. Refresh the plan.
- `flow_package_import_selected_model_ineligible` means the chosen model no
  longer satisfies the package requirement. Refresh the plan and ask the user
  to confirm another eligible model.

An exact retry of a checksum, target-state, and mapping decision that already
succeeded returns the existing import and draft instead of creating a
duplicate. A new decision can still import another draft. Import never
publishes the Flow; the operator reviews and publishes the new draft through
the ordinary authoring journey. Flow packages do not carry Flow MCP or
HTTP-mutation input behavior, and unsupported template assets fail before
installation.

## Common application patterns

For endpoint-and-capability-first design walkthroughs, start with [Designing Flows](/guides/flows/designing-flows). This reference section keeps the deeper API field context.

### Transcription service

A typical transcription app uses a first step with `transcribe_only` on uploaded audio, then adds later steps for summarization, redaction, classification, or document generation. This is usually a good fit for a **service key**, because the integration should not depend on one employee account.

### Municipality intake or case-work service

A municipality service often combines:

1. structured form fields and uploaded documents
2. retrieval over approved knowledge sources
3. generated text or DOCX output
4. evidence and highlighted source passages for explainability

This is where the run contract, runtime uploads, graph, artifacts, and evidence surfaces become especially valuable.

## Integration sequence

For a numbered consumer journey with errors to handle at each step, use [Integrating Flows](/guides/flows/integrating-flows). The sequence below is the compact reference checklist.

For most consumer apps, the safest order is:

1. list published flows in the scoped space
2. fetch the published runtime projection for the chosen flow
3. fetch the published run contract
4. upload files if the flow requires them
5. create a run with an optional `Idempotency-Key`
6. poll the run and step endpoints
7. if the run reaches `awaiting_review`, load the active review checkpoint
8. edit, approve, reject, or resume the checkpoint
9. optionally rerun a completed step when a reviewer accepts a correction
10. fetch artifacts or evidence if your principal is allowed to

## Tenant flow settings for runtime operators

Eneo also exposes **tenant-level Flow runtime settings** for operators and platform owners.

These are admin surfaces, not end-user runtime endpoints:

| Setting area                | Endpoint                                                                           | Purpose                                                                                                                  |
| --------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Flow input limits           | `GET/PATCH /api/v1/settings/flow-input-limits`                                     | Control maximum file/audio sizes and file-count limits                                                                   |
| Flow document render limits | `GET/PATCH /api/v1/settings/flow-document-render-limits`                           | Control generated PDF/DOCX rendering limits                                                                              |
| Flow runtime policy         | `GET/PATCH /api/v1/settings/flow-runtime-policy`                                   | Control runtime step execution timeouts                                                                                  |
| Flow evidence policy        | `GET/PATCH /api/v1/settings/flow-evidence-policy`                                  | Control sensitive-flow export defaults and stricter raw evidence export behavior, especially for classification-3 spaces |
| Flow retention policy       | `GET/PATCH/POST .../preview /api/v1/settings/flow-retention-policy`                | Inspect and change organization run-history, never-attached-upload, and debug-evidence settings                          |
| Classification retention    | `GET/PUT/POST .../preview /api/v1/settings/flow-classification-retention-policies` | Inspect and replace classification-scoped delete-after and barrier state through the same exact-preview gate             |

AI Builder budget settings live at `GET/PATCH /api/v1/settings/ai-builder-budget`.
They are authoring/admin settings for AI Builder sessions, not Flow runtime controls.

### Flow retention policy shape

`GET /api/v1/settings/flow-retention-policy` exposes five inputs:

- `run_debug_evidence_days`
- `flow_run_history_retention_days`
- `flow_run_history_minimum_retention_days`
- `flow_run_history_no_purge`
- `flow_runtime_upload_abandonment_days`

The three day inputs are nullable integers in the range `1..2555`; there is no default or backfill. `flow_run_history_retention_days` activates the organization delete-after envelope for completed run and step history. `flow_runtime_upload_abandonment_days` is the separate delete-after input for runtime uploads that were never attached to a run input. The minimum and no-purge inputs are barriers for both preview projections: they never activate deletion. Debug-evidence redaction remains a separate cleanup policy.

Enabling either delete-after input, shortening an enabled value, or changing either barrier requires confirmation. First send the exact proposed values to `POST /api/v1/settings/flow-retention-policy/preview`. The bounded, read-only response includes the control-plane version, preview hash, preview timestamp, current, proposed, newly eligible, and no-longer-eligible counts, distinct file bytes, delete-after and minimum-not-before ranges, latent Space/Flow values, lifecycle blockers, and policy blockers. Send those three evidence fields back as `confirmation` with the same PATCH. The server locks and transactionally recomputes the exact preview; stale policy or data produces `409`. An ordinary disable or lengthening with unchanged barriers does not need confirmation.

`/api/v1/settings/flow-classification-retention-policies` configures classification-scoped delete-after activation and independent preservation barriers:

- `GET /api/v1/settings/flow-classification-retention-policies` lists policy rows.
- `POST /api/v1/settings/flow-classification-retention-policies/{security_classification_id}/preview` previews the exact desired state.
- `PUT /api/v1/settings/flow-classification-retention-policies/{security_classification_id}` creates or replaces that exact state and accepts the same confirmation shape.
- Sending `data_retention_days: null`, `minimum_retention_days: null`, and `no_purge: false` through preview and confirmed `PUT` removes the row. There is no independent `DELETE` endpoint.

Each policy stores:

- `security_classification_id`
- `data_retention_days`
- `minimum_retention_days`
- `no_purge`

`DataRetentionService` owns the policy calculation used by preview, deletion, and Flow reads. Let `A` be the shortest configured organization and exact matching-classification delete-after value. If neither value is configured, `A` is absent and automatic Flow-run deletion is **Off**, even when the Space or Flow contains a retention value. If `A` is present, the effective window is the shortest of `A`, the Space value, and the Flow value. Space and Flow values can only tighten an active envelope; they cannot activate, loosen, or disable it. Class 3 follows this same ordinary exact-match rule.

Let `M` be the longest configured organization and exact matching-classification minimum. A run is not eligible until both its effective delete-after time and `M` have elapsed. Either no-purge value blocks automatic purge. These barriers never activate deletion, so a barrier-only classification row is valid and an ordinary Space/Flow value remains latent while `A` is absent. Admin preview returns the latent values and policy blockers so a decision shows the full impact.

Every Flow response includes the required `run_history_retention` projection. Its `state` is either `off`, with `effective_days: null`, or `days`, with the positive effective window. The projection also reports `effective_minimum_days`, `no_purge`, `policy_conflict`, activation and barrier sources, and every organization, exact matching-classification, Space, and Flow contributor. There is no absent third state and no per-run `purge_eligible` claim.

Policies remain enforced even when tenant `security_enabled` display is disabled while spaces still retain `security_classification_id`. Deleting the security classification removes its policy and clears the space classification reference. The organization value then remains the only possible activation source; if it is also Off, child Space and Flow values become latent and automatic Flow-run deletion turns Off.

The explicit no-purge value is a retention barrier, not a general records-management or legal-hold framework. The preview separately reports three lifecycle blockers—undelivered audit delivery, unresolved webhook delivery, and active rerun work—and the minimum/no-purge/conflict policy blockers.

Current retention deletes the full run and step history. There is no API for raw per-step deletion intervals yet. When the organization or matching-classification envelope is active, a stricter Flow/Space `data_retention_days` value can shorten the full run-history window. A Flow/Space value cannot activate deletion by itself. Use tenant evidence policy for export controls.

The never-attached-upload input is only a control-plane value in this slice. Upload sweeping remains a separate implementation step and is not performed by these endpoints.

The settings and preview endpoints do not change worker cadence or implement upload sweeping. The canonical run-history purge selector consumes the same activation envelope as preview and public Flow reads.

This is the intended operator-facing seam for sensitive care-data workflows. Avoid hardcoding these policies in consumer apps when an admin/operator setting is the more appropriate control point.

### Flow evidence policy shape

`/api/v1/settings/flow-evidence-policy` controls evidence export behavior for Flow runtime.

Key flags currently include:

- `allow_sensitive_flow_exports`
- `allow_space_admin_raw_export_class3`
- `allow_run_owner_raw_export_class3`
- `allow_service_key_raw_export_class3`

For sensitive care-data flows, the intended default is that evidence export stays disabled unless an operator intentionally enables it by policy.

### Sensitive-flow governance in `metadata_json`

For sensitive workflows, the flow definition may carry a `metadata_json.care_data_policy` object.

Current supported fields are:

- `sensitive`
- `approval_mode`
- `pre_approval_visibility`

Common values for that review model are:

- `approval_mode: "single_reviewer_outside_flow"`
- `pre_approval_visibility: "uploader_and_reviewers"`

This is the intended contract seam for workflows where review happens outside the flow but the workflow still needs explicit governance metadata.

Sensitive flows still deny evidence export by default until tenant flow settings explicitly enable `evidence_policy.allow_sensitive_flow_exports`, even for elevated human roles.

### 2) Upload files

```http
POST /api/v1/flows/{flow_id}/steps/{step_id}/runtime-files/
Content-Type: multipart/form-data
```

Use the step-specific runtime upload path from `runtime_paths.upload_step_runtime_file_template`.
Replace `{step_id}` with a step id from `steps_requiring_input` in the run contract.
Upload files before `create_run`; `runtime` means runtime input, not an already-started run mutation.

Example:

```bash
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "upload_file=@citizen-letter.pdf" \
  https://your-domain.example/api/v1/flows/$FLOW_ID/steps/$STEP_ID/runtime-files/
```

The returned file id belongs under `step_inputs[step_id].file_ids` when starting the run.
You may reuse the same file id under multiple compatible step ids when several steps should
process the same uploaded binary.

Upload response shape:

```json
{
  "id": "00000000-0000-0000-0000-000000000701",
  "name": "review-audio.mp3",
  "mimetype": "audio/mpeg",
  "size": 1843200,
  "created_at": "2026-03-17T10:04:00Z",
  "updated_at": "2026-03-17T10:04:00Z"
}
```

To abandon an upload before creating a run, call the cleanup path from
`runtime_paths.delete_runtime_file_template`:

```http
DELETE /api/v1/flows/{flow_id}/runtime-files/{file_id}/
```

Cleanup is only for orphan runtime uploads. After a file id is attached through
`step_inputs`, the run owns that mapping and deletion returns
`flow_runtime_file_attached` with HTTP 409.

### 3) Create the run

```http
POST /api/v1/flows/{flow_id}/runs/
Idempotency-Key: your-stable-client-key
```

Minimal request shape:

```json
{
  "expected_flow_version": 3,
  "input_payload_json": {
    "employee_name": "Alex Example"
  },
  "step_inputs": {
    "00000000-0000-0000-0000-000000000101": {
      "file_ids": ["00000000-0000-0000-0000-000000000701"]
    }
  }
}
```

Within each step input, `file_ids` are parsed as UUIDs and duplicate ids are
collapsed by first occurrence when the run is created. The remaining order is
preserved in the run input and contributes to SDK-derived idempotency keys. If a
prompt or document needs semantic ordering, model that ordering explicitly in the
flow rather than relying on file attachment order alone.

If the flow is still a draft, the API will return `flow_not_published`.

#### How `input_payload_json` maps to form fields

If the run contract exposes `form_fields`, send those values inside `input_payload_json` using the published field names as keys. The backend validates the values against the published field type and required/optional settings.

Reserved `input_payload_json` keys: `expected_flow_version`, `file_ids`, `step_inputs`, `transkribering`. These keys are owned by Flow run orchestration, so use different form field names and keep runtime file bindings in top-level `step_inputs`.

#### Why `Idempotency-Key` matters

Run creation supports caller-supplied idempotency. Reusing the same key with the same payload returns the existing run. Reusing the same key with a different payload returns:

- `400`
- code: `flow_run_idempotency_conflict`

This is especially useful for browser retries, webhook retries, and unreliable networks.

#### Receiving terminal Flow webhooks

Terminal HTTP POST output uses an **at-least-once sender contract**. A timeout,
connection loss, worker crash, or claim expiry can occur after the receiver
accepted a request but before Eneo committed its receipt, so duplicate POSTs
are possible.

Eneo sends an opaque `Idempotency-Key` that is stable across retries of one Flow
run, output step, and step attempt. That scope is sender-side only: Eneo does
not verify how long your receiver retains keys or how it handles replays. Your
receiver must store the key for its required replay window and return the same
logical result without repeating the mutation when the key is seen again.

Each durable claim consumes one of five attempts before HTTP starts. HTTP `408`
and `429`, `5xx`, and transport failures remain bounded-retryable; other `4xx`
responses are terminal. If the fifth claim expires with an unknown remote
outcome, Eneo dead-letters the delivery and fails the run without a sixth POST.

When tenant capacity is full, create returns HTTP `429`, `Retry-After: 60`, and
code `flow_run_concurrency_limit_reached`. Branch on the HTTP status plus that
string code, wait at least the advertised delay while polling existing runs,
then submit the logical run again. Numeric `eneo_error_code: 9007` is a legacy
category and is not the client control-flow contract.

If you use `@eneo/eneo-js` (`frontend/packages/eneo-js`), the Flow client accepts `idempotencyKey` on `flows.runs.create(...)` and exposes `flows.runs.deriveUploadIntentIdempotencyKey(...)` to build a stable key from the published flow id/version plus the uploaded runtime file bindings you submit in `step_inputs`. It also exports `FLOW_RUN_RESERVED_INPUT_PAYLOAD_KEYS` and `FlowRunReservedInputPayloadKey` for custom form validation. Use the same per-step file order for the key and the run creation request.

Example:

```js
const stepInputs = {
  [stepId]: { file_ids: [runtimeUpload.id] },
};

const idempotencyKey = await client.flows.runs.deriveUploadIntentIdempotencyKey(
  {
    flowId,
    expectedFlowVersion: runContract.published_flow_version,
    step_inputs: stepInputs,
  },
);

await client.flows.runs.create({
  flow: { id: flowId },
  expected_flow_version: runContract.published_flow_version,
  step_inputs: stepInputs,
  idempotencyKey,
});
```

### Audio-to-document runtime pattern

For the full speech-to-structured-report shape, see [Designing Flows](/guides/flows/designing-flows#speech-to-structured-report). The notes here keep the runtime reference constraints.

For an audio workflow that generates structured output or a DOCX artifact, the recommended runtime shape is:

1. record audio in the browser **or** select an audio file
2. upload the completed audio file through the published Flow runtime upload contract
3. derive a stable `Idempotency-Key` from the uploaded file ids and current run payload
4. create one published Flow run
5. let the first step transcribe and the later steps produce the final structured output / DOCX artifact

Important non-goals for this pattern:

- no live transcription streaming while the browser is still recording
- no frontend chunk orchestration for oversized files
- no separate browser-only retry protocol outside the shared `Idempotency-Key` contract

Approval and visibility boundary for sensitive audio-to-document flows:

- final approval is a **single authorized reviewer outside the flow**
- before final approval, generated output and run evidence should be treated as visible only to the uploader and explicitly authorized reviewers
- evidence export stays disabled by default unless policy explicitly enables it

This keeps the published Flow runtime aligned with the same enterprise seams used elsewhere: typed policy metadata, admin-configurable retention/export controls, and idempotent completed-upload execution.

#### What the two `retryable` fields mean

`dispatch_last_error.retryable` is an internal recovery signal for the current
dispatch epoch before terminalization. It tells you that the server may retry
the same queued work; it does not tell a client to create another run.

After terminalization, `error.retryable` answers a different question: whether
a consumer may safely submit a new logical run. It is conservative and true
only for `flow_dispatch_failed` and `flow_step_attempt_start_failed`. A true
value does not start work automatically; the consumer still decides whether
and when to submit a new run.

#### What redispatch does

`redispatch` is for **stale queued runs**. It asks the system to try dispatching a queued run again if it appears stuck before execution started. It is not the same as creating a brand-new run.

If no stale queued work is found, the endpoint can still return `200` with `redispatched_count: 0`. Treat that as a no-op rather than as a new execution.

and can return `typed_io_contract_violation`.

the current checkpoint and run without dispatching duplicate work.

#### Rerun a completed step

Initial execution creates one run for the whole published flow. A rerun is
different: it re-executes one completed step in an existing completed or failed
run, invalidating that step and its downstream results.

Use `runtime_paths.rerun_step_template`:

```http
POST /api/v1/flows/{flow_id}/runs/{run_id}/steps/{step_id}/rerun/
```

Minimal request:

```json
{
  "expected_run_revision": 7,
  "reason": "The reviewer corrected the transcription for step 1."
}
```

The eneo-js helper accepts the generated rerun request fields directly:

```js
const rerun = await client.flows.runs.rerunStep({
  flowId,
  runId,
  stepId,
  expected_run_revision: latestRun.revision,
  reason: "The reviewer corrected the transcription for step 1.",
});
```

`expected_run_revision` comes from the latest run response. `reason` is required
and stored with the rerun operation. You may also send `input_payload_json` and
`step_inputs`, but file overrides must be keyed by the rerun root step id. Upload
replacement files through the normal runtime upload path before requesting the
rerun.

Rerun returns `202 Accepted` with the rerun operation and current run. Redispatch
is only for stale queued runs that have not started; rerun is for deliberate
post-result correction.

An exact replay of the same accepted rerun request is an idempotent replay and
also returns `202`; use the returned operation status rather than starting
another correction. For `flow_run_rerun_stale_revision`, reload the run and
decide whether the correction still applies before submitting its current
revision. For `flow_run_rerun_invalid_transition`, wait for a terminal eligible
status or stop offering rerun. Step/input validation errors require correcting
the target step or replacement inputs before retrying.

### 5) Read results

#### Final run result

Use the run endpoint as the canonical final-result read model:

```http
GET /api/v1/flows/{flow_id}/runs/{run_id}/
```

`result` is `null` while a run is incomplete or when it did not complete
successfully. A completed run returns exactly one closed result shape:

- `inline_text` contains the final `text`.
- `file_backed_text` contains a bounded, non-authoritative `preview` and one
  current-attempt generated-output `file`. Use the authorized artifact endpoint
  to download the complete text only when `file.availability` is `available`.
  When it is `content_purged`, treat the complete text as unavailable and handle
  the artifact endpoint's `410`; never treat `preview` as the full result.
- `structured` contains the authored `value` and the `output_contract` from
  that run's published `flow_version`. Treat `value` as opaque application data;
  do not infer another Eneo envelope inside it.
- `artifact` contains current-attempt file metadata. Request a signed URL with
  the authorized artifact endpoint before downloading a file.
- `outbound_http` contains only `delivery_status: "delivered"`. It is a delivery
  receipt and never exposes destination URLs, headers, credentials, or the sent
  payload.

Every historical list item is projected from its own `flow_version`, so do not
interpret old structured results with the currently published contract. The
generated `FlowRunResult` type supports an exhaustive switch:

```ts
import type { FlowRunResult } from "@eneo/eneo-js";

function renderResult(result: FlowRunResult): string {
  switch (result.kind) {
    case "inline_text":
      return result.text;
    case "file_backed_text":
      return result.file.availability === "available"
        ? `Download complete text from file ${result.file.file_id}`
        : "Complete text is no longer available";
    case "structured":
      return JSON.stringify(result.value);
    case "artifact":
      return `${result.files.length} file(s)`;
    case "outbound_http":
      return result.delivery_status;
    default: {
      const unreachable: never = result;
      return unreachable;
    }
  }
}
```

### 6) Evidence and explainability

#### Evidence view

```http
GET /api/v1/flows/{flow_id}/runs/{run_id}/evidence/
```

Use this when you want the rich evidence payload for one run, including:

- the run summary
- the published definition snapshot
- `definition_integrity`, containing `status`, `expected_checksum`, and `current_checksum`
- step results
- step attempts
- the debug export payload

When `definition_integrity.status = "verified"`, the evidence run uses the same
redacted, typed `FlowRunPublic.result` projection as the canonical run endpoint.
A completed run therefore exposes the same closed result kind here.

Functional endpoints reject a published snapshot whose current checksum differs
from its recorded checksum. Evidence also marks a checksum-matching snapshot invalid
when canonical published-definition parsing fails. Evidence access is intentionally
different: an authorized caller still receives the original stored snapshot for
forensic inspection, with `definition_integrity.status = "invalid"`. Do not treat
that snapshot as executable or retry an operation pinned to its version. Even when
the stored run status is `completed`, `run.result` is `null` because no trustworthy
final-output contract can be projected. Ask a Flow editor to publish a valid version
and start a new run; keep the old run for evidence.
In redacted evidence, `current_checksum` still describes the original stored snapshot,
not the redacted projection.

#### Evidence export

```http
GET /api/v1/flows/{flow_id}/runs/{run_id}/evidence/export?format=json&detail=redacted
GET /api/v1/flows/{flow_id}/runs/{run_id}/evidence/export?format=json&detail=raw
```

You can also pass a `reason` query parameter if you want the audit trail to capture why the export was performed.

The default export is `detail=redacted` with reason `support_debug`. A raw export
requires an explicit non-default reason between 3 and 500 characters. The
eneo-js wrapper exposes both generated options:

The JSON response uses manifest schema `flow-evidence-export.v9`. Its required
`actor` identifies the caller that performed the export, not the run owner.
Branch on `actor.type`: a user actor contains only `user_id`, while a
`service_key` actor contains only `key_id`. Both actor variants reject additional
fields. The content hash continues to cover only the exported `bundle`, so audit
metadata such as the actor does not change the hash.

```js
const evidence = await client.flows.runs.exportEvidence({
  id: runId,
  flowId,
  detail: "raw",
  reason: "Investigate incident 42",
});
```

For the full evidence and classification policy model, see <a href="/docs/flows">Flows</a>. The short version is:

- `evidence/` is the inline inspection surface
- redacted export is the normal support/compliance export
- raw export is the strictest export surface and may be tightened further in classification-3 spaces

#### Service keys and evidence

A service key can access evidence only for **its own runs**. It needs
`resource_permissions.flows >= read` before `resource_permissions.flow_evidence`
is evaluated. The evidence capability levels are:

- `flow_evidence >= read` → evidence view
- `flow_evidence >= write` → redacted export
- `flow_evidence = admin` → raw export, still subject to classification-3 tenant policy

#### RAG trace and highlighted segments

If a step used knowledge, the evidence/debug payload includes RAG provenance such as retrieved sources, chunk snippets, scores, and prompt-context inclusion metadata.

In the web UI, that same trace can open the source document and highlight the matched segments that influenced the answer.

### Principal visibility rules

The published runtime API is intentionally not “open to anyone who can see the flow”.

- user-principal run owners can inspect their own runs
- trusted in-space operators (space owner and space admin) can inspect in-scope runs, artifacts, and evidence
- tenant admins can inspect across the tenant
- service keys can inspect only their **own** runs and evidence
- user-principal run owners need `FLOWS_TRACE` for their own evidence access
- a service key never becomes a user-principal operator just because the key is scoped to a space with admin-level permission

}

### Appendix: user-principal authoring and AI Builder surfaces

If your application also needs to create or maintain flows, there are two user-principal authoring surfaces.

#### Direct flow authoring

| Purpose                       | Endpoint                                       |
| ----------------------------- | ---------------------------------------------- |
| Create draft                  | `POST /api/v1/flows/`                          |
| List drafts / published flows | `GET /api/v1/flows/?space_id=...`              |
| Get draft                     | `GET /api/v1/flows/{flow_id}/`                 |
| Update draft                  | `PATCH /api/v1/flows/{flow_id}/`               |
| Publish                       | `POST /api/v1/flows/{flow_id}/publish/`        |
| Unpublish                     | `POST /api/v1/flows/{flow_id}/unpublish/`      |
| Delete draft                  | `DELETE /api/v1/flows/{flow_id}/`              |
| Upload DOCX template asset    | `POST /api/v1/flows/{flow_id}/template-files/` |

#### AI Builder

AI Builder lives under `/api/v1/flows/ai-builder/` and is a user-principal authoring surface. Service keys can run published flows, but they cannot draft or revise flows through AI Builder. For the product mental model and authoring details, see <a href="/docs/ai-builder">AI Builder</a>.

Plan responses expose a single `proposal` object. Use `proposal.spec` as the proposed draft Flow. For edit sessions, use `proposal.edit` for the approved base revision, explicit removed step refs, preview diff, warnings, advisories, risk flags, and confidence. `description_override_manual` records a reviewer decision to keep the current Flow description. Do not integrate against legacy `edit_result` or compiled-edit fields; those are not part of the public API contract.

For template-fill document output, treat the DOCX template asset path as an **accessibility-reviewed template path**. This is especially important for sensitive document workflows:

- upload reusable DOCX templates through the template asset route
- verify placeholders and mappings before publish
- prefer templates that have already been reviewed for heading structure, reading order, and table semantics

## Troubleshooting

For short capability answers and operational choices, see [Flows FAQ](/guides/flows/flows-faq). For Flow-specific codes, use [Flow error reference](/guides/flows/reference/errors) and branch on `code`, not message text.

| Status    | What it usually means                                                           | What to do                                                                                                                   |
| --------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `400`     | The request shape, state precondition, or Flow contract is invalid.             | Read the Flow error `code` and follow its recovery; reuse a key only for the idempotent create/resume request it belongs to. |
| `401/403` | Authentication, space scope, ownership, or evidence policy blocked the request. | Fix the principal or policy before retrying; platform auth may return `insufficient_scope`.                                  |
| `409`     | The run, checkpoint, file, or idempotency key changed before this request.      | Reload the run or checkpoint and retry with the current revision.                                                            |
| `429`     | The tenant or flow has too many active runs.                                    | Back off and poll existing runs before creating more work.                                                                   |

## Practical takeaway

If you treat Flows as a **published contract plus a versioned runtime**, the API becomes straightforward:

- discover the contract
- upload what the contract requires
- create the run with idempotency
- poll run and step results
- fetch artifacts or evidence only within the visibility rules of the current principal

That is the cleanest way to build robust web applications on top of Eneo Flows.
