# Security for Contributors

This page explains the security checks contributors see when they open a pull request. For the overall picture, see [Security at Eneo](/docs/security). The canonical security policy is [`docs/SECURITY.md`](https://github.com/eneo-ai/eneo/blob/develop/docs/SECURITY.md).

Do not report sensitive vulnerabilities in public issues, pull requests, or discussions. Report them privately through [**Security → Report a vulnerability**](https://github.com/eneo-ai/eneo/security/advisories/new) or by email to `security@sundsvall.se`.

## Pull Request Checks

Pull requests into `develop` run the following security and quality gates:

### CI

`CI / CI` is the main app check. Pull requests and merge-queue candidates run
the checks selected by `.github/scripts/ci-change-scope.mjs`. Each merge
candidate is classified by its own diff onto the preceding candidate; the whole
candidate tree is still built and tested. Missing history, an empty diff,
unknown runtime paths, and changes to CI workflows or local actions select full
validation.

Backend changes require backend quality checks, all six test shards, schema
checks, and both frontend E2E suites. Each frontend's changes require that
app's checks, E2E tests, and Docker build. Shared frontend packages and lockfiles
select both apps. Security scanning and repository checks remain required even
for documentation-only changes. The final gate rejects failed, cancelled,
missing, or unexpectedly skipped jobs; only jobs excluded by the scope plan
may be skipped.

Backend dependency installs use `uv sync --frozen --all-groups`. Frontend dependency installs use `bun install --frozen-lockfile`. This matters because dependency PRs should prove that the committed lockfiles still install and the app still builds.

The Docker matrix contains only the affected backend, Svelte frontend, Next
frontend, or devcontainer images, built without pushing them. This catches
Dockerfile and base-image update problems before they merge.
The Svelte production build runs in E2E and Docker; there is no additional
standalone build of the same app. The web-next E2E and accessibility checks are
part of the required aggregate when selected.

Pushes to `develop` run the full suite once, through **Build and Push Docker
Images**, before the completed release bundle can be published. Release-branch
pushes still run full CI directly; tag and manual publication callers also run
the full suite. Publication and its release checks are not scoped away.

See the [CI operations guide](https://github.com/eneo-ai/eneo/blob/develop/docs/CODE_QUALITY.md#ci-execution-and-recovery)
for time limits, build diagnostics, validation commands, and recovery.

Ruff currently checks `backend/src/eneo`. Tests and Alembic are not part of the Ruff gate yet.

### Dependency Review

`Dependency Review / Dependency Review` checks dependency and lockfile changes in pull requests into `develop`. It fails if a PR introduces a known vulnerable dependency at `high` severity or above.

When this check fails, update the dependency to a safe version, remove it, or document why the vulnerable code is not reachable. Do not dismiss the warning just to make the PR green.

### Source, dependency and secret scanning

The reusable `Security` workflow is part of the CI aggregate. It runs a complete
lockfile audit, Semgrep's security-audit and GitHub Actions rules, and Gitleaks on
added Git history.
Temporary dependency mitigations require a documented owner, targeted tests and
an expiry; see `frontend/patches/SECURITY.md`.

The release review also scans full Git history, verifies credential revocation,
and exercises both frontends in staging with the actual authentication and
integration providers. Automated scanning does not replace those checks.

### Code scanning

CodeQL advanced setup is paused while maintainers evaluate a code-scanning setup that gives developers useful feedback without high false-positive noise. Re-enable code scanning only with a tuned query set and a triage process that keeps alerts actionable.

## Declare access on every endpoint

Every HTTP and WebSocket endpoint must explicitly declare **authentication**
(which identity it accepts) and **authorization** (who may invoke the operation).
There is no implicit "logged in is enough" default and no exemption based on a
URL prefix. This implements the deny-by-default and per-request checking
principles in the [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).
It does not establish compliance with the whole OWASP ASVS standard.

Declare the policy immediately below the route decorator, and retain the real
authentication dependency:

```python
@router.post(
    "/{provider_id}/test/",
    response_model=ProviderTestResult,
    description="Test connectivity using the provider's stored credentials.",
    responses=responses.get_responses([403, 404]),
)
@endpoint_access(
    authentication=Authentication.USER,
    authorization=Permission.ADMIN,
    reason="Uses organization-managed provider credentials.",
)
async def test_provider(provider_id: UUID, user: CurrentUser):
    ...
```

The canonical declaration and enforcement live in
`backend/src/eneo/authentication/endpoint_access.py`. Existing `Permission`
values and domain services remain the owners of role permissions, tenant
boundaries, space membership and object ownership. Endpoint admission never
replaces those resource checks. Use a named permission whenever the operation
requires one. `Authorization.AUTHENTICATED` is an explicit grant to authenticated
callers, suitable for a shared catalogue or an operation whose service restricts
access to the caller's own resources; its reason must identify that purpose.
When several routes rely on the same access rule, reuse a router-local named
constant for their `reason`. Keep the full `@endpoint_access` declaration on
each route, and use separate reasons when the underlying checks differ.

The declaration is the single source for the endpoint's permission and session
requirements. Do not repeat these with `validate_permission` in handlers or
separate permission/session dependencies. Domain service permission checks remain
necessary for internal callers. Storage administration also retains its stricter
active-user and active-tenant checks; these protect identity lifecycle, independently
of the declared `Permission.STORAGE`.

Choose `Authentication.SESSION` when API keys must be rejected. The existing
API-key scope, permission and real-user guards still apply. SCIM tokens,
deployment administrator keys, module credentials and signed file URLs have
separate policies and authentication dependencies. Public operations such as
login entry points and health probes must declare both `Authentication.PUBLIC`
and `Authorization.PUBLIC`, with a reason.

Application construction checks every registered route, including nested
routers and mounted APIs. A missing declaration or missing authentication
dependency prevents startup. The request guard also rejects missing or
misconfigured access contracts, and user authentication enforces the declared
permission before the handler executes. Generated documentation and internal
MCP transport routes have explicit declarations at their registration sites;
MCP tools still authorize each tool invocation.

`scripts/check_route_metadata.py --all` checks declarations and rejects duplicate
endpoint permission/session gates without importing the application. CI also runs
`tests/unit/test_endpoint_access.py` and `tests/unit/test_endpoint_access_matrix.py`.
The matrix exercises the shipped user-authentication dependency graphs, rejecting
anonymous callers, users missing the declared permission and API keys on session-only
endpoints before handler dispatch. When adding an endpoint, add behavior tests showing
that anonymous callers and callers without the required permission cannot
reach its side effects, while an authorized caller succeeds. For resource
operations, test another user's or tenant's resource as well. A declaration
cannot prove that the chosen permission or domain rule is correct.

The request adapter reads FastAPI's effective dependency context so inherited
authentication is included. Its scope layout is framework-specific; retain
the nested-router and mounted-API tests when upgrading FastAPI.

## Required Checks in Branch Protection

The `develop` ruleset requires the checks `CI` and `Dependency Review` (shown on a pull request as `CI / CI` and `Dependency Review / Dependency Review`). A separate `PR label classification` ruleset requires `PR labels` on `develop`, `main` and `release/**`.

Who can approve, merge and release, and how branches and tags are protected, is described in [Governance and Roles](/contributing/governance).

## Dependency Updates

Dependabot alerts report vulnerable dependencies, and the `Security` workflow audits the lockfiles on every pull request and every week. Maintainers patch what they find in focused `fix(deps)` pull requests and carry the fixes to the supported release lines. Automatic Dependabot version-update pull requests are paused: every ecosystem in `.github/dependabot.yml` has `open-pull-requests-limit: 0` and is re-enabled one at a time.

For packages that handle prompts, files, provider keys, network calls, authentication, authorization, Docker images, or GitHub Actions, read the changelog before merging.

## Handling Alerts

Triage security alerts in the order and within the response targets set by the [security policy](https://github.com/eneo-ai/eneo/blob/develop/docs/SECURITY.md#alert-triage): malware, exposed secrets and critical runtime vulnerabilities come first. If a fix cannot be merged quickly, record it as the policy describes, with an owner, risk, mitigation, target date and review date.

## Secrets

Use GitHub Actions secrets for CI and deployment credentials. Use Dependabot secrets only for private package registries. Do not put runtime application secrets in Dependabot secrets.

If a secret enters the repository, rotate it first. Then remove it from history if needed, inspect logs and artifacts, and add a secret scanning pattern if the format is specific to Eneo.
