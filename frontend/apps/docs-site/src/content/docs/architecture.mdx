# Architecture

Eneo is a modular monolith: one FastAPI backend, one SvelteKit frontend, one
background worker that runs the same backend image, PostgreSQL with pgvector,
and Redis. The bundled tool runtime runs Eneo-maintained compute and file tools
in a separate container. Docker Compose supplies the reference deployment;
Traefik fronts the application, while the runtime stays on the private network.

## Skills, Functions, tools and views

Everything a model can call in Eneo is an MCP tool, served from one of three
places: a loopback server inside the backend, the bundled tool runtime in its
own container, or an independently operated MCP server. Skills supply
instructions, Functions supply saved intent that resolves to a provider at ask
time, MCP Apps and Eneo's native previews supply presentation. These parts are
deliberately separate, and the reasons are laid out in one place:

- [Tools and MCP Architecture](/docs/tool-architecture): the three execution
  tiers, what they share, why the split exists, the responsibility map and
  the state and failure boundaries.
- [Tool Runtime Security](/docs/tool-runtime-security): what the isolated
  runtime defends against and how.
- [Built-in Tool Servers](/docs/builtin-tool-servers): the loopback servers
  and the rule for what belongs inside the backend.

For user workflows and limitations, see [Functions](/guides/capabilities#tools-files-and-views).
For Skill authoring, see [Skills](/guides/skills). For view approval, isolation
and deployment, see [MCP Servers](/guides/mcp-servers#interactive-tool-views).

### Backend (FastAPI)

**Technology stack:**

- FastAPI on Python 3.11
- SQLAlchemy 2 with the async `asyncpg` driver; Alembic for migrations
- Pydantic 2 for request/response models and `pydantic-settings` for configuration
- `dependency-injector` container wiring services and repositories per request
- LiteLLM as the transport for completion, embedding, and transcription providers
- Asynchronous HTTP crawling, with `pdfplumber`, `docx2python`, `python-pptx`, and
  pandas for text extraction

**Process model:** the backend container runs Alembic migrations and then
Gunicorn with Uvicorn workers on port 8000 (three workers unless `NUM_WORKERS`
is set). With `RUN_AS_WORKER=true` the same image starts the ARQ worker
instead.

**Layout:** the code is organised by domain under `backend/src/eneo/`. Newer
domains follow a layered layout (`application/`, `domain/`,
`infrastructure/`, `presentation/`); older domains use flat
`<name>.py`, `<name>_repo.py`, `<name>_service.py`, and `<name>_router.py`
modules, sometimes with an `api/` folder.

```

├── run.sh                       # Gunicorn or ARQ entrypoint

    ├── server/                  # FastAPI app, routers, middleware, websockets
    ├── main/                    # Settings, DI container, logging, observability

    ├── worker/                  # ARQ adapter, upload and crawl tasks, feeder
    ├── tenants/  users/  roles/  authentication/  scim/  sysadmin/  admin/
    ├── spaces/  assistants/  group_chat/  sessions/  questions/  conversations/
    ├── collections/  groups_legacy/  info_blobs/  files/  websites/  crawler/
    ├── object_content/          # Durable content control plane and S3 adapter
    ├── embedding_models/  completion_models/  transcription_models/
    ├── model_providers/  ai_models/  tenant_models/  token_usage/
    ├── mcp_servers/  internal_mcp/  mcp_apps/  skills/  apps/  services/  workflows/
    ├── integration/             # SharePoint and Confluence knowledge sources
    ├── audit/  data_retention/  jobs/  limits/  modules/  observability/
```

**HTTP surface:**

- All application routes are mounted under `API_PREFIX` (`/api/v1` in the
  reference deployment). Swagger UI is served at `/docs` and the schema at
  `/openapi.json`, both at the root.
- SCIM provisioning is a separate ASGI app mounted at `/scim/v2`.
- Loopback MCP servers for knowledge search, attachment reading and image

- Middleware adds a request context, an `X-Trace-Id` response header, CORS
  whose origins are matched against the `allowed_origins` table, and

### Space persistence ownership

A loaded Space is a read projection. It can omit invalid applications, deleted
members, deprecated models and disabled MCP servers, and can include knowledge
inherited from its organization. It is never a complete database snapshot and
must not be written back as one.

| Write owner | Responsibility |
| --- | --- |
| `SpaceRepository` | Space settings, individual user/group memberships, explicit model/server/capability selections |
| `AssistantRepository` | One assistant, its prompt and explicit knowledge, attachment and tool selections |
| `GroupChatRepository` | One group chat and explicit replacements of its assistant seats |
| `GroupRepository` | Collection configuration and distribution to Spaces |
| `WebsiteRepository` | Website configuration and distribution; crawl lifecycle remains with `CrawlRunRepository` |
| App, service and integration repositories | Their existing resource lifecycles |

Services authorize the operation and validate its requested values before
passing explicit write intent to the owning repository. Omitted relationships
are untouched. An explicitly submitted list replaces that relationship;
`[]` clears it, including currently hidden targets. The shared association writer
compares that explicit selection with stored rows and writes only differences.
Unchanged rows keep their timestamps. Renaming a Space cannot delete an assistant
or materialize inherited knowledge as a direct distribution.

Replacement writes lock their parent in the request transaction. Assistant moves
lock both Spaces in ID order, then the assistant; group chat seat replacements
take the same Space lock before validating membership. Moves update ownership
without deleting the assistant or its history. Assistants and services move
alone: their collections and websites stay in the Space that owns them.
Collections and websites cannot be moved or shared between Spaces; the only
distribution is from an organization Space, whose knowledge its child Spaces
see. Concurrent changes to distinct
resources do not overwrite each other. Two explicit replacements of the same
relationship remain serialized, last-writer-wins operations; there is no
client-visible optimistic version contract.

The security classification preview reports affected IDs without editing the
Space projection. A committed classification change explicitly removes
incompatible stored model/server selections, including hidden ones. The default
assistant is a supported group chat member through the API and is included when
resolving seats.

Malformed stored model options remain visible to operators through the
[inspection and repair API](/docs/api#inspect-and-repair-invalid-model-options).
No schema migration or automatic data normalization is required. Roll back by
redeploying the previous application only if its aggregate-save defect is
acceptable; previously deleted resources require restoration from a backup.

### Database (PostgreSQL + pgvector)

**Technology:**

- PostgreSQL 16 (`pgvector/pgvector:pg16` in the reference deployment)
- pgvector for cosine-distance search over chunk embeddings
- Alembic migrations in `backend/alembic/`, applied by `init_db.py` on first
  start and by `run.sh` on every backend start

**Schema conventions:** every table is declared in
`backend/src/eneo/database/tables/`. Table names are derived from the class
name in snake case. Entity tables use UUID primary keys and carry `created_at`
and `updated_at`. Junction tables use composite primary keys;
`BaseCrossReference` supplies both timestamps. The distribution links
`groups_spaces` and `websites_spaces` use `CreatedAtMixin` and only carry
`created_at`: links are inserted or deleted and have no mutable settings.

**Core tables:**

| Table                                   | Purpose                                                                                  |
| --------------------------------------- | ---------------------------------------------------------------------------------------- |
| `tenants`                               | Organisations; hold federation, crawler, and API-key policy as JSONB                     |
| `users`                                 | Accounts within a tenant, with roles and user groups                                     |
| `spaces`                                | Workspaces; a personal space has a unique `user_id`, shared spaces have members and roles |
| `assistants`                            | Assistant configuration, completion model, and knowledge bindings                        |
| `sessions`                              | Conversations with an assistant, service, or group chat                                  |
| `questions`                             | One question/answer pair per row, including token counts and tool calls                  |
| `info_blob_references`                  | Which `info_blobs` a question cited and with which similarity score                     |
| `groups`                                | Collections of uploaded documents (the code calls them collections)                     |
| `websites`, `crawl_runs`                | Crawled sources and each crawl execution                                                 |
| `info_blobs`                            | Extracted text per document or page, with `source_id` and `version_state`                |
| `info_blob_chunks`                      | Chunked text with its embedding vector                                                   |
| `files`                                 | Uploaded files and attachments                                                           |
| `object_contents` and related tables    | Durable byte control plane (see below)                                                   |
| `jobs`                                  | Background job status for the frontend                                                   |
| `api_keys_v2`                           | API keys stored as hashes with prefix and suffix for display                             |
| `audit_logs` and audit config tables    | Audit trail and retention policy                                                         |

**Key relationships:**

```
tenants (1) ─── (N) users
tenants (1) ─── (N) spaces
spaces  (1) ─── (N) assistants
spaces  (1) ─── (N) groups (collections) / websites / integration knowledge
groups | websites | integration knowledge (1) ─── (N) info_blobs
info_blobs (1) ─── (N) info_blob_chunks
assistants (1) ─── (N) sessions
sessions (1) ─── (N) questions ─── (N) info_blob_references
```

**Vector search:** `info_blob_chunks.embedding` is a dimensionless pgvector
`Vector()` column, so one table holds embeddings from every configured
embedding model. Retrieval orders by cosine distance, restricts the scope to
the requested collections, websites, or integrations, and reads only the
active document version:

```python
# backend/src/eneo/info_blobs/info_blob_chunk_repo.py
await self.session.execute(sa.text("SET LOCAL enable_seqscan = off;"))

stmt = (
    sa.select(
        InfoBlobChunks,
        InfoBlobChunks.embedding.cosine_distance(embedding),
        InfoBlobs.title,
    )
    .join(InfoBlobs)
    .where(active_info_blob_version())
    .options(defer(InfoBlobChunks.embedding))
    .order_by(InfoBlobChunks.embedding.cosine_distance(embedding))
    .limit(limit)
)
```

<Callout type="info">
  There is no approximate-nearest-neighbour index (no IVFFlat or HNSW) on the
  embedding column. The B-tree indexes on `info_blob_id`, `tenant_id`, and the
  scope foreign keys narrow the candidate set, and `SET LOCAL enable_seqscan =
  off` steers the planner away from a full scan of the TOAST-heavy chunk table.
  Retrieval cost therefore grows with the number of chunks in scope, not with
  the whole table.
</Callout>

#### Database schema check

`backend/tests/integration/test_database_schema.py` checks that every table and
column declared in SQLAlchemy's `Base.metadata` exists in the migrated database.
It uses the same table registration as Alembic, including tables without an ORM
class. New table modules must be registered through
`backend/src/eneo/database/tables/__init__.py`, as required by Alembic. There is
no separate test list to maintain and no dependency on a model's base class.

The shared integration fixtures start disposable PostgreSQL and Redis containers
and build the database with `alembic upgrade head`. They do not create the schema
from the models with `metadata.create_all()`, which would hide missing migrations.
Each table is a separate test case, named after the table. The test selects all
declared columns with `LIMIT 0`: PostgreSQL validates their existence without
reading or changing rows, so empty tables are checked too.

**Run it:** with Docker running, from `backend/`, use the resource supervisor
required by your environment to run:

```bash
uv run pytest -n 0 -m integration tests/integration/test_database_schema.py -v
```

**When it fails:** first distinguish a test failure from a fixture setup error.
If container startup or a migration fails during setup, resolve that error first.
For a missing table or column, the test ID identifies the table and PostgreSQL's
error names the missing object. Compare its declaration in `src/eneo/database/tables/`
with its migrations in `alembic/versions/`. Decide whether the model describes the
intended stored data: add a migration for a needed schema change, correct an
incorrect model declaration, or remove confirmed unused model code. Do not skip
the table to make CI pass. For example, `groups_spaces` and `websites_spaces`
incorrectly inherited `updated_at`; their insert/delete lifecycle only needs
`created_at`, so the fix belongs in the models.

**Limits:** this is a table-and-column existence check, not a complete schema
comparison. Unregistered tables are outside its scope. It does not validate types,
constraints, defaults, indexes, extra database columns, or upgrades with existing
customer data. Keep focused migration
and behavior tests for those contracts. The CI job named **Schema drift** is a
separate check of the generated TypeScript API schema.

### Durable Object Content

Durable content has one PostgreSQL control plane and one explicit byte backend
per record:

| PostgreSQL control plane                                | Byte backend                                                       |
| ------------------------------------------------------- | ------------------------------------------------------------------ |
| Content identity and lifecycle state                    | Bounded `postgres_inline` payload or private `object_store` object |
| Canonical SHA-256, exact size, and media type           | Payload bytes only                                                 |
| Concrete authorization references, holds, and retention | Backend-specific transport/deletion state                          |
| Audit and bounded reconciliation/query facts            | No authorization, routing, or product policy                       |

Inline bytes, control state, and the first owner reference commit atomically.
Object-store intent and the first reference commit before remote work. Eneo
verifies the PostgreSQL-owned SHA-256 before returning full or range responses,
and a bounded reconciler resolves process and network failures.

Object storage is optional. The default reference deployment is inline-capable
without another service. Operators can run Eneo's built and attested SeaweedFS
profile or an external endpoint such as MinIO. Administrators with the Storage
permission connect and select either option through the same vendor-neutral
contract.

Read [Object Content Architecture](/docs/object-content-architecture) for the
complete lifecycle, integrity, reconciliation, binding, and image publication
design. The [Object Content Storage guide](/guides/object-content-storage)
covers deployment and operations.

### Worker Service (ARQ today)

**Technology:**

- **Queue**: Redis-based ARQ (Async Redis Queue)
- **Language**: Python with async/await
- **Concurrency**: `WORKER_MAX_JOBS` concurrent jobs per worker process
  (default 15) and `TENANT_WORKER_CONCURRENCY_LIMIT` concurrent crawl jobs per
  tenant (default 4), enforced through durable PostgreSQL admission

**Responsibilities:**

- Document upload processing (extraction, chunking, embedding, versioned publish)
- Crawl admission and recovery, with execution on the dedicated crawler worker
- SharePoint and Confluence synchronisation, including subscription renewal
- Audit log export and cleanup, usage statistics, conversation insights
- Scheduled jobs: daily data retention, weekly cleanup of orphaned models,
  redispatch and reaping of stale knowledge jobs, object-content
  reconciliation (also run at worker startup)

Object-content reconciliation is implemented as a queue-neutral async task.
Only the current registration and schedule adapter depends on ARQ. A future
worker change therefore does not alter the object store, lifecycle, or database
contract, and Eneo avoids a speculative generic queue framework in the meantime.

**Task registration:** each domain declares tasks on its own `Worker`
instance, and `worker/arq.py` composes them into one `WorkerSettings` for ARQ.

```python
# backend/src/eneo/worker/routes.py
@worker.function(with_user=False)
async def log_audit_event(
```

```python
# backend/src/eneo/data_retention/infrastructure/data_retention_worker.py
@worker.cron_job(hour=3, minute=0)  # Run daily at 3 AM
```

**Web Crawling:**

The API, general worker and crawler worker share a durable crawl lifecycle in
PostgreSQL. Redis carries work to the dedicated `arq:crawler` queue.

1. **Admission:** A manual request or schedule creates a crawl run in PostgreSQL
   before dispatch. Concurrency limits determine when queued work can start.
2. **Execution:** The crawler worker claims an execution attempt with a renewable
   lease, then discovers pages through links or a sitemap. It records progress
   against that attempt.
3. **Publication:** Extracted text is hashed, split and embedded. Unchanged text
   with the same embedding model reuses stored content. Publication checks that
   the attempt still owns its lease before committing each batch.
4. **Recovery:** The general worker reconciles missed deliveries, expired leases
   and transport cleanup. A dead execution becomes interrupted; a stale worker
   cannot publish after losing ownership. Both worker services are required.

Recursive crawls fetch HTML again so unchanged pages can still lead to new or
previously missed descendants. Conditional page requests are limited to sitemap
crawls with file downloads disabled. Robots server errors, timeouts and network
failures stop discovery after bounded retries. Only complete discovery can
authorize removal of sources no longer present; partial runs preserve them.

A normalized source URL identifies each website document. Files at different
URLs remain separate even when their names match; a title change at the same URL
keeps the source's version history. Migration preserves existing metadata and
citation IDs. Unknown or ambiguous legacy URLs remain available and require
resolution before publication can replace them. Changed content retains the
text and metadata of previous versions so citations stay readable; their chunks
and embeddings are removed once the replacement is published, because retrieval
reads only the active version. Removal of an absent source removes its history
and citation references. There is no automatic age-based retention policy.
Crawl history is paginated, and the UI loads older runs on request.

Uploads and crawl downloads share extraction subprocesses with time, output,
archive and PDF bounds; Linux also enforces address-space limits and parent-death
cleanup. HTML parsing and text splitting use a bounded thread pool so they do not
run directly on the worker's event loop. Quota checks include what retained
versions keep, credit the chunks a replacement releases, and serialize the
final commit after provider work, rolling back an over-limit
publication. Stored knowledge also prevents changes to embedding model semantics
or provider routing; those changes require a new model and reindexing.

The worker writes a heartbeat key to Redis; `/api/healthz` reports the worker
as unhealthy when that heartbeat is stale.

## Data Flow

### User Authentication Flow

```
Browser ──POST /login (SvelteKit form action)──▶ Frontend server
Frontend ──POST /api/v1/users/login/token/ ──▶ Backend  (password login)
Frontend ──GET  /api/v1/auth/initiate → IdP → POST /api/v1/auth/callback ──▶ Backend  (OIDC)
Backend  ──signed JWT (sub, aud, iss, exp)──▶ Frontend
Frontend ──Set-Cookie: auth=<jwt>; HttpOnly; Secure; SameSite=Lax──▶ Browser
Browser  ──subsequent requests: frontend server forwards the JWT as a bearer token──▶ Backend
```

The frontend stores the backend-issued JWT in an httpOnly `auth` cookie whose
`maxAge` is the token expiry minus ten minutes. There is no refresh token: when
the token expires the user signs in again. A second httpOnly cookie, `acc`,
carries a provider access token when the identity provider issues one.

### AI Chat Flow

```
User types message
    ↓
Frontend POSTs to /api/v1/conversations/ with stream: true
    ↓
Backend authenticates the JWT and checks space access
    ↓
Embed the question and run the pgvector search over the assistant's
collections, websites, and integrations (or expose search as an MCP tool)
    ↓
Build the prompt within the model's context budget
    ↓
LiteLLM streams from the tenant's configured provider
    ↓
Server-Sent Events stream chunks back to the browser
    ↓
Question, answer, token counts, and info-blob references are saved
```

See [Knowledge Retrieval and MCP](/docs/knowledge-retrieval-and-mcp) for the
retrieval modes.

### Document Upload Flow

<div className="bg-white dark:bg-white p-4 rounded-lg border border-gray-200 dark:border-gray-700 my-8">

![Document Processing Pipeline showing User uploading to Backend API, which queues jobs in Redis for the Worker to process. The Worker runs the Processing Pipeline (Text Extractor, Text Chunker, Embedding Model, Vector Store) and stores results in PostgreSQL with pgvector (InfoBlobs for raw text, InfoBlobChunks for embeddings searched by cosine distance, Jobs for status tracking).](/diagrams/document-processing-pipeline.svg)

</div>

1. User uploads a File; its bytes follow the deployment's selected storage policy.
2. Backend enqueues document processing.
3. Worker extracts text, creates chunks, and generates embeddings.
4. One short transaction supersedes the previous version, publishes the new
   `InfoBlobs` version and every `InfoBlobChunks` vector, and removes the
   previous version's chunks.
5. Retrieval reads only the active version. Exact historical references and
   the previous text remain readable until the document is deleted.
6. A failed replacement rolls back; the previous complete version, chunks
   included, remains active.
7. The job records `COMPLETE` or `FAILED` for the frontend.

PostgreSQL owns searchable text, version state, and pgvector data regardless of
where Eneo stores the original File bytes. Object storage remains optional.

## Security Architecture

### Authentication

1. **Username and password** (`POST /api/v1/users/login/token/`): the backend
   verifies the credentials and mints a JWT signed with `JWT_SECRET` using
   `JWT_ALGORITHM`, with `JWT_AUDIENCE`, `JWT_ISSUER`, and `JWT_EXPIRY_TIME`
   (the session lifetime in minutes; `1440` is 24 hours).
2. **OIDC federation** (`/api/v1/auth/federation-status`, `/auth/tenants`,
   `/auth/initiate`, `/auth/callback`): per-tenant identity providers configured in the tenant's
   `federation_config`, with a signed state parameter. See
   [Authentication Architecture](/docs/authentication-architecture).
3. **API keys** (`X-API-Key` header): scoped keys stored as HMAC hashes in
   `api_keys_v2`, with optional rate limits, allowed origins, allowed IPs, and
   expiry. A separate super API key protects the `/api/v1/sysadmin` routes.
4. **SCIM** (`/scim/v2`): tenant-scoped bearer token for user provisioning.

Cookies are `HttpOnly`, `Secure` outside development, and `SameSite=Lax`.
There is no separate CSRF token or refresh-token mechanism.

### Authorization Model

- **Tenant permissions**: users hold roles that grant permissions such as
  `assistants`, `collections`, `websites`, `api_keys`, `storage`, `modules`,
  and `admin`.
- **Space roles**: `admin`, `editor`, or `viewer` per space member or user
  group. A personal space belongs to exactly one user.
- **Resource checks**: every space action goes through a space actor that
  answers questions such as "can this user create websites here" based on the
  member's role and the resource type.

### Data Security

- TLS is terminated by Traefik with Let's Encrypt certificates.
- Secrets are read from environment files (`env_backend.env`,
  `env_frontend.env`, `env_db.env`), never from the image.
- API keys are stored as keyed HMAC hashes; only the prefix and suffix are kept
  for display.
- Durable object content is verified against its PostgreSQL-owned SHA-256
  before being served.
- PostgreSQL and Redis sit on an internal Docker network (`data_net`) with no
  internet egress and no route from Traefik or the frontend.

## Scalability Considerations

### Horizontal Scaling

- The API holds no per-user session state, and worker-to-browser updates travel
  through Redis pub/sub, so several backend instances can sit behind Traefik.
  The reference Compose file pins `container_name` for every service, so remove
  those names before running more than one replica.
- Each backend container already runs three Gunicorn/Uvicorn workers
  (`NUM_WORKERS`).
- Worker capacity scales with additional worker containers; per-process
  concurrency is `WORKER_MAX_JOBS`, and crawl fan-out per tenant is capped by
  `TENANT_WORKER_CONCURRENCY_LIMIT`.

### Database

- Keep `WORKER_MAX_JOBS` below roughly 60 % of `DB_POOL_SIZE +
  DB_POOL_MAX_OVERFLOW` so the API always has connections; the backend
  environment template documents the sizing formula.
- Retrieval cost is proportional to the chunks in scope of a search, so large
  tenants benefit from splitting knowledge into focused collections.

## Deployment Topology

The reference deployment in `docs/deployment/docker-compose.yml` starts the
services in this order, gated by health checks:

1. `db` (PostgreSQL 16 + pgvector) and `redis` become healthy.
2. `db-init` runs `python init_db.py`: Alembic migrations and the default
   tenant and user, then exits.
3. `backend` and `worker` start; `backend` exposes `/api/healthz`.
4. `frontend` starts.

Networks: `proxy_tier` (Traefik, frontend, backend, worker; internet-facing),
`data_net` (PostgreSQL and Redis; internal only), `module_net` (Traefik and
backend; reserved for optional module containers), and `tool_runtime_net`
(backend, general worker and bundled runtime; internal only).

The runtime starts as a separate service, without gating backend readiness.
It exposes port 3010 only on the private network and has no database, Redis or
internet route in the reference deployment. The separate MCP App content
hostname routes view content to the backend, not to the runtime. See
[Tool Runtime Security](/docs/tool-runtime-security) for what the container
and network settings protect, and the
[tool runtime operator guide](https://github.com/eneo-ai/eneo/blob/develop/docs/deployment/TOOL_RUNTIME.md)
and [MCP Apps deployment guide](https://github.com/eneo-ai/eneo/blob/develop/docs/deployment/MCP_APPS.md)
for configuration.

Optional overlays:

- `docker-compose.object-content.yml` adds the bundled SeaweedFS S3 endpoint
  under the `object-content` profile on its own internal network.
- `docker-compose.modules.yml` adds optional module containers such as
  speech-to-text.

See [Deploy Eneo](/guides/deployment) for the full procedure.

## Monitoring & Observability

### Logging

Backend and worker log JSON lines to stdout, with the trace id of the current
request attached when tracing is active.

### Tracing

FastAPI, SQLAlchemy, Redis, aiohttp, and httpx are instrumented with
OpenTelemetry, and every response carries an `X-Trace-Id` header for
correlating a user report with server logs.

### Health Checks

| Endpoint               | Purpose                                                                                                           |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `GET /api/livez`       | Liveness: the API process can serve requests                                                                      |
| `GET /api/healthz`     | Backend, worker heartbeat, and object-content readiness; `503` when the worker is stale or the store is not ready |
| `GET /api/readyz`      | Alias of `/api/healthz` for readiness probes                                                                      |
| `GET /api/healthz/crawler` | Detailed crawler diagnostics; requires the deployment's super API key; not intended for orchestrator probes |

## Technology Decisions

### Why SvelteKit?

- Server-side rendering with a single Node process
- Small bundles and a compiler-driven component model
- Form actions keep login and cookie handling on the server

### Why FastAPI?

- Async-native Python with first-class OpenAPI generation, which also feeds the
  frontend's typed client
- Pydantic models shared between validation and documentation

### Why PostgreSQL + pgvector?

- One database for relational data, versioned text, and vectors: a document
  version and its chunks publish in a single transaction
- Dimensionless vector column allows several embedding models per tenant

### Why ARQ?

- Python-native async task queue on the Redis that is already deployed
- Cron jobs, job abort, and lifecycle hooks with a small surface, kept behind a
  queue-neutral task layer
