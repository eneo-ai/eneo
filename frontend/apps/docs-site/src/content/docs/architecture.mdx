# Architecture

Eneo is a web application with a Python API, relational control plane, and
background workers. The reference deployment is a Docker Compose stack; it is a
deployment model, not a claim that every installation uses a microservice or
Kubernetes topology.

## System shape

```text
Browser
  │
  ├── frontend web application
  │
  └── reverse proxy (reference deployment)
          │
          ├── FastAPI application ── PostgreSQL with pgvector
          │           │                         │
          │           └── Redis                 └── durable content metadata
          │
          └── background workers ── AI providers and configured integrations
```

The backend is the boundary between users and the data layers, configured
external providers, optional object storage, and optional modules. The reference
Compose configuration keeps PostgreSQL and Redis on an internal data network;
the backend and workers receive the outbound access they need for configured
providers and integrations.

## Application components

### Frontend

The primary web application lives in `frontend/apps/web`. It is a SvelteKit
application built with Vite. It presents Eneo’s user interface and calls the
backend API; it does not own the authoritative data or permission decisions.

The documentation site is a separate Next.js and Nextra application in
`frontend/apps/docs-site`. It is not part of the product request path.

### Backend API

`backend/src/eneo/server/main.py` creates the FastAPI application. The server
mounts the main API router under the configured API prefix, exposes generated
OpenAPI at `/openapi.json`, and serves interactive documentation at `/docs` and
`/redoc`.

Route adapters own HTTP concerns. Domain services and repositories own the
application and persistence behavior behind those routes. See the
[API Reference](/docs/api) for the generated public contract.

### PostgreSQL, Redis, and durable content

PostgreSQL, with pgvector in the reference deployment, holds application data
and searchable vector data. Redis supports queueing and other transient runtime
coordination.

Durable file content has a PostgreSQL control plane. Bytes can remain bounded
and inline or use a configured object store; authorization, integrity,
lifecycle, retention, and reconciliation remain backend-owned. Read
[Object Content Architecture](/docs/object-content-architecture) for the
complete contract.

### Background work

The general worker uses ARQ for asynchronous work such as document processing,
crawls, and integrations. Flow execution and maintenance use dedicated Celery
workers and a scheduler. Their queues share infrastructure where configured,
but their responsibilities stay separate so Flow runtime recovery does not
change unrelated background work.

### Identity and authorization

Eneo supports local sign-in as well as OpenID Connect federation. Federation
can use globally configured OIDC settings or tenant-specific configuration;
the login route resolves the appropriate configuration and validates redirect
origins before it redirects to an identity provider.

Maintainers should use [Authentication Architecture](/docs/authentication-architecture)
for protocol and implementation detail.

## Reference deployment

The tracked Compose deployment includes Traefik, the frontend, backend,
PostgreSQL, Redis, a general worker, and the dedicated Flow worker processes.
Traefik terminates TLS and routes product, API, SCIM, and API-documentation
traffic to the correct service.

Deployment-specific settings, startup ordering, health checks, network
boundaries, and optional object storage belong in the
[deployment guide](/guides/deployment), not in this overview.
