# AI Builder

AI Builder helps a human operator draft or revise an Eneo Flow through a guided conversation. It is an authoring surface, not a separate runtime. The result is still a normal draft Flow that you review, adjust if needed, publish, and run through the same Flow runtime contract as manually authored flows.

Use AI Builder when you know the outcome you want but do not want to assemble every step, input binding, and output contract by hand.

<Callout type="info">
  AI Builder requires a user principal with Flow edit permission. Service keys
  can run published Flows, but they cannot author drafts through AI Builder.
</Callout>

## When to use AI Builder

AI Builder is a good fit for:

- text workflows such as intake summaries, comparison memos, and review notes
- document workflows that read PDF/DOCX input and produce structured JSON, PDF, or DOCX output
- audio workflows that transcribe a recording and then generate follow-up material
- flows that need reusable runtime fields, such as audience, language, date range, or classification
- flows that need a specific MCP tool in one step, such as fetching live data or writing to an external system

It is less useful when the intended process is still unclear. In that case, use the conversation to clarify the outcome, required input, final output, and any external systems before approving the plan.

## Authoring model

AI Builder separates semantic intent from Flow mechanics.

| Layer            | Responsibility                                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------------- |
| User             | Describes the outcome, constraints, source material, runtime fields, and external systems               |
| AI Builder       | Proposes semantic fields, steps, and resource intent                                                     |
| Backend compiler | Turns the plan into Flow mechanics: step wiring, material bindings, validation, and assistant resources |
| Human reviewer   | Approves, changes, or rejects the plan before it becomes a draft Flow                                   |

This split keeps generated plans maintainable. The model describes what each step should accomplish; the backend owns deterministic details such as step output mechanics, final artifact rendering, and how previous outputs and form fields become material for later steps.

For create-plan compilation, supported shapes now pass through an explicit compile-time assembly spine:

| Module                            | Responsibility                                                                                                 |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `ai_builder_assembly.create`      | Admits supported create topologies and builds a `FlowAssemblyPlan`                                             |
| `ai_builder_assembly.plan`        | Defines the compile-time `FlowAssemblyPlan` and `PlannedStep` contract                                         |
| `ai_builder_assembly.fixed_steps` | Owns backend-fixed planned steps such as audio transcription, final document rendering, and DOCX template fill |
| `ai_builder_assembly.lower`       | Projects the assembly plan into the normal `FlowDraftSpecCore` authoring graph                                 |

That spine is compile-time only; it is not persisted and it is not a second Flow definition. Its job is to make mechanical choices once, then lower them into normal Flow authoring data.

`FlowAssemblyPlan` is the construction-time guardrail. It validates capability support, step order, previous-output references, form-field placement, source exposure, source-reader obligations, UI language, and aggregation intent before lowering. Linear plans reject fan-in; aggregate and compare plans may use fan-in only where the body writer intentionally combines compacted prior outputs.

The lowering layer is the only writer of compiled source refs and input bindings for assembly-backed create plans. Do not add create-mode passes that rewrite underlag, renderer, transcription, or template-fill mechanics after lowering.

Current assembly-backed create shapes include:

- linear text, JSON, and document-source flows
- generated PDF/DOCX artifact flows with a body-writer step followed by a `render_verbatim` renderer
- aggregate and compare document flows where the body writer intentionally fans in prior compacted step outputs
- pure audio transcription and audio-derived report flows
- DOCX template-fill flows with a template-variable reader, content-preparation step, and `template_fill` step

Generated document artifacts use `render_verbatim` for the final renderer. Audio transcription uses `transcribe_only`. Both are zero-LLM runtime pathways; the LLM work happens in semantic preparation steps before those fixed runtime modes.

Create-mode proposal tools do not expose per-step input sources, input types, output types, output modes, previous-step refs, or raw bindings. `output_fields` describe semantic JSON fields; the compiler derives the concrete Flow output type and renderer mechanics from the committed architecture.

In edit sessions, changes to a step's input source, input type, or selected form/previous fields are semantic changes. The backend re-derives the compiled input bindings, input contract, and runtime input configuration from those choices.

Existing Flow steps are preserved unless the approved edit proposal explicitly includes a modified version of the step or lists the step for removal. AI Builder can request a terminal artifact format from the conversation context, but Flow package imports and manual authoring do not infer a final artifact type from Builder-only conversation state.

Resource names shown to AI Builder are prompt-visible aliases. The Builder resolves those aliases into portable Flow resource refs before the Flow application preparation validates and applies the authoring graph.

## Typical workflow

1. Start an AI Builder session in a space.
2. Describe the flow in plain language.
3. Answer clarification questions about input, output, runtime fields, and external tools.
4. Review the generated plan.
5. Approve the plan to apply it to a draft Flow.
6. Publish the Flow when the draft is ready to run.

The review step matters. A plan can be valid but still not be the best workflow for your organization. Check the input contract, final output, external tool access, and evidence requirements before publishing.

## Plan proposal contract

AI Builder plan endpoints return one proposal object. Treat `proposal.spec` as the draft Flow that will be applied after approval. Supporting fields such as `assumptions`, `lint_warnings`, `risk_acknowledgments`, and `plan_rationale` explain why that draft was proposed.

Edit sessions may also include `proposal.edit`. This is the approval metadata for the edit, not a second Flow spec. It contains the base draft revision, the explicit existing step refs that will be removed, the preview diff, warnings, advisories, risk flags, and confidence. Use it to render edit review UI and stale-revision checks.

The `description_override_manual` flag records that the reviewer chose to keep the current Flow description. It applies to create and edit plans.

Do not depend on compiled edit internals or legacy `edit_result` fields. The public contract is the proposal content plus optional `proposal.edit`; the backend owns compilation, validation, and application details.

## Inputs, outputs, and contracts

AI Builder can propose the same core capabilities used by manually authored Flows:

| Capability         | What it means                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| Runtime input      | The main text, document, audio, image, file, or structured input for a run                          |
| Form fields        | Reusable values supplied at run time, such as language, audience, role, date range, or report level |
| JSON output fields | Structured output that later steps or integrations can reuse reliably                               |
| Final artifacts    | User-facing PDF or DOCX output rendered from a prepared body step                                   |
| Step resources     | Knowledge sources or MCP tools attached only where the step needs them                              |

Prefer explicit form fields when a value will vary per run. Prefer JSON output fields when a downstream step or integration needs stable machine-readable data.

## Underlag till steget

The Flow editor uses the Swedish label **"Underlag till steget"** for the material text a step receives.

That is different from instructions:

| Concept              | Purpose                                                     |
| -------------------- | ----------------------------------------------------------- |
| Instructions         | Tell the model what to do                                   |
| Underlag till steget | Controls the text or structured material the model works on |

AI Builder should normally let the backend compose material from flow input, form fields, files, and previous outputs. That is more robust than asking the language model to hand-write fragile prompt templates. Use advanced material overrides only when the default material assembly is not precise enough.

For assembly-backed create plans, the underlag channel is part of `FlowAssemblyPlan`: implicit previous output, whole-object refs, field refs, text anchors, or fan-in. The selected channel is lowered into normal Flow bindings once. Later validation may reject invalid output, but it must not silently choose a different channel.

See <a href="/docs/flows#advanced-step-input-templates-underlag-till-steget">Advanced step input templates</a> for the runtime mental model.

## MCP tools in AI Builder

AI Builder can use MCP server and tool metadata from the current space when deciding whether a step should have external tool access. It reads names, descriptions, and available tools. It does not execute MCP tools while drafting a plan.

At runtime, only the published Flow step executes with the MCP tools configured for that step.

Use MCP when a step needs external data or an external action, for example:

- looking up a live case, ticket, product, or record
- writing a result to a system of record
- calling an approved internal calculation or validation tool
- fetching data that should not be copied into static knowledge

Use the narrowest practical access:

| Selection           | Effect                                                      |
| ------------------- | ----------------------------------------------------------- |
| Tool-level access   | The step receives only the selected MCP tools               |
| Server-level access | The step receives every enabled tool on the selected server |

If a flow needs both knowledge retrieval and MCP tools, keep them on separate steps. This makes the data source for each result easier to inspect and avoids mixing retrieval context with external tool execution in the same assistant configuration.

<Callout type="warning">
  Treat MCP descriptions as part of the authoring contract. Good descriptions
  should state what the tool reads, what it writes, when to use it, and any
  important side effects.
</Callout>

## Token usage

AI Builder shows token usage for the builder work itself. The total includes planning, proposal generation, and any repair attempts needed to produce a valid plan.

The token meter is for transparency:

- input tokens show what was sent to the model
- output tokens show what the model generated
- the model name shows which model handled the builder call
- an estimated label means the provider did not return exact usage, so Eneo used a local estimate

It is not a billing view. Cost and budget policy stay in the operator and admin surfaces.

## Review checklist

Before approving an AI Builder plan, check:

- the final output type matches the real user need
- runtime fields cover values that change from run to run
- JSON outputs are structured enough for downstream steps
- document or audio inputs are attached to the right step
- each MCP tool is intentional and scoped to the step that needs it
- knowledge retrieval and MCP execution are separated when both are needed
- the final artifact has a clear reader, purpose, and format
- sensitive workflows have the right evidence and retention policy expectations
