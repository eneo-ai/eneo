# AI Builder

AI Builder helps a human operator draft or revise an Eneo Flow through a guided conversation. It is an authoring surface, not a separate runtime. The result is still a normal draft Flow that you review, adjust if needed, publish, and run through the same Flow runtime contract as manually authored flows.

Use AI Builder when you know the outcome you want but do not want to assemble every step, input binding, and output contract by hand.

<Callout type="info">
  AI Builder requires a user principal with Flow edit permission. Service keys
  can run published Flows, but they cannot author drafts through AI Builder.
  Applying an edit also requires ownership of the target draft. Tenant admins
  and space owners may override draft ownership; space admins and editors may
  not change another member's draft. A refused apply returns `flow_owner_required`
  in the standard 403 Builder error envelope and makes no draft change.
</Callout>

## Permissions

Builder session and plan operations require the role permissions `flows_manage`
and `flows_ai_builder`, together with Flow edit access in the session's space.
Requesting Builder run-review findings also requires `flows_ai_builder_review`.
Resource scope, session ownership and plan-state checks still apply; for example,
only the session creator can request a structured plan revision.

## When to use AI Builder

AI Builder is a good fit for:

- text workflows such as intake summaries, comparison memos, and review notes
- document workflows that read PDF/DOCX input and produce structured JSON, PDF, or DOCX output
- audio workflows that transcribe a recording and then generate follow-up material
- flows that need reusable runtime fields, such as audience, language, date range, or classification

It is less useful when the intended process is still unclear. In that case, use the conversation to clarify the outcome, required input, final output, and any external systems before approving the plan.

## Authoring model

AI Builder separates semantic intent from Flow mechanics.

| Layer            | Responsibility                                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------------- |
| User             | Describes the outcome, constraints, source material, runtime fields, and external systems               |
| AI Builder       | Proposes semantic fields, steps, and resource intent                                                    |
| Backend compiler | Turns the plan into Flow mechanics: step wiring, material bindings, validation, and assistant resources |
| Human reviewer   | Approves, changes, or rejects the plan before it becomes a draft Flow                                   |

This split keeps generated plans maintainable. The model describes what each step should accomplish; the backend owns deterministic details such as step output mechanics, final artifact rendering, and how previous outputs and form fields become material for later steps.

When the final report or document needs named sections, say which headings must appear in the finished output. You can still use headings to organize a detailed workflow description: headings that describe inputs, tasks, reviews, or delivery stages are treated as authoring guidance rather than as an automatic final-report outline.

Compilation is deterministic and server-owned: the model never chooses step
wiring, output mechanics, or renderer settings, so two plans that describe the
same outcome compile to the same Flow mechanics. Supported create shapes are:

- linear text, JSON, and document-source flows
- generated PDF/DOCX artifact flows: a body-writer step followed by a fixed renderer
- aggregate and compare document flows, where the body writer reads structured outputs from prior steps
- pure audio transcription and audio-derived report flows
- DOCX template-fill flows: a template-variable reader, a content-preparation step, and a fixed fill step

The final renderer, transcriber, and template-fill steps make no model calls;
model work happens in the preparation steps before them.

In generated PDF/DOCX create flows, mentioning the artifact type in a step's name or instructions does not remove that step. The fixed renderer follows the final content writer.

In edit sessions, changes to a step's input source, input type, or selected form/previous fields are semantic changes. The backend re-derives the compiled input bindings, input contract, and runtime input configuration from those choices.

Existing Flow steps are preserved unless the approved edit proposal explicitly includes a modified version of the step or lists the step for removal.

When an edit adds a step before the saved first step, a saved step that takes the run's input as its own input, takes an upload, or has a configuration the Builder cannot read must stay first: the edit is sent back to the model. A saved step that names what it reads (run-form fields, or the run's text or whole input explicitly) is moved and keeps reading the same input; its input source becomes the previous step because only step 1 may take the run's input as its input source.

An applied edit writes only what the approved plan lists as changed. A modified step keeps every column the plan does not name as it was saved, including configuration the Builder cannot author, and a column the plan names with no value is cleared rather than filled with a default. Two changes reach a column the plan does not name: a reference to a step that moves follows that step, and configuration of a mode the step no longer runs is dropped. The run form keeps its saved field types.

The Builder cannot edit a saved Flow that has a step which fetches data over HTTP, takes an image as input, or sends its result over HTTP. The Builder asks its usual questions first; when it would propose the edit, it instead answers with the names of those steps and a pointer to the step editor, where they are changed by hand, and no plan is proposed. A request to edit another step of the same Flow is refused the same way and the answer says that no edits can be proposed while those steps exist.

A saved Flow with steps that read an MCP tool stays editable. The Builder keeps those steps as they are saved, name and configuration included, unless the edit changes a step's tool arguments while the space's tools are listed to the Builder, or removes the step (see External data and delivery): another step that takes the same name gets the suffix, and a whole-Flow edit shows the model each one's arguments (as JSON, the first 220 characters). A request scoped to one of those steps, or a run failure or suggestion that names only such steps, gets the same step-editor answer as above while the Builder lists no tool of the space, and so does any edit while one of them holds a tool configuration that cannot be used. A tool argument that reads an earlier step's result counts as a read of that step: an edit that removes the producer step, or the output field the argument reads, is refused or sent back to the model for a fix. An argument that names its producer by number (`step_1`) follows the producer when it moves; an edit that would make a read in such a step (an argument or its instructions; for a step whose arguments the edit writes, its instructions) name another step, by number or by name (for example by removing the producer and giving another step its name), is sent back to the model; `föregående_steg` keeps meaning the step just before.

When no step of a saved Flow reads what a run is started with besides its form fields (the run text or a step's upload), the Builder does not need an answer about what the Flow receives at runtime, and its summary says that the Flow receives no material to upload or paste. It still asks when it reads a material in the request: a word such as PDF or document can be read that way even when it names the result. A tool argument or a step's prompt that reads the run input, for example `{{flow_input.text}}`, is such a read. The Builder reads the steps' sources, prompts, bindings, tool arguments and output settings for this, and asks as before when it cannot read every step's prompt and configuration, or when a step fetches or sends data over HTTP. The run form does not change: a Flow without form fields and uploads still shows a text box.

When a modified step's patch names a review mode (`view` or `edit`), it changes the mode only: a review deadline saved on the step stays, and the approval lists the step as unchanged when the mode is the one already saved. Setting the mode to `none` removes the review step, deadline included. AI Builder cannot set or reset a review deadline; to return to the default, remove the review and add it again.

When you ask to check and correct a structured (JSON) result before the flow continues, the review goes on the step whose result you named, even when later steps also produce structured results: the plan marks that step, and when only one of the plan's own steps produces a structured result, the review goes there. If the plan cannot say which step it is, AI Builder asks for a new plan instead of guessing. On a saved flow, a request to change or remove that review acts on the step that already has it. When several steps of a saved flow review structured results, AI Builder answers with their names and a pointer to the step editor before it asks the model for a proposal, so no other saved review changes.

## Typical workflow

1. Start an AI Builder session in a space.
2. Describe the flow in plain language.
3. Answer clarification questions about input, output, runtime fields, and external tools.
4. Review the generated plan.
5. For a new Flow, approve and create the draft. For an edit, approve the plan and then apply it to the saved Flow.
6. Publish the Flow when the draft is ready to run.

The API separates these actions. Paths below are relative to
`/api/v1/flows/ai-builder`; use the prefix from your deployment's OpenAPI contract.

| Action                     | Request                                                                         | Effect                                                                                                                                |
| -------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Create a new Flow          | `POST /plans/{plan_id}/create`                                                  | Approves a proposed create-mode plan and creates its draft Flow in one transaction; an already-approved create plan is also accepted. |
| Approve an edit            | `POST /plans/{plan_id}/approve`                                                 | Changes a proposed plan to `approved`; this action does not write the Flow.                                                           |
| Apply the approved edit    | `POST /plans/{plan_id}/apply`                                                   | Applies the approved plan to its target Flow.                                                                                         |
| Keep the saved description | `POST /plans/{plan_id}/revise` with `type: "keep_current_description"` | Replaces a proposed plan with a new proposed revision that keeps the current description.                                             |

The requirements card summarises what the Builder understood. Its wording is never read back as if you had written it.

The purpose you choose for a runtime field guides where a new plan places it: the step that interprets the input, the step that shapes the result, or every step. A plan can also ask for the field on further steps that read it, such as a calculation in the middle of the flow. Such a request is accepted only on steps that can read a form value directly; a request on any other step, such as one that runs once per source, sends the plan back for revision.

The review step matters. A plan can be valid but still not be the best workflow for your organization. Check the input contract, final output, external tool access, and evidence requirements before publishing.

## Template attachments and reference material

Builder attachments do not all become Flow inputs. Reference documents and
example outputs are planning evidence: they can shape the approved Flow, but
they are not materialized as Flow inputs or resources and their content is not
sent again at Flow runtime. A published Flow that accepts runtime files receives
separately uploaded files when a run starts.

A terminal DOCX template-fill Flow requires exactly one confirmed DOCX
template. Before approval, AI Builder inspects the real document, binds every
exact placeholder to an injected transcription value, the current date
(`datum`), a typed earlier-step output, or a form field, and refuses
placeholders it cannot prove will exist. A step field a placeholder reads is
compiled as a required field of one type, even when the plan declared it
optional or nullable: the fill step stops a run on null or a missing key and
treats an empty string as a deliberate omission, so the step writes an empty
string for a text value the source does not state. Only `type` and `required`
change, and only when they must: a field declared as one type plus null keeps
that type, and every other keyword stays. The change is made only when the
whole output contract of the step is plain (types, properties, required, items
and annotations only): a step whose contract carries an enum, a constraint,
allOf, $ref or not anywhere, or a field with no single type, is not edited and
is sent back to the plan. Before an edit is kept, a sample instance is
validated against the edited contract, and if it fails nothing is changed. An
edit of a single step rewrites nothing for the template and refuses such a
field in the selected step; an edit of the whole flow corrects it. A
placeholder nothing in the Flow fills sends the plan back to add a step that
prepares it; it becomes a form field only when you ask to type it at run time
or it names a Flow input (`flow_input.x`). A transcription placeholder also
makes the Flow's audio input required. Zero or multiple selected templates
produce a typed refusal instead of a publishable-looking incomplete Flow.

When the plan is applied, Eneo reuses the same uploaded File and creates the
Flow-owned template asset and binding inside the atomic plan-apply transaction.
It does not copy the DOCX or leave a raw Builder-session file identifier in the
published definition. A successful template asset remains available after the
Builder session is deleted; a failed apply rolls back the Flow, asset, binding,
and plan transition together.

The final template-fill step is deterministic: it performs zero model calls and
zero model tokens. Earlier preparation steps may still use a model when the
workflow needs generated or transformed content for the template.

Public AI Builder request bodies are closed contracts. Build payloads from the
OpenAPI schema or generated Eneo client: an unknown or misspelled property
returns HTTP `422` with code `request_validation_error`. Correct the payload
instead of retrying the same invalid request.

## One user, several concurrent clients

A user can drive AI Builder from more than one place at once, for example
several browser tabs or an application using a user-owned API key. All of them authenticate as
the same user, so the server cannot tell them apart, and each Builder session
still belongs to that user: only its creator may read or send to it, and a
session id on its own grants nothing. Service-key principals cannot author
Builder sessions at all.

The guarantee is one specific rule: creating or resuming a session never
mutates another session. `force_new` on `POST /api/v1/flows/ai-builder/sessions`
creates one session and does not replace or cancel another, so a session a
client abandons keeps its conversation, its proposed plan and its attachments.

This is not isolation between clients. They authenticate as the same user, so
any of them may list that user's sessions and explicitly send to or cancel a
session that was created through another client; retention and other explicit
operations can also end sessions. Only the create/resume path is guaranteed not
to touch a sibling.

Two sends on the _same_ session id still conflict: the second is refused with
`session_send_in_progress` while the first turn is with the provider. Give each
concurrent client its own session id.

Cancelling a session also stops the turn that is with the provider. While the
server can read the session, the call in flight is closed within about 12
seconds plus a 1 second stream close, and that turn's stream then ends with
`session_send_lease_lost` after the turn's cleanup, which may take up to 30
seconds when the database is slow. Noticing the cancel needs a successful read
of the session, so while the database keeps failing there is no finite
detection guarantee.
The provider may still finish and bill work it had already started.

## Reliable message sends and retries

Each message send has one `client_turn_id`. A client creates this UUID once and
reuses it only when retrying that same message, attachment set, and request. The
server rejects the key if a later request changes those inputs.

The session response exposes the latest accepted turn in `latest_turn`. This
record survives conversation compaction and includes the exact `retry_request`
the server accepted. After a reload, use that request instead of rebuilding one
from visible chat text.

Retry behavior depends on the persisted turn state:

| State                      | Client behavior                                                                                                                                                                                                     |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `open`                     | The request is durably accepted but provider work has not started. Wait and reload the session; do not create a second logical turn.                                                                                |
| `failed_before_provider`   | Retry the exact `retry_request`. Provider work did not start.                                                                                                                                                       |
| `provider_outcome_unknown` | Never retry automatically. Ask the user to acknowledge that the provider may repeat work or incur another charge, then send the exact `retry_request` with `acknowledge_duplicate_provider_spend` set to `true`.    |
| `processing`               | Wait and reload the session. Do not create a second logical turn.                                                                                                                                                   |
| `committed`                | Use the committed conversation, plan state, and typed `latest_turn.error` (when present) returned by the session. A same-key replay returns that exact error and then completes without calling the provider again. |

A typed provider rejection, including a rate limit, is a known rejection. The
server commits its typed error with `provider_disposition=known_rejection`,
`retry_scope=new_turn`, and `another_call_permitted=false`. Replay the same turn
to recover the same error without another provider call. To try provider work
again, create a new turn; do not set duplicate-spend acknowledgement and do not
recall the provider with the rejected turn ID. Rate-limit errors identify
`provider_exception_class=rate_limit` but do not promise a retry delay.

If the protected current turn and latest repair context exceed the selected
model's context window, the server commits
`planner_context_limit_exceeded` before calling the provider. The error uses
`retry_scope=new_turn` and `another_call_permitted=false`; shorten the request
or select a model with a larger context window. A same-key replay returns the
committed error without provider work or duplicate-spend acknowledgement.

Before planning, the Builder reads each message. When that reading's reply
reaches the call's output limit, is empty, or is not in the required format,
the message stays unread and the turn ends with the committed error
`classification_output_limit` or `classification_unreadable_reply`. While a
message is unread, every later turn that reaches planning ends with such an
error, a click on an option included. The error's details name the newest
unread message (`unread_message_id`), why it was not read (`reason`:
`output_limit`, `no_content`, `invalid_reply`, or `unknown` when no reason was
recorded), the call's `output_cap_tokens` for an output limit, and whether it
is an earlier message than the turn's own (`held_turn`). In the session response, an unread user
message carries `reading` with the same reason and a `resend` request: the
message text with its edit or review scope. Send it as a new turn with a new
`client_turn_id`; a reading that receives it whole settles the earlier copy.

Timeouts, connection failures, provider `5xx` responses, and unknown failures are
ambiguous. They leave the turn in `provider_outcome_unknown`; never retry them
automatically. The only same-turn retry path is the exact persisted
`retry_request` with explicit `acknowledge_duplicate_provider_spend=true`.

The deduplication horizon is intentionally bounded to the latest accepted turn
for a session. A different accepted message receives a new `client_turn_id`.
Deleting the session also deletes this recovery record. These guarantees cover
Eneo's local state; provider execution remains at-least-once and may have an
unknown outcome if the connection fails after the provider accepts work.

Handle HTTP `409` by its typed error code. A
`session_turn_idempotency_conflict` means the key was reused with a different
request and must not be retried. A `session_turn_provider_outcome_unknown`
response requires a session reload and the explicit acknowledgement flow above;
never turn it into an automatic transport retry.

## Failure triage

When an operation fails in the AI Builder UI, the frontend automatically reports
the error's stable identity. Operators can group recent failures for triage with
`GET /api/v1/sysadmin/ai-builder/failure-summary/?days=7` and the super API key,
or run `uv run python scripts/ai_builder_failure_summary.py --days 7` from
`backend`. Choose a `days` value from 1 to 90.

## Plan proposal contract

AI Builder plan endpoints return one proposal object. Treat `proposal.spec` as the draft Flow that will be applied after approval. Supporting fields such as `assumptions`, `lint_warnings`, and `plan_rationale` explain why that draft was proposed.

Edit sessions may also include `proposal.edit`. This is the approval metadata for the edit, not a second Flow spec. It contains the base draft revision, the explicit existing step refs that will be removed, the preview diff, warnings, advisories, risk flags, and confidence. Use it to render edit review UI and stale-revision checks.

The `description_override_manual` flag records that the reviewer chose to keep the current Flow description. It applies to create and edit plans.

The public contract is the proposal content plus optional `proposal.edit`; the backend owns compilation, validation, and application details.

## Inputs, outputs, and contracts

AI Builder can propose the same core capabilities used by manually authored Flows:

| Capability         | What it means                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| Runtime input      | The main text, document, audio, file, or structured input for a run                                 |
| Form fields        | Reusable values supplied at run time, such as language, audience, role, date range, or report level |
| JSON output fields | Structured output that later steps or integrations can reuse reliably                               |
| Final artifacts    | User-facing PDF or DOCX output rendered from a prepared body step                                   |
| Step resources     | Knowledge sources attached only where the step needs them                                           |

Prefer explicit form fields when a value will vary per run. Prefer JSON output fields when a downstream step or integration needs stable machine-readable data.

If the flow's input is a JSON export, upload it as a file when the flow runs: the Builder treats an uploaded file as documents. JSON that another system sends in, or that someone pastes into a field, is JSON input. If the Builder is unsure which one you mean, it asks you to choose, with its own reading preselected. Check the input on the requirements card before you apply the plan.

For per-source document readers, every `documents[]` item schema must declare `source_label` and `source_file_id` as required JSON Schema `string` properties. The runtime writes both fields from uploaded file metadata; they are not model output and are removed from model-facing guidance.

For Builder-generated intermediate JSON, field names are stable machine keys and default to canonical English terms. Localized language belongs in descriptions, instructions, and final report text. If a user explicitly requests a public final JSON schema with localized field names, that terminal output contract can use those names, but the Builder should not emit parallel keys such as `summary` and `sammanfattning` for the same source fact.

## Underlag till steget

The Flow editor calls the material a step receives **Underlag** in Swedish and **Material** in English.

That is different from instructions:

| Concept      | Purpose                                                     |
| ------------ | ----------------------------------------------------------- |
| Instructions | Tell the model what to do                                   |
| Material     | Controls the text or structured material the model works on |

AI Builder lets the backend compose material from flow input, form fields, files, and previous outputs instead of asking the language model to write prompt templates. Use advanced material overrides only when the default material assembly is not precise enough.

See <a href="/docs/flows#advanced-step-input-templates-underlag-till-steget">Advanced step input templates</a> for the runtime mental model.

## External data and delivery

When the space has MCP tools that Flows may use, a new Flow's Builder session
first asks whether the Flow should read data with them: yes, no, or show the
tools first. Until you answer yes, the Builder proposes no step that uses a
tool; a no is kept for the rest of the session. A space whose tools are all
unavailable gets no such question. After a yes, the question about what the
Flow receives at runtime also offers "No material – the tools fetch the data":
nothing is uploaded or pasted, and the tools' arguments come from run-form
fields or fixed values. With that answer the summary says that the Flow
receives no material to upload or paste, the Builder adds no field for
material to the run form, and a plan whose first step does not read a tool, or with a step that
reads the run text, its payload or an upload, is sent back to the model to fix.
The option is not offered after a no, before the question about tools is
answered, after you chose no tool for every tool use you were asked about, or
when you edit a saved Flow. If you answer no to the tools, or no tool for every
use, after choosing it, that choice no longer counts and the Builder asks again
what the Flow receives at runtime. A new Flow that fills a DOCX template takes
no step that reads a tool, so with "No material" the Builder answers that this
combination of input and final output is not supported before it plans. A saved
Flow that reads a tool and fills a DOCX template stays editable. AI Builder can then propose a
step that reads the answer of one of the tools. It names the tool and, for each argument,
a fixed value, a field of the run form that the person fills in when starting a
run, or a field that an earlier step's JSON result declares (the earlier step is
counted as the plan lists its steps, so a transcription step the Builder puts
first in an audio Flow is not counted). An argument read from the run form gets
a field of the matching type: a date, a number, text, or a choice from the
tool's allowed values; the field is required when the tool requires the
argument, and an optional one left empty is not sent to the tool. An argument
that names an existing run-form field must spell it as the form does, and that
field must fit the tool (the same type, only values the tool accepts, required
wherever the tool requires it) or the Builder uses another field name. A plan whose first step reads a tool
gets no field for run text; files the run is started with are still read by the
first step. Before showing the plan, the Builder checks each
argument the way publishing does: a required argument without a value, an
argument the tool's input schema neither declares nor takes, or a fixed value
the schema refuses, is sent back to the model to fix.
Before it shows a plan, the Builder asks you which tool a step should use when
another tool of the space would serve the step too, even when your request
names one; the question shows your words that point to a tool, and you can
also choose no tool. It asks where a required argument's value comes from
when the request does not say: a value you give now (or one of the tool's
allowed values), a field of the run form, or a field of the same type that an
earlier step declares. An answer is checked again every time the Builder
proposes: a value the tool's input schema refuses, a run-form field of
another type, or an earlier step's field the plan no longer has is asked
again. Your answers are kept for the session (for the 20 tool uses answered
most recently), also when a later plan leaves the value out; the latest answer
to a question counts. If you choose an option of a tool question, the Builder
keeps the confirmation of the requirements card unless your answer changed the
card; then you confirm the new card. Before the Builder has proposed a plan, a
typed reply to the question still withdraws the confirmation. A plan uses tools at most 20 times, and the Builder
asks for at most 40 values of one tool step; beyond that it tells you to split
the work or to add the step in the step editor.
When the request needs a tool that the space may not use (for example switched
off in the space or waiting for review), or a tool whose input schema is too
large for the Builder to show while it writes the arguments, the Builder says
why instead of proposing a step with another tool. It does not offer a tool
whose MCP server takes a credential at a plain `http` address other than
`localhost`, `127.0.0.1` or `[::1]` either, because the call would send the
credential readable on the network (a flow refuses a call to those loopback
addresses later, through the destination policy); it says that the instance
administrator registers the server's `https` address, without a user name or
password in it. With that answer it shows
the reason and how a tool becomes available in the space, with a link to the
space settings (in a new tab) when you may edit the space; a session reopened
before it has a plan shows them again. The Builder can also answer that it
could not match a specific tool you ask for to a tool it lists for the space,
usable or not. That answer has no plan, so no step uses another tool in its
place; it shows the words the AI Builder took as your request for the tool and
the same steps for making a tool available. It does not say that the tool is
missing, since the list the Builder sees can be shortened to fit the model. In
an edit, the Builder asks before every step that would use a tool the step does not already use. It may
add a step that reads a tool, change the arguments of a saved tool step, or
remove a saved tool step; nothing else of a saved tool step changes, a tool step
the edit does not name stays as saved, and an edit that removes a tool step
another kept step still reads is sent back to the model.
Where you describe the Flow, a note names the space's MCP servers and how many
of their tools a Flow may use; opening it lists each tool with its approved
description. In the proposal, a step that reads a tool shows its server and
tool, and for each argument the fixed value, the run-form field it asks for, or
the earlier step and field it reads.
A plan that fills a DOCX template or only transcribes audio has no tool step.
Otherwise use supported Flow inputs for required data: runtime form or file
input, prior step output, or knowledge.

The Builder proposes only what it can write safely: text, JSON, audio, document,
file, and any-type input from the run, the previous step, or all previous steps,
with text, JSON, PDF, or DOCX output. HTTP GET input and HTTP POST output are
added by hand in the step editor; the Builder does not propose them, and the
platform keeps them as they are. When you ask to name the speakers in a
transcription, the Builder adds the speaker-mapping step itself (the model does
not propose it directly). Image input is not supported.

Standalone assistants and conversations keep their separately owned MCP
behavior.

## Token usage

AI Builder shows token usage for the builder work itself. The total includes planning, proposal generation, and any repair attempts needed to produce a valid plan.

Proposal correction is bounded across all attempts. If a correction does not change the proposed plan or the problem it needs to fix, AI Builder stops that correction path instead of repeatedly sending the same work to the model.

The token meter is for transparency:

- input tokens show what was sent to the model
- output tokens show what the model generated
- the model name shows which model handled the builder call
- an estimated label means the provider did not return exact usage, so Eneo used a local estimate

It is not a billing view. Cost and budget policy stay in the operator and admin surfaces.

## What did not fit in the model's request

When a model request for a turn could not carry everything, the conversation
shows one muted line under your message, for example "Not everything fit in the
model's request: 12 older messages". Select it to see what was left out or
shortened, and when: while your message was read (your earlier messages and
answers) or while the flow was drafted (older messages and confirmed
assumptions). Where the model's context window was the limit, a model with a
larger context window would see more; some limits are fixed by the Builder and
do not depend on the model. The line appears on turns that completed, with or
without an error. A turn that ended without completing (another send took over
the session, the provider outcome is unknown, or the stream failed) shows it
only if it had saved its messages before it ended.

API clients read the same value as `coverage` on the turn's user message in the
session response. The turn's own message stream sends it once in a `coverage`
event before `done`; a replay answered from the stored turn may not, so read
it from the session. Each note has a `kind` (`count`), the `stage`
(`classification` or `proposal`), the `material` (`classification_sources`,
`history_messages`, `requirement_assumptions`), the `total`, how many items
were `omitted` and how many `shortened`, and the `reasons` (`model_room`,
`fixed_limit`). Skip a note whose `kind` or `material` your client does not
know: later releases may add kinds and materials. A turn that left nothing out
has no `coverage` and no event.

## Review checklist

Before approving an AI Builder plan, check:

- the final output type matches the real user need
- runtime fields cover values that change from run to run
- JSON outputs are structured enough for downstream steps
- document or audio inputs are attached to the right step
- each knowledge source is intentional and scoped to the step that needs it
- the final artifact has a clear reader, purpose, and format
- sensitive workflows have the right evidence and retention policy expectations
