# Audit Logging (Technical)

Audit logging is a first-class subsystem in Eneo for security, compliance, and traceability. It records actions across the platform, stores them in PostgreSQL, and exposes controlled access for admins.

For admin-facing guidance, see the [Audit Logging Guide](/guides/audit-logging).

## High-level architecture

Audit events are created through the existing `AuditService`; Flow does not have
a parallel audit subsystem. There are three persistence paths:

1. Configurable events call `log_async`, which applies the audit configuration and
   enqueues an ARQ job for PostgreSQL persistence.
2. Required request-time events call `log(required=True)` in the same database
   transaction as the protected change, or commit the audit before returning
   sensitive data.
3. Run terminal and review transitions insert the existing Flow audit-outbox row
   in the same transaction. Delivery is idempotent and observable; a failed outbox
   insert prevents the transition from committing.

The global feature toggle (`audit_logging_enabled`) and per-tenant category/action
overrides apply only to configurable events. Required Flow events deliberately
bypass those controls.

Audit-log retention is enforced separately by its scheduled purge job. Exports are
generated through `AuditExportService`.

## Flow assurance contract

| Level                    | Canonical examples                                                                                                                           | Failure behavior                                                                                                                                                                                                            |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Required transaction     | Run creation; runtime-file upload/delete; terminal and review transitions; redispatch; run-history policy replacement; package import        | Roll back the protected database transition. Idempotency keys, state compare-and-set, or unique outbox revisions prevent misleading duplicates.                                                                             |
| Required before response | Run input/result detail; active review payloads; evidence/provider-call access and export; template and run-file signed URLs; package export | Return `503` without protected content, bytes, or a signed URL.                                                                                                                                                             |
| Configurable async       | Routine authoring and most Flow setting changes                                                                                              | Apply tenant audit configuration. An ARQ outage does not roll back the completed low-risk change.                                                                                                                           |
| Best-effort operational  | Executed Flow HTTP calls and transcription summary events                                                                                    | Preserve the authoritative runtime records even if the extra admin audit summary fails. Executed HTTP calls use persisted step/attempt or webhook-delivery state; transcription uses required `FlowProviderCalls` evidence. |

Routine status polling and run-history summaries deliberately exclude accepted
input, results, result-file metadata, and usage data, so they are not business
audit events. Retrieving run detail or an active review payload is a required,
fail-closed access event. Side-effect-free package validation/import planning is
also not a business audit event.

The authoring-time **Test HTTP request** action differs from an executed Flow HTTP
step. It makes an external request before emitting a configurable asynchronous
audit event and creates no runtime step, attempt, or webhook-delivery record. If
the audit queue is unavailable, the test result can still be returned and no
durable HTTP evidence is guaranteed. Use executed Flow runs when durable runtime
evidence is required.

The future explicit Flow purge consumes the same required transaction contract.
Its immutable receipt records the requester, reason, eligibility snapshot, eligible
and deleted run counts, deleted bytes, outcome, correlation/idempotency identity,
and receipt id. Saving a retention policy still never performs or schedules a
purge.

## Storage model

Audit logs are stored in PostgreSQL (table `audit_logs`) with structured JSON metadata.

Key fields include:

- `action`, `entity_type`, `entity_id`
- `actor_id` (nullable for system actions or deleted users)
- `description`
- `metadata` (JSONB)
- `outcome`, `timestamp`

Metadata follows a consistent schema via `AuditMetadata` to prevent drift. It stores actor and target snapshots so log entries remain meaningful even if users or entities are renamed or deleted.

## Configuration model

Configuration is layered to allow broad and precise control:

- **Global toggle**: enable/disable all audit logging for the tenant.
- **Category toggles**: enable/disable whole groups (admin actions, user actions, security events, file operations, integration events, system actions, audit access).
- **Action overrides**: enable/disable specific actions within a category.

Changes apply immediately for new audit events; historical logs are not modified.
Required Flow safety events are not configurable and remain enforced when these
controls are disabled.

## Access model and justification

Viewing audit logs requires an access justification session. The access event itself is logged, including:

- reason category
- justification text
- access time and actor

This provides traceability for who accessed audit logs and why.

## Query and search behavior

Audit queries support filters for:

- actor (`actor_id`)
- actions (single or multi-select)
- date range

Free-text search matches the log `description` field. If you want reliable search for a name or identifier, include it in `description` or metadata.

## Retention

### Audit log retention

Audit log retention is tenant-specific. A daily purge job hard-deletes logs older than the configured retention period. This is independent from conversation retention.

### Conversation retention hierarchy

Conversation data (questions and app runs) follows a hierarchical retention policy:

1. Assistant or App `data_retention_days` (if set)
2. Space `data_retention_days`
3. Tenant-level conversation retention (if enabled internally)
4. no effective policy means keep indefinitely

Use assistant/app-level overrides when you need a different period from the Space default. A null child value removes that override and falls back to its parent. The shared daily retention worker removes conversation data after its effective configured period; under the current model this can include Flow AI Builder conversation sessions.

Flow run and step history is separate. Its dedicated Organization → Space → Flow policy never authorizes scheduled deletion and only sets eligibility or a human-review queue. See [Data retention and deletion](/guides/data-retention).

## Export formats

### Synchronous export

Endpoint: `GET /api/v1/audit/logs/export`

- `format=csv` (default)
- `format=json` (JSON Lines/NDJSON)

Synchronous exports are best for small to medium exports.

### Asynchronous export

Endpoint: `POST /api/v1/audit/logs/export`

- `format=csv` or `jsonl`
- status: `GET /api/v1/audit/logs/export/{job_id}/status`
- download: `GET /api/v1/audit/logs/export/{job_id}/download`

Async exports are streamed and resilient for large datasets. Export files are retained for 24 hours before cleanup.

## UI behavior notes

- Free-text search matches the audit log description. Include names or identifiers in descriptions if you want them to be searchable.
- Access to the audit log view is guarded by an access justification session.

## Implementation example

```python
from eneo.audit.domain.audit_metadata_schema import (
    AuditMetadata,
    AuditActor,
    AuditTarget,
    AuditChange,
)
from eneo.audit.domain.action_types import ActionType
from eneo.audit.domain.actor_types import ActorType
from eneo.audit.domain.entity_types import EntityType

metadata = AuditMetadata(
    actor=AuditActor(
        id=str(current_user.id),
        name=current_user.username,
        email=current_user.email,
        type=ActorType.USER.value,
    ),
    target=AuditTarget(id=str(space.id), name=space.name),
    changes={
        "name": AuditChange(old=old_name, new=space.name),
    },
).to_dict()

await audit_service.log_async(
    tenant_id=current_user.tenant_id,
    actor_id=current_user.id,
    actor_type=ActorType.USER,
    action=ActionType.SPACE_UPDATED,
    entity_type=EntityType.SPACE,
    entity_id=space.id,
    description="Updated space name",
    metadata=metadata,
)
```

## Roadmap

We plan to add optional external audit log storage (e.g., SIEM or analytics sink) to reduce long-term load on the primary database while keeping the same access controls and retention guarantees.
