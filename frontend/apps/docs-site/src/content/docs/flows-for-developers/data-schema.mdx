# The data schema

Use this page to understand ownership and invariants before changing Flow
persistence. It is intentionally a hand-maintained map, not a copy of every
SQLAlchemy column. The ORM and Alembic revisions remain authoritative.

## Final migration chain

Flows contributes two linear revisions after the current `develop` head:

1. `202608201000` creates the final core schema.
2. `202608201100` integrates Flow ownership with existing platform tables.

The stacked AI Builder PR adds `202608201200`. It creates only
`builder_sessions`, `builder_plans`, and `builder_session_files` and extends the
resource-binding source vocabulary with `ai_builder`.

Private pre-release revision IDs are unsupported. Existing development
databases must be rebuilt rather than migrated through the deleted history.

## Core aggregates

| Aggregate | Tables | Ownership |
| --- | --- | --- |
| Draft and publication | `flows`, `flow_steps`, `flow_versions`, `flow_template_assets`, `flow_resource_bindings` | Mutable authoring is separated from immutable published snapshots. |
| Execution and evidence | `flow_runs`, `flow_step_results`, `flow_step_attempts`, `flow_step_attempt_resolved_inputs`, `flow_provider_calls` | A run executes one published version. Attempts and provider calls preserve evidence across retries and recovery. |
| Runtime files | `flow_runtime_uploaded_files`, `flow_run_step_input_files`, `flow_run_step_result_files` | File identity remains in the platform `files` table; Flow rows record tenant-scoped use and provenance. |
| Review | `flow_run_review_checkpoints` | Revisioned review state, actor attribution, edited payloads, and resume idempotency. |
| Delivery | `flow_run_audit_outbox`, `flow_run_webhook_deliveries` | Transactional intents are written with lifecycle state and delivered asynchronously. |
| Portability | `flow_package_imports` | Import state for validated `.eneopkg` archives. Imported definitions remain drafts. |
| Shared platform integration | `service_principals`, `provider_token_usages` | Principal and token-usage records shared with non-Flow consumers. |

There are no partial-rerun operation or invalidation tables, no
classification-retention policy tables, and no Flow retention tombstones in the
final schema. Starting again means creating a new run; the attempt ledger remains
because it is required for evidence, provider-call accounting, review, and
terminalization.

## Tenant and actor invariants

- Every tenant-owned Flow query includes `tenant_id`.
- Composite foreign keys pin child rows to the same tenant as their Flow, run,
  checkpoint, file, or service principal.
- A run records exactly one requesting principal shape: user or service
  principal. Review checkpoints apply the same rule to requester and decider.
- Runtime files must belong to the run's tenant and authorized principal before
  they can be bound.
- Builder session-file rows use composite tenant foreign keys on the stacked
  branch; a session cannot attach another tenant's file.

These are database constraints as well as service-layer checks. Do not replace a
composite ownership constraint with an application-only assertion.

## Lifecycle integrity

The schema enforces the invariants that must survive process crashes:

- only one active review checkpoint exists for a run;
- review transitions and resume requests use revision/idempotency keys;
- dispatch fields form a bounded, generation-fenced retry record;
- terminal audit and webhook intents are unique for their lifecycle generation;
- attempt numbers are unique per run and step;
- terminal runs keep their attempt and provider-call evidence until retention
  removes the run.

Repositories add row locking and compare-and-swap behavior around these
constraints. Schema presence tests alone are not sufficient coverage; exercise
the repository transition that depends on the constraint.

## Retention

Run-history retention is a simple effective number of days resolved in this
order:

1. Flow `data_retention_days`
2. Space `data_retention_days`
3. Tenant Flow-run-history default

The first configured value wins. No value means automatic Flow run-history
deletion is off. The shared retention worker selects complete run aggregates in
bounded tenant-scoped batches and respects audit/webhook delivery blockers. It
does not implement preview/confirm governance, classification barriers,
minimum-retention rules, or tombstones.

## JSONB ownership

JSONB columns always have a typed owner. The registry in
`eneo.flows.infrastructure.flow_jsonb_ownership` records the parser, storage
category, schema-version policy, and corruption behavior for each column.

When adding or changing JSONB:

1. define the Pydantic/domain owner first;
2. update the ownership registry;
3. decide whether old rows require a migration or versioned parser;
4. test malformed, old-version, and tenant-boundary behavior;
5. update this map only when ownership or lifecycle meaning changes.
