## OIDC Protocol Flow

Eneo implements the **OAuth 2.0 Authorization Code Flow** with OpenID Connect, PKCE (`S256`) and a `nonce`. Both single-tenant and multi-tenant setups go through the same public endpoints (`/api/v1/auth/initiate` and `/api/v1/auth/callback`). Each sign-in is a one-time transaction in Redis, named by a server-signed state JWT (HS256). The provider contract is summarised in the [OIDC guide](/guides/oidc-federation#provider-contract).

### Flow Steps Explained

<Steps>
### Authorization Request
The frontend calls `GET /api/v1/auth/initiate` (with `?tenant={slug}` in multi-tenant mode). The backend resolves the tenant's IdP configuration and discovery document, computes the `redirect_uri` server-side and starts a [sign-in transaction](#sign-in-transaction) holding a fresh `nonce` and PKCE `code_verifier`. The authorization URL carries:
- `state` - JWT signed with HS256 that names the transaction
- `nonce`
- `code_challenge` (the verifier's SHA-256) with `code_challenge_method=S256`

A client that also sends `binding_challenge`, the S256 hash of a secret it keeps, binds the transaction to itself (see [Public OIDC Endpoints](#public-oidc-endpoints)). The Svelte login always does.

A `correlation_id` (16 hex characters) traces the request. When Redis cannot store the transaction, initiation is refused with `503` (`oidc_login_unavailable`).

### User Authentication
User authenticates with their Identity Provider.

### Authorization Response
IdP redirects to `{origin}/login/callback` with:
- `code` - Authorization code (single-use)
- `state` - Original state JWT for validation
- `iss` - The provider's issuer, when it sends one ([RFC 9207](https://www.rfc-editor.org/rfc/rfc9207))

### Token Exchange
The frontend posts `code`, `state`, `iss` and, for a bound sign-in, `binding_verifier` to `POST /api/v1/auth/callback`. The backend validates the state JWT signature (HS256) and expiry, takes the transaction from Redis exactly once and only for the client that started it, checks that it belongs to the state's tenant, validates the `redirect_uri` and the `iss` parameter, then exchanges the code and the PKCE verifier for tokens at the IdP's token endpoint.

### ID Token Validation
JWT signature verified against the IdP's JWKS with the allowed algorithms, then the claims listed under [ID Token Validation](#id-token-validation). Any failure is refused with `401` (`oidc_response_not_verified`).

### Session Creation
After token validation, both OIDC entry points delegate tenant membership and JIT admission to `UserService.resolve_federated_user`. It checks the configured domain restriction, tenant and account state, and the additional JIT requirements below before an Eneo session JWT is issued.
</Steps>

## Security Mechanisms

### Eneo Session Identity

Eneo-issued browser, internal MCP and module tokens share one identity contract:

| Claim | Meaning |
|-------|---------|
| `token_version` | Required value `2`; older session formats are rejected |
| `user_id` | Immutable UUID of the authenticated Eneo account |
| `tenant_id` | UUID of the account's organization when the token was issued |
| `credential_version` | Required integer matching the account's current credential version |
| `auth_method` | `password` when the session started with the local password login; absent for federated and exchanged sessions |
| `iss`, `aud`, `iat`, `exp` | Required issuer, audience, issue time and expiry |
| `sub`, `username` | Email and optional display name; never used to select the account |

After signature, issuer, audience and time validation, the backend resolves the
account by **both** `user_id` and `tenant_id`. Deleted accounts and mismatched
identity claims cannot authenticate. Account and tenant state checks and normal
resource permissions still apply. A name or email change cannot transfer an
existing session to another account, including one with the same username.

The identity contract belongs to Eneo session tokens. Identity-provider tokens
are validated separately during OIDC login and exchanged for an Eneo session.

#### Server-side sessions

Every password sign-in and every OIDC sign-in through `POST /api/v1/auth/callback`,
in the Svelte app and in the Vite app, starts one server-side session in
PostgreSQL. The token it hands out names that session (`sid`), and it
authenticates, as the cookie or as Bearer, only while the session exists.

- **Sign-out** ends the session, so every copy of the token stops working at
  once. When the end cannot be confirmed within 5 seconds, sign-out answers
  503 and clears nothing: the session may already have ended, or may still
  work, and trying again completes the sign-out. It does not end the identity
  provider's session.
- **Live updates** stop with the session. The job-event stream
  (`GET /api/v1/jobs/events/`) and the `/ws` socket check their session at
  most 30 seconds apart while they are open, and end at the token's expiry.
  After sign-out, a password change, signing out everywhere or the account's
  deactivation they close at the next check; the socket closes with code 1008
  and the client does not reconnect with that token.
- **Expired sessions** admit nothing; a nightly job deletes them.
- **No session**: provider access tokens, API keys, system tokens, internal
  MCP and module tokens, and the provider-bound MobilityGuard login. They work
  as before, and sign-out does not affect them.

An API client that signs in with `POST /api/v1/users/login/token/` holds a
session token as well. `POST /api/v1/users/logout/`, with that token as
Bearer, ends its session. The route reads only the `Authorization` header,
never a cookie.

| Answer | Meaning |
|--------|---------|
| `204` | No session remains that this token can use: its session has ended, or it named none to end (no or an invalid token, a token without a session such as one issued before sessions, a provider token, or a token expired for longer than it was valid). A token without a session is not revoked and works until it expires. A token expired for less than that still ends its session |
| `503` `sign_out_unavailable` | The end is not confirmed: the session may already have ended, or the token may still work. Keep the token and retry; once the session has ended, a retry answers `204` |

#### Backend browser sessions

The backend-served web app remains disabled by default. With
`BROWSER_SESSION_ENABLED`, an authenticated cookie response includes
`Eneo-Session-Generation`, a fingerprint of the selected session: of its
server-side session id for a browser sign-in, which staying signed in keeps, and
of the credential itself otherwise. It is neither an authentication credential
nor a CSRF token.

A document must remember its initial generation and send it on subsequent
cookie-authenticated requests. Only GET and HEAD may omit it for bootstrap;
a supplied mismatch on any method returns HTTP 401 with `eneo_error_code: 9090`
before authentication or domain work. Cookie writes without the header are
also refused. This prevents a tab from acting as another account after a
different tab replaces the shared cookie. Bearer and API-key authentication
retain their existing precedence and do not use this check.

Password and federation login establish a new session and must end with a new
document. Logout requires the expected generation whenever a session cookie
is present, including an expired cookie; without a cookie it still returns 204
and clears any remaining authentication cookies.
A document must never adopt a replacement generation to retry a refused write.

Logout (`POST /api/v1/auth/session/logout/`) ends the
[server-side session](#server-side-sessions) before it clears the cookie, so a
copy of the cookie stops working at once; when that cannot be confirmed, it
returns 503 and keeps the cookie for a retry. Requests admitted before logout
may finish. A password change still ends every session of the user.

The Vite transport binds the document through `GET /api/v1/auth/session/`
before rendering. Typed requests, raw fetches, job events and uploads share
that binding. Resuming a hidden or cached page checks the session before more
authenticated work. A changed session aborts active work, clears cached data
and requests a new document; if the user cancels navigation, a blocking screen
offers an explicit reload. A temporary network failure preserves the binding
and unsaved form state, blocking new requests until a session check succeeds.
Signed downloads use their resource token instead of adopting the current cookie.

The session check also answers `Eneo-Session-Expires-In`, the whole seconds the
session has left, and `Eneo-Session-Lifetime`, the whole seconds its token was
issued for. Two minutes before the end (half the lifetime for a session shorter
than four minutes, never less than 20 seconds) the web app asks whether to stay
signed in. `POST /api/v1/auth/session/extend/`, sent from the site's own page
with the current generation, renews the same session: the cookie gets a new
token with the same `sid`, user, organisation and sign-in method, valid for
`JWT_EXPIRY_TIME` again. The body answers the generation, which a renewal keeps
because it is derived from the `sid`, and the seconds the new token has left;
the token stays in the cookie. The server-side session now ends with the new
token, and a renewal recorded after a later one never moves that end earlier.
Each renewal writes a `session_extended` audit entry. The token carries the
original sign-in time (`auth_time`), so renewal never reaches past
`BROWSER_SESSION_MAX_AGE` (by default 30 days) after sign-in. Bearer tokens and API keys cannot renew a session. Other open tabs of
the same session follow the new end through a `BroadcastChannel` message that
carries only the generation and that end (`{generation, expiresAt}`). A lost
renewal answer is harmless: the cookie still names the same session, so the
page keeps working and can renew again, and a tab that misses the message
learns the new end at its next session check. Because the session stays the
same, logout with the token a renewal replaced still ends it, provided that
token expired no longer ago than it was valid for.

The retained Next frontend does not use this transport. The Vite route migration
must still be completed before enabling the backend-served app in production.

#### Deploying the identity contract

The transition requires users to sign in again. Pre-upgrade Eneo and module
tokens, and pending module login tickets, are rejected; there is no fallback to
username or email authentication. Module applications must restart the login
handoff on an authentication failure.

Update all API instances and workers together, draining old instances before
serving traffic with the new deployment. Old instances still resolve sessions
by username and must not remain in a rolling deployment. No account rename,
account merge or database migration is needed for this change. A recovery build
must retain the identity validation; rolling back to username-based
authentication reintroduces the vulnerability.

### Local Password Lifecycle

Accounts that sign in with a password stored in Eneo follow the tenant's
password lifecycle policy. The decision is owned by one module,
`eneo/users/password_lifecycle.py`; the admission gate in
`authentication/endpoint_access.py` and the `password_status` field of
`GET /api/v1/users/me/` both call it, so they cannot disagree.

Only a session whose `auth_method` claim is `password` is ever affected.
A session that signed in through an identity provider, a module token, an
internal MCP token or an API key carries no such claim and is never blocked,
even when the account also keeps an older local password. Accounts
provisioned through OIDC or SCIM have no local password at all.

A password set by someone other than the account (generated in
**Admin → Users**, set through the sysadmin API, or the `DEFAULT_USER_PASSWORD`
seed) is always a one-time password: the account must choose its own at its
next password sign-in. This is not a tenant setting. Only two deployment-level
exceptions keep a set password usable: the sysadmin API's
`password_change_required: false` (for service accounts) and
`DEFAULT_USER_PASSWORD_CHANGE_REQUIRED=false` for the seed (for test stacks).
Neither exempts the password from `max_age_days`.

| Rule | Default | Effect |
|------|---------|--------|
| `max_age_days` | unset | A local password must be replaced after this many days. The age counts from the last change; passwords that existed before the lifecycle was introduced count from that upgrade. |

Administrators edit the policy under **Admin → Users → Password policy**
(`GET`/`PATCH /api/v1/admin/password-policy`).

Administrators never type a password in **Admin → Users**. Creating an
account, or choosing **Generate a new password** for an existing one, has the
browser generate a random password that meets the local password policy from
`GET /api/v1/users/password-policy/`, so a change to that policy needs no change
in the frontend. The password is shown once after saving, for the administrator
to hand over.

API-key integrations are unaffected by this policy and by local password
changes; their existing key permissions, expiry and revocation rules still
apply. An integration that obtains a bearer token through the password login
is subject to the policy and may receive `403/9070`. For unattended use,
prefer a service-owned API key with the permissions and scopes the integration
needs, provided its endpoints support service identities.

A password session that must replace its password still signs in, so the
account can do exactly that. Every other endpoint answers `403` with error
code `9070` (`password_change_required`) until the password has been replaced
through `POST /api/v1/users/me/password/`, which stays reachable together with
`GET /api/v1/users/me/`, the password policy and session invalidation.
`GET /api/v1/users/me/` reports the state as `password_status`:
`change_required` (true only when the current session is blocked), the
`reason` (`admin_set` or `expired`), `changed_at` and `expires_at`. The web
app sends such a session to `/password-change`, where the user enters the
one-time or expired password as the current password. The change bumps the
credential version, so the user signs in again with the new password.

Two deliberate exceptions: an administrator who sets a new password on their
own row in **Admin → Users** keeps it, because the account chose it; and the
deployment administrator's `POST /api/v1/sysadmin/users/{id}/access-token/`
mints a session without the claim, so support access is never blocked by a
pending change. After upgrading to this version, passwords that already
exist, including an already seeded administrator's, are stamped with the
upgrade time and stay usable; every password an administrator sets from then
on is one-time. On a fresh installation the seeded password is one-time. Existing sessions and deployments that still issue tokens without
the claim keep working during a rolling upgrade.

### Signed State Token

The `state` parameter is a JWT signed with HS256 that names the sign-in transaction. It carries `tenant_id`, `tenant_slug`, `frontend_state`, `transaction_id`, `correlation_id`, `iat` and `exp`; the nonce and the PKCE verifier are never in it.

**Key parameters:**
| Parameter | Value | Source |
|-----------|-------|--------|
| Algorithm | HS256 | `federation_router.py` |
| Signing key | `JWT_SECRET` | `config.py` |
| TTL | 600 seconds (10 minutes) | `oidc_state_ttl_seconds` |
| Correlation ID | 16 hex chars (8 bytes) | `secrets.token_hex(8)` |

An expired state is rejected with `400 Authorization session expired. Please try logging in again.`; a state that fails signature validation, or one issued by a version without sign-in transactions, is rejected with `400 Invalid state parameter`.

### Browser Login Binding

Generic OIDC login also requires a browser-bound attempt. Starting authentication
through the `/login` page's `oidc` POST action creates a random attempt ID and a
binding verifier (32 random bytes). It passes the attempt ID as `frontend_state`
and the verifier's S256 hash as `binding_challenge` to the backend. After
successful initiation, the action stores both in the HttpOnly `oidc-login-resume`
cookie, even when no `next` destination was requested. Its expiry follows the backend-signed state's
`exp`: the default is 10 minutes from initiation, rather than from opening the
login page. The cookie uses `Path=/`, `SameSite=Lax`, and `Secure` outside
development. Single-tenant automatic login, tenant selection, and retries use
this same action so each starts a fresh attempt.

Both `/login/callback` and its `/auth/callback` alias require a matching, unexpired
attempt before exchanging the authorization code or writing a session cookie.
A missing, malformed, expired, or mismatched attempt returns the user to login
with `oidc_attempt_rejected`, which asks them to start the sign-in again;
`oidc_invalid_request` remains the identity provider's own error. A matched
attempt is consumed, so a later callback without that cookie cannot exchange
another code. The backend still verifies the state signature; reading its
frontend payload for browser correlation does not replace that verification.

The attempt ID travels in the state, which anyone who sees the callback URL can
read, so it only tells tabs apart. The verifier stays in the cookie and the Svelte
server: the callback sends it as `binding_verifier`, and the backend redeems the
code only with it. A leaked code and state therefore cannot be finished in another
browser or by calling the API directly.

The optional local `next` destination is separate from the required binding.
Unsafe or oversized destinations are omitted from the cookie without allowing
an unbound login. Module handoff destinations retain their original encoding.

The cookie is host-only: start login on the same public origin as the configured
callback. Login started on an alternate hostname cannot finish on the canonical
hostname. Only the latest authentication attempt started in a browser is stored.
An older tab's mismatched callback and its error-page redirect preserve the newer
binding. Viewing the login page and a failed initiation do not replace an attempt;
starting authentication again does. After deploying this change, attempts started
with an older cookie format must restart login.

The legacy Zitadel flow continues to use its existing local PKCE verifier
cookie and sends no nonce. It is deprecated and is removed in the next release;
see [Migrate from the Zitadel settings](/guides/oidc-federation#migrate-from-the-zitadel-settings).

### Sign-in Transaction

`authentication/oidc/transaction.py` stores each sign-in in Redis under `oidc:transaction:{id}` for `oidc_state_ttl_seconds`. It holds the `nonce`, the PKCE `code_verifier`, the `redirect_uri`, the tenant and its config version, the provider's issuer and whether its discovery announced the `iss` parameter, the time the sign-in started, the channel that started it and, for a bound sign-in, the hash of the client's binding secret. The browser and the provider never see the verifier. The callback checks the `iss` parameter and the ID token's `iss` against the stored issuer, so a config or discovery change during a sign-in does not change what it accepts. If the provider's issuer has changed since, the callback refuses before the token exchange.

There are two channels. `POST /api/v1/auth/callback` answers with a bearer token. The Vite web app's server-side sign-in (`GET /api/v1/auth/browser/initiate`) answers with an HttpOnly session cookie: it always binds the transaction to its transaction cookie, and only its own callback redeems it.

The callback first reads the transaction and checks the channel and the binding secret, comparing hashes in constant time. Only then does it take the transaction with `GETDEL`, so exactly one callback can use it. A channel or binding refusal removes nothing, so whoever holds a leaked code and state cannot use up a bound sign-in either:

| Situation | Behaviour |
|-----------|-----------|
| Transaction present | Taken and removed; its tenant must match the state's, otherwise `400 Authorization state mismatch detected. Please restart the sign-in flow.` |
| Started on the other channel; bound, but `binding_verifier` is missing or wrong; or unbound, but a `binding_verifier` was sent | `400` `oidc_transaction_invalid`. The transaction stays, so the client that started the sign-in can still finish it |
| Transaction missing or unreadable (expired, already used, Redis restarted, or stored by a version without the sign-in binding), or the provider's issuer changed since the sign-in started | `400` `oidc_transaction_invalid`: "Authorization session is invalid or has expired. Please restart the sign-in flow." |
| Redis unavailable, or no answer within 2 seconds | `503` `oidc_login_unavailable` at initiation or callback. The callback is refused and nothing writes the transaction back, so the sign-in must be started again |

A state from a version without sign-in transactions is refused earlier with `400 Invalid state parameter`. None of these refusals writes a session or a user row.

### Redirect URI Grace Period

When tenant federation configuration changes (e.g., updating `canonical_public_origin`), users mid-authentication could encounter redirect URI mismatches. The grace period mechanism prevents failed logins during configuration updates.

**How it works:** `_require_registered_redirect_uri` in `federation_router.py` checks the stored `redirect_uri`, and `_changed_during_sign_in` decides whether the grace period applies. The grace period is the smaller of `oidc_redirect_grace_period_seconds` and `oidc_state_ttl_seconds`.

The `redirect_uri` stored in the transaction is first checked for well-formedness and then compared with the tenant's currently configured redirect URIs (canonical plus `additional_redirect_uris`). On a mismatch:

- **`strict_oidc_redirect_validation = false`**: any well-formed `redirect_uri` from the transaction is accepted.
- **`strict_oidc_redirect_validation = true`** (default): the old `redirect_uri` is accepted only if **all** of the following hold:

| Condition | Check |
|-----------|-------|
| Config version changed | `current_config_version != state_config_version` |
| Grace period configured | `grace_period > 0` |
| State issued within grace period | `seconds_since_issue <= grace_period` |
| Config updated within grace period | `seconds_since_update <= grace_period` |
| Config changed after state issued | `tenant_updated_at > state_config_dt` |

Otherwise the callback fails with `400 Redirect URI mismatch - authentication flow invalid. This may occur if tenant configuration changed during login. …`.

<Callout type="info">
  The grace period defaults to 15 minutes but is capped at the state TTL (10 minutes), effectively making it 10 minutes maximum. The backend logs a warning at startup when `OIDC_REDIRECT_GRACE_PERIOD_SECONDS` exceeds `OIDC_STATE_TTL_SECONDS`.
</Callout>

### Token Auth Method Selection

At sign-in, `_token_auth_method` in `authentication/oidc/profile.py` selects the token endpoint authentication method. When a federation config is saved, `_select_token_auth_method` in `tenants/tenant_federation_service.py` stores one from discovery.

**Selection priority:**

| Priority | Method | Description |
|----------|--------|-------------|
| 1 | Explicit config | `token_endpoint_auth_method` in federation config |
| 2 | `client_secret_post` | Credentials in request body |
| 3 | `client_secret_basic` | HTTP Basic Authentication header |
| 4 | First supported | First method from discovery |
| 5 | Default | Falls back to `client_secret_post` |

Any other method selected from discovery is logged as unsupported and replaced by `client_secret_post`.

### Tenant State Validation

Authentication is blocked for non-active tenants at both initiate and callback stages. Both return `403 Forbidden`:

| Stage | Response detail |
|-------|-----------------|
| `GET /auth/initiate` | `Tenant '{slug}' is not active. Contact your administrator.` |
| `POST /auth/callback` | `Tenant is not active. Contact your administrator.` |

| Tenant State | Authentication Allowed |
|--------------|------------------------|
| `active` | Yes |
| `suspended` | No |

<Callout type="warning">
  If a tenant becomes suspended during a user's authentication flow, the callback will fail even if initiate succeeded.
</Callout>

### Tenant Resolution

When federation is enabled (`FEDERATION_ENABLED=true`) and more than one active tenant exists, the login page has to know which tenant's IdP to use. Eneo does **not** derive the tenant from the hostname; the frontend resolves it in this order:

| Priority | Method | Description |
|----------|--------|-------------|
| 1 | `?tenant={slug}` query parameter | `https://eneo.example.com/login?tenant=sundsvall` starts the flow for that tenant directly |
| 2 | Remembered slug | The last used slug is stored in `sessionStorage` (`eneo-last-tenant-slug`) and stays the active tenant within the browser session: the selector is skipped and the sign-in form is shown with a **Choose another organisation** link. It does not start the IdP redirect by itself |
| 3 | Tenant selector | `GET /api/v1/auth/tenants` lists tenants; the user picks one. When exactly one tenant is returned it is selected automatically |

Slugs must match `^[a-z0-9-]+$`. The selector lists every **active tenant that has a slug**, regardless of whether federation is configured for it; a tenant without an IdP fails at `/auth/initiate` with `500 No identity provider configured for tenant '{slug}'`.

On the backend, `GET /api/v1/auth/initiate` without a `tenant` parameter auto-selects the tenant when exactly one active tenant exists and otherwise returns `400 Tenant parameter required when multiple tenants exist`.

### Federation Config Storage

Federation config is stored in the `federation_config` JSONB column of the `tenants` table. `PUT …/federation` fetches the discovery document immediately and stores the resolved endpoints alongside the request fields:

| Key | Source | Notes |
|-----|--------|-------|
| `provider` | request | Identity provider label (`entra_id`, `mobilityguard`, …) |
| `discovery_endpoint` | request | OIDC discovery URL |
| `client_id` | request | OAuth client ID |
| `client_secret` | request | Encrypted with Fernet before storage |
| `allowed_domains` | request | Email domain allowlist (lower-cased) |
| `canonical_public_origin` | request (optional) | Tenant's access URL, falls back to `PUBLIC_ORIGIN` |
| `redirect_path` | request (optional) | Defaults to `/login/callback` |
| `additional_redirect_uris` | request (optional) | Extra fully-qualified redirect URIs accepted at callback |
| `signing_algorithms` | request (optional) | ID token algorithms to accept; default from discovery, else `RS256` |
| `email_verified_claims` | request (optional) | Claims that say the email is verified, in order; default `["email_verified", "xms_edov"]` |
| `issuer`, `authorization_endpoint`, `token_endpoint`, `userinfo_endpoint`, `jwks_uri` | discovery | Resolved at PUT/PATCH time |
| `token_endpoint_auth_method`, `token_endpoint_auth_methods_supported` | discovery | See [Token Auth Method Selection](#token-auth-method-selection) |
| `scopes` | default | `["openid", "email", "profile"]` (not configurable via the API) |
| `claims_mapping` | default | `{"email": "email", "subject": "sub", "username": "sub", "name": "name"}`; only `subject` is configurable, as `subject_claim` on `PUT`, `PATCH` and the administrators' `PATCH /api/v1/admin/federation`; `email` and `subject` are read at login |
| `encrypted_at` | server | Timestamp of the last secret encryption |

A `PATCH` that sets `canonical_public_origin`, `redirect_path`, `additional_redirect_uris`, `signing_algorithms` or `email_verified_claims` to `null` removes the key, which restores its default. A `GET` returns `null` for a key that is not stored.

### Secret Encryption

Client secrets are encrypted using **Fernet** (AES-128-CBC + HMAC-SHA256):

| Aspect | Details |
|--------|---------|
| Algorithm | Fernet |
| Env Variable | `ENCRYPTION_KEY` |
| Key Format | Base64-encoded Fernet key |
| Encrypted Format | `enc:fernet:v1:<ciphertext>` |

**Key generation:**
```bash
uv run python -m eneo.cli.generate_encryption_key
```

<Callout type="warning">
  `ENCRYPTION_KEY` is required when `FEDERATION_ENABLED=true`; the backend refuses to start without a valid key. Back up securely - loss means re-registering all tenant IdPs.
</Callout>

## ID Token Validation

### Claims Validated

`authentication/oidc/verification.py` owns the response check; `FederatedIdentity` owns the validated email identity. Every failure is refused with `401` (`oidc_response_not_verified`) and logged as `oidc_response_refused` with a reason, never with the token:

| Claim | Validated? | Details |
|-------|------------|---------|
| `alg` | **Yes** | One of the provider's [allowed algorithms](/guides/oidc-federation#provider-contract); `none` and symmetric algorithms never |
| `iss` | **Yes** | Required; must equal the provider's issuer (the stored `issuer`, else discovery's) |
| `aud` | **Yes** | Required; must contain `client_id` |
| `azp` | Conditional | When present, must equal `client_id`; required when `aud` names several clients |
| `exp` | **Yes** | Required; automatic PyJWT validation |
| `iat` | **Yes** | Required; a token issued more than the clock leeway in the future is rejected as not yet valid |
| `sub` | **Yes** | Required; a configured subject claim (`claims_mapping.subject`) is required as well |
| `nonce` | **Yes** | Must equal the transaction's nonce |
| `auth_time` | Conditional | When present, a number not in the future |
| `acr`, `amr` | Conditional | When present, text and a list of text |
| `at_hash` | Conditional | If present, must match access token hash |
| `email_verified` | Conditional | For the standard `email`, explicit `false` rejects login before account lookup when this claim decides; omission is allowed for existing active members, while JIT requires `true` |
| `xms_edov` | Conditional | Entra ID's "email domain owner verified" claim; a positive value verifies the standard `email` for JIT when `email_verified` is absent |

The verification claims and their order come from the provider's `email_verified_claims` (default `["email_verified", "xms_edov"]`); the first one present decides. A claim left out of that list decides nothing, `email_verified` included.

**Clock skew tolerance:** 120 seconds (2 minutes) - configurable via `oidc_clock_leeway_seconds`

### User Claims Extracted

Two claims are used: the email claim (`claims_mapping.email`, default `email`) and the subject claim (`claims_mapping.subject`, default `sub`). The issuer, the audience, the subject claim's name and its value select the account the identity is bound to; see [Account Binding](/guides/oidc-federation#account-binding).

A missing claim is rejected with `401 Email claim not found in ID token`; a malformed address with `401 Email claim from identity provider is invalid. Contact your administrator.`

When `email_verified` is the claim that decides, an explicit boolean `false` for the standard `email` claim is rejected before account lookup or JIT provisioning. The federation callback returns `401 Email is not verified by the identity provider`. A missing flag remains accepted for existing active members when enterprise IdPs issue administrator-controlled directory addresses without this claim. JIT creation still requires verified email, as described below.

The email binds an account to an identity on its first sign-in, so the configured IdP must control who can claim that address. If `claims_mapping.email` uses a different claim, such as `upn`, the standard `email_verified` flag does not describe that claim and is not applied to it. Administrators must choose a claim controlled by their organization's directory.

### Domain Validation

When `allowed_domains` is configured, email domains are compared case-insensitively using IDNA2008. Unicode and punycode forms of the same domain match; distinct domains such as `faß.de` and `fass.de` do not. A non-matching domain is rejected with:

```
403 Email domain '{domain}' is not allowed for this organization. Contact your administrator to add your domain.
```

Global OIDC uses `OIDC_ALLOWED_DOMAINS` (JSON array, default `[]`); per-tenant federation uses `allowed_domains`. An empty list leaves existing active tenant members unrestricted by domain, but cannot admit new members through JIT. The federation callback records admission refusals as `callback.user_denied` with a reason.

### JIT Provisioning

`UserService.resolve_federated_user` is the single admission owner for every OIDC sign-in, with per-tenant federation or the global `OIDC_*` settings. It signs in to the account the identity is bound to, binds an active account in the configured tenant found by email when it has no binding yet, rejects inactive accounts and cross-tenant matches, and checks for removed rows before considering account creation. The removed-account lookup is tenant-scoped and tests for existence because several historical rows can share an email.

| Account state | Result |
|---|---|
| Existing active member of the tenant | Sign in, subject to any configured domain restriction and to [account binding](/guides/oidc-federation#account-binding) (`403` `identity_conflict` otherwise). No new email-verification requirement is applied. |
| Existing account in another tenant, or inactive/removed account | `403`; no account creation or reactivation. |
| No account, `tenant.provisioning: false` (default) | `403`; provision through SCIM or administration. |
| No account, `tenant.provisioning: true` | Creation requires a non-empty domain allowlist, a matching domain and the ID token's `email_verified: true` for the selected address. |

`FederatedIdentity.from_claims` receives validated token claims and preserves only a valid email address and its verification status. OIDC defines `email_verified` as a boolean; as a compatibility deviation for IdPs that can only emit text claims, the strings `"true"` (case-insensitive) and `"1"` and the number `1` also count as verification. Microsoft Entra ID omits `email_verified` for organisational accounts and can emit `xms_edov` (email domain owner verified) instead; when the token carries no `email_verified` at all, a positive `xms_edov`, in the same forms, verifies the standard `email` instead, because the mandatory domain allowlist already restricts which domains may be admitted. `xms_edov` is only that fallback: any `email_verified` value the IdP does send keeps its own verdict, so a negative or unrecognised value is never overridden, and an explicit boolean `false` still rejects the login. Missing claims and all other values do not verify. When email is selected through a custom claims mapping, neither claim authorizes JIT unless the selected address equals the standard `email` claim.

Provisioning is a per-tenant flag set through the sysadmin API (`POST /api/v1/sysadmin/tenants/{id}/`). Keep it `false` when SCIM manages membership. A SCIM token does not implicitly change this setting. SCIM or an administrator can restore an account; login cannot.

New accounts use `state=ACTIVE`, the email local part as username (falling back to the full email, then no username, on collisions), and the tenant's default role. Without a default role they have no roles and a warning is logged. Creation writes `USER_CREATED` with actor `SYSTEM` and `provisioning_method: jit_federation`; audit-log failure does not prevent account creation.

## JWKS Handling

The signing key is looked up by the token's `kid` among the signing keys in the provider's JWKS (`use` is `sig` or absent; a key marked `enc` is never used). The key set is cached per `jwks_uri`, shared by every issuer that uses that address, for `oidc_jwks_cache_ttl_seconds` (default one hour) and fetched again, at a limited rate, when a token names an unknown `kid`. The discovery document is cached per URL for the same time, and concurrent sign-ins share one fetch. When it cannot be fetched, sign-in fails rather than falling back to stored values, and the URL is tried again at most every 30 seconds.

A JWKS fetch or key lookup failure is reported as `401 Failed to validate ID token signature`.

## Federation Admin API

### Endpoints

All paths are relative to `/api/v1/sysadmin` and return `404 Federation is not enabled` unless `FEDERATION_ENABLED=true`.

| Method | Path | Description |
|--------|------|-------------|
| `PUT` | `/tenants/{tenant_id}/federation` | Provide a complete config (replaces the current one) |
| `PATCH` | `/tenants/{tenant_id}/federation` | Update individual fields of an existing config |
| `GET` | `/tenants/{tenant_id}/federation` | View config (secrets masked) |
| `DELETE` | `/tenants/{tenant_id}/federation` | Remove config |
| `POST` | `/tenants/{tenant_id}/federation/test` | Test IdP discovery endpoint |

**Authentication:** `X-API-Key` header with the super admin API key (`ENEO_SUPER_API_KEY`).

`PUT` and `PATCH` (when `discovery_endpoint` changes) fetch the discovery document before saving and fail with `400` if it is unreachable or lacks `issuer`, `authorization_endpoint`, `token_endpoint` or `jwks_uri`. Every change writes a `FEDERATION_UPDATED` audit event.

### Test Endpoint Behavior

`POST /tenants/{tenant_id}/federation/test` performs:

- Fetches the discovery document from the stored `discovery_endpoint`
- Validates HTTP 200 response
- Verifies required OIDC fields are present (`issuer`, `authorization_endpoint`, `token_endpoint`, `jwks_uri`)
- Returns `{"success": true, "message": "Federation config is valid and IdP is reachable", "issuer": "…"}`
- Does NOT fetch the JWKS
- Does NOT attempt authentication
- Does NOT validate client credentials

Failures are reported as `500` with the reason in `detail` (HTTP status from the IdP, missing fields, or connection error).

## Observability

### Correlation IDs

Generated with `secrets.token_hex(8)` → 16 hex characters.

- Created in `/auth/initiate`
- Embedded in state JWT
- Reused in `/auth/callback`
- Included in all log entries and returned as the `X-Correlation-ID` header on callback errors

### OIDC Debug Events

Enable debug logging via the observability API (`POST /api/v1/sysadmin/observability/oidc-debug/`). Events follow pattern `[OIDC DEBUG] {event}`:

**Initiate phase:**
- `initiate.authorization_ready`

**Callback phase:**
- `callback.state_decoded`
- `callback.email_extracted`
- `callback.user_denied`
- `callback.jit_provisioning`
- `callback.success`
- `callback.unexpected_error`

A refused or failed sign-in is logged whether or not debug logging is on: `oidc_transaction_refused` and `oidc_response_refused` name the check that refused it, and `oidc_transaction_store_failed` means Redis is missing or failing.

## Public OIDC Endpoints

These endpoints do NOT require authentication:

| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/api/v1/auth/federation-status` | Tells the login page which mode is active (`has_single_tenant_federation`, `has_multi_tenant_federation`, `has_global_oidc_config`, `tenant_count`) |
| `GET` | `/api/v1/auth/tenants` | List active tenants with a slug for the selector |
| `GET` | `/api/v1/auth/initiate` | Initiate OIDC authentication (`tenant`, `state`, optional `redirect_uri` and `binding_challenge` query parameters) |
| `POST` | `/api/v1/auth/callback` | Handle OIDC callback (`code`, `state`, optional `iss` and `binding_verifier`) and issue the Eneo session token |

`/auth/initiate` and `/auth/callback` refuse with a typed code in the error body:

| Status | `code` | `eneo_error_code` | Meaning |
|--------|--------|-------------------|---------|
| `503` | `oidc_login_unavailable` | `9077` | Redis could not store or return the sign-in transaction |
| `400` | `oidc_transaction_invalid` | `9078` | The sign-in transaction is missing, used, started by another client or no longer fits the provider |
| `401` | `oidc_response_not_verified` | `9079` | The provider's response failed a check of the provider contract |

Other refusals are plain `400` answers without a code: `Invalid state parameter`, `Authorization session expired. Please try logging in again.`, `Authorization state mismatch detected. Please restart the sign-in flow.` and the redirect URI mismatch.

**Clients that call the API directly**, such as eneo-js, should bind each sign-in:

1. Create a verifier from at least 32 random bytes, encoded as 43 to 128 characters of `A-Z`, `a-z`, `0-9`, `-`, `.`, `_` and `~` (like a PKCE verifier, [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636#section-4.1)). Keep it out of URLs and logs.
2. Send `binding_challenge`, the unpadded base64url SHA-256 of the verifier, to `/initiate`.
3. Send the verifier as `binding_verifier` to `/callback`.

A bound sign-in is redeemed only with its verifier. An unbound one works as before and refuses a `binding_verifier`. Binding adds only the verifier: the callback's other requirements stay, including forwarding the provider's `iss` when it sends one. A malformed value is refused with `422`. `code_verifier` is still accepted and ignored.
