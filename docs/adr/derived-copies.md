# Copies of another conversation's content

- **Status:** Proposed; accepted when this record merges to `develop`
- **Date:** 2026-11-08
- **Decision owners:** Product and architecture
- **Scope:** How Eneo knows that a conversation holds content copied from
  another one, what a read of such a copy does once its source is removed, and
  how the copy is then removed. Builds on
  [Retention levels and rules](retention-levels-and-rules.md) and
  [One retention engine](retention-engine.md).

## Context

A feature can store content read from another conversation: a summary, a
continued conversation, a quoted answer. Removing the source must not leave
its content readable in the copy. That has to hold at the moment the removal
commits, also when the retention task is switched off or has not run yet, and
whichever path removed the source: a user, the deletion of its Assistant, or
retention. No feature in this release stores copies yet; this record fixes the
contract the first one meets.

## Decision

### One edge per copied question, ids only

`content_derivations` holds `copy_session_id` and `source_question_id`,
unique on `(copy_session_id, source_question_id)`, with no foreign keys. One
installation is one organisation, so an edge needs nothing else. No deletion
path writes to it, so removing a question or a
session costs nothing extra and needs no cascade budget. Question and session
ids are generated by the database and never supplied by a caller or reused: a
dangling edge stays dangling, and a new session cannot adopt an old edge.

### The producer contract

`eneo.data_retention.derivations` is the one port. Before copied content
leaves a producer, it calls `register_derivations` with the copy session and
every source question. Registration runs in its own short transaction, holds
the copy session `FOR KEY SHARE` and returns only once it committed. Any
failure, an unknown commit outcome included, raises
`DerivationRegistrationError`, and the producer returns no
copied content. A source removed before registration commits leaves a
dangling edge, which makes the copy invalid at once.

Each producer is listed in `KNOWN_COPY_PRODUCERS`. A test proves that each
listed function registers, and that every function calling
`register_derivations` is listed.

### Reads refuse an invalid copy in the same statement

A copy is invalid once one of its edges points at a question that no longer
exists. `copy_session_valid` is part of the statement that reads the content,
so a removal that committed before the statement's snapshot makes the copy
unreadable to that statement; there is no separate check to race.

Each existence check is fenced with `OFFSET 0`, which keeps it a probe per
row. Without the fence PostgreSQL 13 and 16 flatten the check into a join
that hashes every question on each list read. With it, a read pays one index
probe per conversation it already considers, plus one per edge of each copy
among them.

A caller first passes the usual ownership and partner checks, so anyone else
learns nothing about a removal. Then a detail, tool result, title, document,
Assistant session, helper run, insight or message logging read answers `410`
with `derived_source_removed` (`9085`). Lists, counts, recent conversations,
exports and insights leave the copy out; a follow-up question finds no
conversation.

### The task removes what is left

`conversations.derived_copies` follows a removal already made, so it runs
without an organisation choice and has its own switch,
`RETENTION_DERIVED_COPIES_ENABLED`. Switching it off keeps invalid copies
stored and still unreadable.

- Step `copies` walks the edges in the order of their unique index, so every
  window is bounded by the rows it returns. The questions of each invalid copy
  go through the shared conversation unit, with their Files, within the
  conversation budgets; the unit releases the session with its last question.
  The fresh check inside each `DELETE` keeps a question only while its copy is
  still invalid and outside a widget.
- Step `edges` deletes the edges of copy sessions that are gone and releases
  an invalid copy left without questions once it is a day old
  (`COPY_IN_FLIGHT_MARGIN`): a producer creates the session before it writes
  the copy's questions. The copy is unreadable meanwhile.
- A source removed behind the cursor is found on the next sweep.

Registration holds the copy session and locks no question; the task locks
questions with `SKIP LOCKED` and skips a session it cannot lock. Neither
waits for the other.

### Holds

Holds are not part of this record. A hold that keeps a copy stored becomes
one more condition in the task's fresh check.

### Measurement

Seeded PostgreSQL 13 and 16 with 20,000 conversations of one user,
200,000 questions and 2,000 copies whose edge counts fall from 5,000 to one
(22,179 edges); `backend/scripts/benchmark_derived_copies.py` reproduces it.
Median of five warm runs in milliseconds, with the same statement without the
check in brackets, on a shared development machine:

| Read | PostgreSQL 13 | PostgreSQL 16 |
| --- | --- | --- |
| Detail of a valid copy with 5,000 edges | 6.7 (0.01) | 6.1 (0.01) |
| An Assistant's list page of 50 | 11.1 (0.5) | 10.7 (0.8) |
| Its total count | 7.8 (0.03) | 7.8 (0.03) |
| Recent conversations of that user | 129.8 (24.2) | 123.3 (26.0) |
| Detail of the copy after one source was removed | 7.2 | 4.9 |
| Copies window of 500 edges, without and with an invalid copy | 1.2, 1.1 | 0.8, 0.8 |
| No copies stored: list page, total, recent | 1.1, 0.04, 58.0 (0.3, 0.02, 24.6) | 1.0, 0.03, 30.0 (0.6, 0.02, 26.6) |

The cost follows the edges of the copies a read considers: the recent list
above reads all 2,000 copies of its user. Before the fence the same list page
took 43 and 66 ms, its total 7 and 78 ms, and the copies window 3 and 97 ms,
because the check hashed all 200,000 questions.

## Alternatives rejected

- **A marker written by the task, read in place of the edges.** With the task
  off no marker is written, so a list would still show an invalid copy.
- **A trigger that marks copies when a source is deleted.** Every deletion of
  a question would fan out to its copies inside the deleting transaction,
  outside the deletion budgets.
- **Foreign keys from the edges.** A cascade would remove the evidence that
  the copy is invalid together with the source.

## Consequences

- Every conversation read carries the copy check. While no feature registers
  copies, it is one index probe per conversation considered that finds
  nothing.
- A copy has no detail or tool result after its source is removed: `410`
  where it was readable, absent from lists.
- Background jobs carry ids only: an App run reads its prompt from the stored
  run, an insights job its question from the job record, and these jobs and
  the audit job keep no result.

## Follow-ups

- The first feature that stores copies registers its sources and lists
  itself in `KNOWN_COPY_PRODUCERS`.
- Consultations of other Assistants join the conversation history rule with
  their own steps.
