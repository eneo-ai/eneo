# T137 Flow Runtime File Lifecycle Owner Preflight

Date: 2026-05-27
Task: T137 read-only Scout
Decision: `scout_more`

## Decision

Do not approve a runtime uploaded/generated blob retention Worker yet.

The correct model is not "make `DataRetentionService` safer at nulling `files.blob/text`" and not "add lifecycle booleans beside the current `file_id` references." Flow runtime bytes need a Flow-owned, run-private content lifetime owner. The existing step input/result xrefs are the canonical owners of run-step-file relationships, but they are not a safe content lifetime owner by themselves because the current source model still stores bytes in principal-owned `files` rows.

The next safe task should be a Judge for a minimal Flow runtime file snapshot design. The default architecture should be:

- keep `FlowRunStepInputFiles` / `FlowRunStepResultFiles` as relationship owners;
- introduce or approve one Flow-owned runtime file snapshot/content owner only if it removes principal-owned `Files` content from runtime lifecycle truth;
- explicitly collapse the current source-of-truth gap where `run.input_payload_json` is the runtime read path while xrefs are a persistence projection;
- copy or promote uploaded runtime input bytes into run-private snapshots at run creation/rerun;
- create generated artifacts directly as run-private snapshots, or explicitly keep the current `Files` path only until the generated-artifact slice moves it;
- make retention/tombstones/API evidence read from the Flow runtime owner, not from direct `Files.blob/text` inference.

This needs a schema/API/runtime Judge before implementation because the smallest correct slice crosses migrations, run creation, runtime input loading, artifact download/evidence projection, and generated-client/OpenAPI semantics.

## Architecture Challenge

| Question | Answer |
| --- | --- |
| Correct model if designed today | Flow runtime input/generated bytes are immutable run-owned snapshots with explicit content lifecycle state. Shared/principal `Files` rows may stage uploads, but they do not own runtime retention eligibility, purge completion, or evidence tombstones. |
| Current model | Runtime upload endpoints save principal-owned `Files`; run creation stores those file IDs in `input_payload_json` and `flow_run_step_input_files`; generated artifacts are saved as principal-owned `Files`; evidence joins `flow_run_step_result_files` to `Files` and derives availability from `blob/text`. |
| Is current model wrong or only incomplete? | Wrong for retention. It can validate and execute normal paths, but it encodes runtime lifecycle as a side effect of shared principal file content. |
| Refactor/replace needed? | Yes. Replace the content lifetime model; keep the relationship xrefs. |
| Why not just improve the existing path | Adding purge logic around current `Files` rows would be a workaround around the wrong owner. A file ID can be reused by source across steps/runs, so one run's retention cannot safely null shared content. |
| Canonical owner | Relationship: `FlowRunStepInputFiles` and `FlowRunStepResultFiles`. Content lifecycle: a Flow runtime file snapshot/content owner to be designed by the next Judge. `DataRetentionService` should remain an executor after lifecycle truth exists. |
| Existing code to reuse/move/merge/delete | Reuse xrefs for step/run linkage; reuse `FlowFileUploadService` policy validation; move runtime input loading away from principal `FileRepository.get_list_by_id_for_owner` once snapshots exist; move generated artifact persistence away from principal-owned `FileRepository.add`; delete direct artifact availability inference from `Files.blob/text` after the lifecycle owner is wired. |
| Compatibility paths to delete | `Files.blob/text` as the sole artifact availability signal; generated-artifact zero counters/comment once real lifecycle counters exist. |
| Tests that should be deleted/replaced | Current safety guards that forbid generated-artifact retention scheduling and direct `Files` content nulling should stay until lifecycle-owned purge lands. Later, replace them with guards that require purge through the Flow runtime content owner. |
| Migration/data preflight needed | Yes: new table/columns/FKs/indexes/downgrade, current reference reuse, tenant mismatch, orphan counts, backfill byte volume, old terminal run windows, generated-client/OpenAPI effects, and rollback behavior. |
| Smallest reviewable slice | A Judge that picks input snapshot first or generated artifact snapshot first, with exact files, red tests, migration plan, rollback/downgrade notes, and Claude plus Antigravity gates before implementation. |

## DB Evidence

Read-only DB preflight ran against Docker Postgres at `alembic_version=20260527_flow_sp_runtime_owner`.

### Catalog

- `files` stores `text`, `blob`, owner fields, tenant, checksum, size, MIME, and type. It has only `files_pkey(id)` plus owner/checksum indexes, and no unique `(id, tenant_id)` constraint.
- `flow_run_step_input_files` and `flow_run_step_result_files` both reference `files(id) ON DELETE RESTRICT`, plus composite FKs to `flow_runs(id, tenant_id)` and `flow_runs(id, flow_id)`.
- FK references into `files` are shared across non-Flow tables: `app_runs_files`, `apps_files`, `assistants_files`, `builder_session_files`, `questions_files`, `flow_template_assets`, and Flow input/result xrefs. That confirms direct `Files` content mutation is cross-module risk.
- Existing xref indexes cover `flow_run_id`, `(tenant_id, file_id)`, and run/step/attempt lookups. They do not cover lifecycle state because no lifecycle state exists.

### Query Shape

Current retention scan:

- current local plan: seq scan on tiny `flow_runs`, joins to `flows`, `spaces`, `tenants`, sort by run id;
- execution: about 0.26 ms locally;
- production-shape concern: a large terminal-run table would benefit from a partial expression index such as terminal status plus `coalesce(finished_at, created_at)` only if lifecycle cleanup becomes high-volume.

Candidate old terminal file-ref scan through existing xrefs:

- current local plan: build old terminal run CTE, join to input/result xrefs, then index-scan `files_pkey` once per ref;
- execution: about 0.20 ms locally for 107 content-available refs;
- production-shape concern: the xref side is indexed by `flow_run_id`, so starting from old runs can scale linearly with old run count plus refs per run. Starting from `Files` would be the wrong shape because `Files` is shared and not Flow-run-lifecycle scoped.

Evidence list-result-files query:

- current local plan uses `ix_flow_run_step_result_files_run_step_attempt` and `files_pkey`;
- execution: about 0.04 ms locally for the sample run;
- future lifecycle state should preserve this per-run lookup shape by keeping the run/result relationship indexed.

## Owner Options

| Option | Assessment |
| --- | --- |
| Deepen existing xrefs only | Good relationship owner, insufficient content owner unless xrefs also store/copy bytes. Storing bytes in both input and result xref tables would duplicate lifecycle columns and can duplicate bytes when a file is bound to multiple steps/attempts. |
| Add one Flow runtime file snapshot/content table | Best long-term model if kept narrow and Flow-specific. It can store run-private content once, support input and generated artifact references, hold lifecycle/tombstone state, and let xrefs stay relationship owners. It earns its weight because source permits file reuse even though current data does not show it. |
| Extend `Files` with run-private scope/run ID | Cheaper schema surface, but likely wrong owner: it concentrates Flow runtime lifecycle state in the shared Files owner and still requires strict tenant/run constraints. T138 must explicitly rule this option in or out with source and migration evidence rather than skipping it. |
| Keep using generic `Files` with more owner types | Not preferred. It pushes Flow lifecycle state into the shared Files owner and makes non-Flow file lifecycle harder to reason about. |
| Improve `DataRetentionService` only | Reject. It would make the executor own discovery and mutation, leaving the wrong content model intact. |

## Test Taxonomy For A Future Worker

| Layer | Required behavior |
| --- | --- |
| Unit/domain | A Flow run cannot treat a principal staging file as the runtime byte owner after run creation; duplicate file IDs across steps resolve to one run-owned content snapshot or a clearly intentional copy policy. |
| Repository/schema | Snapshot rows are tenant/run-scoped; xrefs cannot point across tenant/run; content state transitions are explicit; generated artifacts have no orphan window or have a reconciler with a deterministic rule. |
| Integration/runtime | Run creation/rerun snapshots uploaded inputs; execution reads the run snapshot, not a mutable principal file; generated artifacts are downloadable through Flow evidence APIs after step persistence. |
| Retention safety | Purging content changes lifecycle state and leaves metadata/tombstones; no direct `Files.blob/text = NULL` path appears in `DataRetentionService`. |
| API/OpenAPI | Public response fields and error/tombstone shapes are documented and generated-client-safe if artifact IDs or availability semantics change; semantic-equivalence tests prove `content_available`/artifact availability stays stable for non-purged fixtures across the ownership move. |
| Compatibility deletion guard | A red test must prove why direct `Files` content nulling is wrong: a Flow-referenced `Files` row can also be referenced outside the lifecycle owner unless the model has first copied/promoted bytes into a run-private snapshot. |
| Source-of-truth guard | A test must pin the relationship between submitted `run.input_payload_json.step_inputs` and persisted xrefs/snapshots so runtime execution cannot drift back to a parallel ID path. |
