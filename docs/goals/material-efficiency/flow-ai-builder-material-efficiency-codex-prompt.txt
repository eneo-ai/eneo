A generated flow should use `input_bindings.question`, `uses_previous_fields`, `uses_previous_outputs`, `uses_form_fields`, JSON contracts, form_fields/inmatningsfält, and input/output types together correctly.

Known risk to investigate:
A step with explicit `input_bindings.question` receives exactly that material; it does not automatically augment implicit `input_source`. This can cause source text/transcripts or earlier JSON sections to be lost when a composer/finalizer crosses JSON boundaries. Do not assume the fix. Reproduce or disprove it first.

Score every live case with this 0/1/2 rubric:
- Clarification restraint: asks the minimum necessary question when the prompt is underspecified; does not ask noise questions.
- Minimal viable topology: uses the smallest flow that satisfies the user-visible job.
- Source preservation: later steps that need original text/audio/document material can actually see it.
- Targeted material routing: uses explicit references to needed fields/outputs; broad fan-in appears only for true compare/aggregate work.
- Form-field lifecycle: content fields are declared once, consumed by relevant steps, and not hard-coded as examples.
- Terminal mode fit: chooses text/DOCX/PDF/template/API terminal behavior that matches the user-visible output.
- Context efficiency: records binding bytes, fan-in width, structured field count, whole-output refs, source duplication count, and `all_previous_steps` count.
- Output usefulness: the generated plan and any run result would answer the user's actual request, not only pass schema validation.

Passing threshold:
- A case passes at 12/16 or higher and no source-preservation or terminal-mode axis scores 0.
- The create suite passes at 8/10 cases or higher.
- Any empty final output, lost transcript/source in the final artifact, unused content form field, or unsatisfied run contract is a blocking regression even if the plan was created.
- Compare baseline vs after-change scores and metrics. A "better" result must improve score and/or reduce unnecessary material cost without losing required evidence.
- Run each case 3 times when API time allows. Report median score per axis and flag a case as flaky when any axis differs by 2 points across runs. If only one run is possible, label the result as single-run smoke, not a stable baseline.
- The runner emits raw per-run records, manual score fields, and median/flake rollups after scores are filled. It does not compute binding/fan-in metrics automatically because substring-based metrics would create false confidence. Use the saved plan/flow JSON plus deterministic tests for material-efficiency metrics.
