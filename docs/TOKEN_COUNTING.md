# Token Counting

This document explains how Eneo tracks token usage for LLM requests, including the provider-based counting mechanism and the fallback estimation strategy.

---

## Overview

Every LLM request in Eneo records two token counts:

- **Input tokens** (`num_tokens_question`) — tokens consumed by the prompt, system message, conversation history, and tool definitions
- **Output tokens** (`num_tokens_answer`) — tokens generated by the model in its response, including reasoning tokens

These counts are stored per question/app run and aggregated in the Insights/Admin dashboards.

---

## Primary: Provider-reported usage

LLM providers (OpenAI, Anthropic, Azure, etc.) return actual token counts in their API responses via the `usage` object:

```
response.usage.prompt_tokens      # input tokens as counted by the provider
response.usage.completion_tokens  # output tokens as counted by the provider
```

Eneo extracts these counts through LiteLLM's unified response format. This is the most accurate source because:

- The provider uses its own tokenizer (e.g. Anthropic uses their tokenizer, not OpenAI's `cl100k_base`)
- System prompts, tool definitions, and message formatting overhead are included
- Reasoning tokens (from models like o1 or Claude with extended thinking) are counted

### How it works

1. **Non-streaming requests**: After `litellm.acompletion()` returns, `TenantModelAdapter._extract_usage()` reads `response.usage` directly.

2. **Streaming requests**: The adapter passes `stream_options={"include_usage": True}` to the LiteLLM call. Providers that support this will include usage data on the final stream chunk. The adapter captures it during stream iteration.

3. **Multi-round MCP tool calls**: When a model calls MCP tools and receives a follow-up completion, token usage from all rounds is accumulated via `_accumulate_usage()`.

The extracted usage is attached to the `Completion` object as a `TokenUsage` instance and propagated through `CompletionModelResponse` to the calling services.

### TokenUsage model

```python
class TokenUsage(BaseModel):
    prompt_tokens: Optional[int] = None
    completion_tokens: Optional[int] = None
    reasoning_tokens: Optional[int] = None
```

## Fallback: tiktoken estimation

When provider usage data is unavailable (`usage` is `None` or the relevant field is `None`), Eneo falls back to local token estimation using [tiktoken](https://github.com/openai/tiktoken).

### When the fallback activates

| Scenario | Why usage is unavailable |
|----------|--------------------------|
| Self-hosted models (vLLM, Ollama) | Many OpenAI-compatible servers don't populate `usage` |
| Streaming without `include_usage` support | Some providers silently ignore `stream_options` |
| Older or non-standard provider APIs | May not return usage data at all |

### How the fallback works

- **Input tokens**: Uses the pre-computed `total_token_count` from the `ContextBuilder`, which estimates token count using tiktoken's `cl100k_base` encoding on the assembled prompt text.
- **Output tokens**: Calls `count_tokens()` on the response text, also using `cl100k_base`.

### Known limitations of the fallback

- **Wrong tokenizer**: `cl100k_base` is OpenAI's tokenizer. Other providers (Anthropic, Mistral, etc.) use different tokenizers, so counts will differ.
- **Missing overhead**: The estimation only counts visible text. System prompt formatting, tool schemas serialized by the provider, and internal message framing are not included.
- **No reasoning tokens**: Extended thinking / chain-of-thought tokens that don't appear in the response text are not captured by tiktoken. The `reasoning_token_count` field from streaming chunks is added when available, but this is a separate code path.
- **chars/4 fallback**: If tiktoken itself fails (e.g. encoding error), `count_tokens()` falls back to `len(text) / 4`, which is a very rough approximation.

## Decision logic per caller

All callers follow the same pattern:

```python
# Input tokens
if response.usage and response.usage.prompt_tokens is not None:
    num_tokens_input = response.usage.prompt_tokens
else:
    num_tokens_input = response.total_token_count  # tiktoken estimate

# Output tokens
if response.usage and response.usage.completion_tokens is not None:
    num_tokens_output = response.usage.completion_tokens
else:
    num_tokens_output = count_tokens(response_text)  # tiktoken estimate
```

This is implemented in:

| Caller | Path | Mode |
|--------|------|------|
| `AssistantService._handle_response` | `assistants/assistant_service.py` | Streaming and non-streaming |
| `AppRunService.run_app` | `apps/app_runs/app_run_service.py` | Non-streaming |
| `ServiceRunner.run` | `services/service_runner.py` | Non-streaming |
| `GroupChatService._handle_response` | `group_chat/group_chat_service.py` | Tiktoken only (receives raw text, not LLM response) |

## Data flow diagram

```
LLM Provider
    │
    ▼
litellm.acompletion() ──► response.usage.{prompt_tokens, completion_tokens}
    │
    ▼
TenantModelAdapter._extract_usage()
    │
    ▼
Completion.usage: TokenUsage
    │
    ├── (non-streaming) ──► CompletionModelResponse.usage
    │                            │
    │                            ▼
    │                       Caller checks response.usage
    │
    └── (streaming) ──► Final chunk carries usage
                            │
                            ▼
                        Caller captures chunk.usage during iteration
                            │
                            ▼
                        If usage is None ──► fallback to tiktoken estimate
```

## Monitoring

When provider usage is available, the token counts in Insights will be accurate. If you notice that token counts seem too low or inconsistent (especially for non-OpenAI models), it may indicate that the fallback is being used. Check backend logs for:

- `[TenantModelAdapter]` log lines to verify which adapter handled the request
- The `TokenUsage` values in debug-level logs

To verify whether a specific provider returns usage data, make a test request and inspect the `Completion.usage` field in the response.
