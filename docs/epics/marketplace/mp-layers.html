The Marketplace in five layers

One Hub run by Sundsvall. Each layer does one job and refuses one thing. Nothing reaches an Eneo instance unless a local person with the right permissions installs it.

1. People and roleswho may do what

DoesAllowlisted e-mail domains sign in with a link. Admins assign organisations and roles: member, publisher, curator, admin. A publisher cannot approve their own release.

NeverNo one is a publisher because of their e-mail address. Hub users and Eneo users are never the same identity.

2. The packageone envelope, five kinds

DoesFlow, Skill, Assistant, App, MCP definition. Prompts, settings, nested Skills and requirements travel. One versioned contract validates it in both code bases.

NeverNo knowledge content, no credentials, no local IDs, no run history. A Skill never contains an MCP server.

3. The Hubcatalogue and review

DoesStores immutable versions with a reviewed description, prerequisites and changelog. A curator approves. Yank stops new installs. Audit of who did what.

NeverNever calls an Eneo instance. Never changes a published version. Never deletes a local copy.

4. Eneo connectorbrowse, verify, hand over

DoesConnects with one token per instance, kept encrypted. Shows the complete content and the plan. Rechecks permissions and release state right before anything is created.

NeverNever creates resources itself; the kind's own installer does. Never shows the token to a browser. Never installs anyway.

5. Your instancelocal copies

DoesCreates a new copy in the chosen space with a receipt: listing, version, digest, who installed. Shows origin, newer-version notices and withdrawal warnings.

NeverNever auto-updates or merges. Keeps working when the Hub is down.
