# Phase 7 File Split And Do-Not-Split Plan

## TL;DR

Large files are not split because they are large.
Split only when each new module owns a real domain/lifecycle concept and exposes a smaller interface than the logic it hides.
Avoid `utils`, `helpers`, `common`, `shared`, `manager`, `misc`, vague `processor`, and vague `handler` names.
Delete or rewrite compatibility code before splitting it into new homes.
Tests should be split by behavior/lifecycle only after behavior pins exist.

## Required Checklist Before Any Split

- [ ] File path and LOC are named.
- [ ] Distinct responsibilities have line ranges in the implementation PR.
- [ ] Each new module name is a real domain/lifecycle concept.
- [ ] New module interface is smaller than the moved implementation.
- [ ] Compatibility/dead code is deleted before relocation.
- [ ] Review plan explains why a week-one senior engineer will understand the result faster.
- [ ] Split does not create duplicate logic across callers.
- [ ] Split does not create shallow pass-through modules.
- [ ] Split does not make a simple workflow require jumping through more files.
