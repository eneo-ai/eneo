## Summary

The decision is structurally sound: deleting top-level `file_ids` and snapshotting `step_inputs` for evidence/idempotency aligns with what the runtime already does (`flow_run_service.py:399-407` already writes `effective_payload["step_inputs"]` into `input_payload_json`, and `step_input_resolution.py:110` reads it back). The relational mapping table is **defensible but not yet justified** — PRD-003:32 explicitly forbids normalizing runtime inputs into tables "without ADR proof," and this proposal doesn't produce one. The harder problem the proposal under-specifies is rerun semantics on top of the existing `FlowStepResults` shape, which has a one-row-per-step unique constraint (`flow_tables.py:519-521`) that quietly forecloses several supersession options. Two pieces of the rerun model are also missing: a `flow_run_rerun_operations` table and per-attempt scoping on the new file-mapping rows. Without those, `new_attempt_no` and `invalidated_step_ids` (PRD-003:204-208) get reconstructed from joins across `FlowStepAttempts` and the snapshot, which is fragile.

## Alternatives

1. **Snapshot-only, indexed JSONB.** Keep file mapping in `FlowRuns.input_payload_json` (already there) plus an expression index on extracted step→file pairs. Avoids a new table; preserves the existing idempotency fingerprint (`flow_run_service.py:492-510`) verbatim. Loses cheap "show me every run that referenced file X" — but PRD-003 doesn't list that as a requirement.
2. **Mapping table scoped per attempt, not per run.** `flow_run_step_input_files(flow_run_id, step_id, attempt_no, file_id, ordinal, tenant_id)`. Lets rerun submit different files per attempt without overwriting prior lineage. The proposed run-scoped table cannot answer "what files were used on attempt 2 of step 5?" — which the evidence export promise (PRD-003:241) implicitly requires.
3. **Treat `FlowStepResults` as overwrite-only current projection, push history into `FlowStepAttempts.provenance_json`.** Keeps the existing UQ constraint, accepts that "current" means "latest". Cleaner than splitting current/superseded across two row states inside the same UQ-constrained table.
4. **Make `FlowStepDependencies` version-scoped.** Today it keys on `flow_id` (`flow_tables.py:186-228`), so a published-then-edited flow has drifted dependencies relative to a queued run. Either add `flow_version` to its PK or compute DAG invalidation from `FlowVersions.definition_json` (`flow_tables.py:243`) at rerun time. Pin one before shipping rerun.

## Risks or Blind Spots

- **`FlowStepResults` UQ constraint forecloses "supersede not delete."** `uq_flow_step_results_run_step` on `(flow_run_id, step_id)` (`flow_tables.py:519-521`) means there's exactly one current-projection row per step. If supersession means "keep the old row," the constraint must be dropped and replaced with a partial unique index on `is_current=true` — a real migration the proposal doesn't name. If supersession means "overwrite, history lives in `FlowStepAttempts`," say so explicitly.
- **Idempotency fingerprint regression.** `_build_idempotency_fingerprint` (`flow_run_service.py:492-510`) hashes the *whole* `input_payload_json`. Today step_inputs ride inside it via `serialize_step_inputs_payload` (`flow_run_step_inputs.py:244-252`). If the relational table becomes the truth and JSONB drops file_ids, the fingerprint shape changes silently — old idempotency rows stop replaying. Mitigation: keep the snapshot in JSONB unchanged; the table is a denormalization for queries/audit. The proposal asserts this ("Persist a normalized snapshot for evidence/idempotency") but the design must wire it: writes go to both, reads for fingerprint go to JSONB only.
- **Client-side idempotency derivation will churn.** `frontend/packages/intric-js/src/endpoints/flows.js:78-95` sorts `file_ids` into the SHA-256 input. After deletion, every consumer that derived a key including top-level `file_ids` produces a different digest. PRD-003:380 calls this a "pre-production breaking change" but doesn't list the SDK-side digest churn as a separate risk. The `_normalizeRunIntent` helper still has a `file_ids` branch (line 93) — it must be removed in lockstep, not in a follow-up.
- **`apply_legacy_step_one_adapter` silently rewrites top-level into step_inputs** (`flow_run_step_inputs.py:104-128`). Deleting it without a hard-422 stub means clients that still send `file_ids` get a generic Pydantic validation error rather than the canonical `flow_run_legacy_file_ids_not_supported` (PRD-003:157). The error code is a behavior contract — implement the explicit rejection with that code, don't let Pydantic shape the message.
- **Missing indexes/constraints on the proposed mapping table:**
  - Composite FK `(flow_run_id, tenant_id) → flow_runs(id, tenant_id)` for cheap tenant isolation (existing pattern at `flow_tables.py:507-512`).
  - Composite FK `(flow_id, step_id) → flow_steps(flow_id, id)` to prevent cross-flow step IDs (pattern at `flow_tables.py:218-221`).
  - PK or UQ on `(flow_run_id, step_id, attempt_no, ordinal)` for stable order — PRD-003:171 requires "sorted by step ID and file ID" for idempotency, so order must be deterministic on read.
  - FK to `files.id` with `ondelete=RESTRICT` (matches `FlowTemplateAssets.file_id` at `flow_tables.py:272-275`); cascading deletes here would corrupt evidence.
  - Index `(file_id, tenant_id)` for "where is this file referenced" queries the audit/debug story implies.
- **Rerun operation table is not in the proposal.** The PRD response shape (`flow_run_rerun_response` at PRD-003:200-209) returns `rerun_step_id`, `new_attempt_no`, `invalidated_step_ids` — none of which is currently materialized. Without `flow_run_rerun_operations(id, flow_run_id, rerun_step_id, prior_attempt_no, new_attempt_no, requested_by_user_id/api_key_id, principal_type, reason, idempotency_key, invalidated_step_ids JSONB, created_at, tenant_id)`, audit logging (a CLAUDE.md hard requirement) has nowhere to anchor. Reconstructing this from `FlowStepAttempts` joins works for happy path but loses the "why" (reason) and the invalidation set.
- **DAG invalidation source of truth ambiguity.** PRD-003:213-217 says traverse `flow_step_dependencies`. But that table is keyed on `flow_id`, not version (`flow_tables.py:186-198`). After a publish-then-edit, the graph for a queued run has drifted. The honest source is `FlowVersions.definition_json` parsed via `parse_runtime_steps` (already used in `flow_run_service.py:373`). Pin this in the rerun design or version-scope `FlowStepDependencies`.
- **Step-1 audio adapter coupling.** `apply_legacy_step_one_adapter` only fires when `file_ids` is present (`flow_run_step_inputs.py:111-128`). Removing top-level `file_ids` also removes the convenience path for single-step audio flows — the canonical `step_inputs[step1].file_ids` is more verbose. Consider whether `recommended_run_payload` in `FlowInputPolicyPublic` (`flow_models.py:481-484`, still emits top-level `file_ids`) needs a coordinated update or this becomes a dead documentation surface.
- **Generalization claim is narrow.** The proposal says "Keep heterogeneous non-file input payloads in typed/versioned JSONB envelopes," but `step_inputs` today only encodes `file_ids` (`flow_models.py:410-411`). If Phase 7 also wants typed-payload step inputs (text, structured JSON for a downstream HTTP step), the relational table will be a file-only side table while typed payloads sit in JSONB — two sources of step input truth. Either widen the table to `(flow_run_id, step_id, attempt_no, payload_kind, payload_ref)` with file_id as one kind, or accept "files only get the table; everything else stays JSONB" and write that boundary down.
- **No behavior pin before deletion.** PRD-003:382 mentions a pre-production rollback but doesn't require a characterization test for the legacy adapter prior to its removal. Add a test that asserts the current `apply_legacy_step_one_adapter` behavior verbatim — that's the diff that proves the deletion is safe and isolates the SDK churn.

## Recommended Next Step

Write the ADR PRD-003:32 already requires before adding the relational table. The ADR should answer four pinned questions:

1. **Table or JSONB** — which queries does the table enable that JSONB+expression-index can't, and what's the expected fan-out (files per run, runs per file)?
2. **Scope key** — `(flow_run_id, step_id)` or `(flow_run_id, step_id, attempt_no)`? The latter is the only shape that supports rerun lineage and the evidence export promise.
3. **`FlowStepResults` supersession model** — overwrite (history in attempts) vs. drop the UQ and add `is_current`. Pick one explicitly; both are defensible.
4. **DAG source of truth** — version-scope `FlowStepDependencies` or compute from `FlowVersions.definition_json`. The proposal will silently regress without this pinned.

Alongside the ADR, add the missing `flow_run_rerun_operations` table to the design and confirm the snapshot in `FlowRuns.input_payload_json` remains the canonical fingerprint surface (the table is denormalized read path, not the truth for idempotency). Then land a characterization test for `apply_legacy_step_one_adapter` so the deletion has a visible diff.

## Confidence

Medium-high on the structural risks (UQ constraint, missing rerun ops table, fingerprint regression, DAG source of truth) — these are evidenced directly in the cited files. Lower on whether the relational table is genuinely overkill: that hinges on actual file-per-run distribution numbers and the "show every run referencing file X" use case, neither of which is quantified in the prompt. I did not inspect the executor or `flow_run_repo.py`, so I cannot verify whether other write paths would be affected by the table addition; that should be checked before the ADR lands.
