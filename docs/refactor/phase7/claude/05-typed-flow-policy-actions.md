## Summary

Direction is right: typed actions + a single policy module is the correct cleanup. Concrete enforcement-point findings against the code as it stands:

- The "raw `request.state.api_key_scope_*` reads" the PRD calls out are isolated to `ai_builder_router.py:180-210` (4 hits). All main flow routers funnel through `enforce_flow_scope` → `get_scope_filter`, which already abstracts state. So the unification target is mostly: kill the AI Builder duplicates and extend the existing helper, not reinvent it.
- The two paths have **already drifted in default behavior**. `flow_api_common._ensure_flow_scope_type_allowed` (`flow_api_common.py:118-127`) raises if the scope_type isn't in `{None, tenant, space}`. The AI Builder version (`_require_ai_builder_scope`, `ai_builder_router.py:180-193`) silently returns when `scope_id` isn't a UUID and only blocks on `scope_type=="space"` mismatch. That is a real, existing inconsistency the new policy must close, not just a stylistic cleanup.
- `Permission.FLOWS` (the legacy umbrella) is a true superset in `roles/permissions.py:37-59` — every typed permission accepts `FLOWS` as an alias. The PRD's "legacy aliases do not automatically grant review/resume/rerun" only holds if the new gates use **new permission constants** that are *not* aliased to `FLOWS`. If `flow.review` is gated on `FLOWS_MANAGE`, holders of legacy `FLOWS` get review automatically. This needs to be an explicit decision pinned in the migration matrix.

## Alternatives

1. **Action enum vs capability enum.** The proposed list mixes verbs (`view/run/edit`) with lifecycle states (`rerun/resume/review`). A cleaner cut is `flow.read | flow.write | flow.execute | flow.lifecycle.<state-transition> | flow.audit.read | flow.builder.use`. Today the helper already collapses to three buckets (view/run/manage) — splitting straight to 8 verb-actions reverses that consolidation. Worth asking: do the new endpoints need 8 actions, or 4 actions × resource-level checks? "Reviewer can review" is often "user has a per-run grant," not a tenant-level role.
2. **Don't invent `flow.edit` separately from `flow.manage`** without a concrete reason. Today there is no "edit-without-manage" role. Adding the action without a permission to back it leaves it as a synonym for `flow.manage`, which is exactly the kind of stringly drift you're trying to retire.
3. **Keep AI Builder access as a domain check, not a top-level FlowApiAction.** It has two orthogonal gates (tenant `FLOWS_AI_BUILDER` + space `can_edit_flows` + per-session `actor_user_id`) that don't reduce cleanly to one action. The policy can expose `flow.builder.use` as a coarse permission gate; the session-creator and space-actor checks belong at the domain layer, as the PRD diagram already implies.

## Risks or Blind Spots

- **Action list omissions**: `flow.template.read/write` (`flow_template_router.py`), `flow.upload` (`flow_upload_router.py`), `flow.assistant.*` (`flow_assistant_router.py`), `flow.publish/delete` (lifecycle in `flow_authoring_router.py`). The PRD action list is enumerated in prose without exhaustive sweep — missing entries become string drift in disguise.
- **`flow.audit.view` vs existing `FLOWS_TRACE`**: name mismatch invites confusion. Either rename the permission to `FLOWS_AUDIT_VIEW` or call the action `flow.trace.view`. `flow_run_evidence_router.py` and `flow_trace_audit.py` are the surfaces that need to agree.
- **Enforcement point can't be a pure dependency for body-driven routes** (e.g., `create_session` reads `space_id` from the JSON body). FastAPI dependencies don't see the body, so the policy will end up as an explicit `FlowPolicy.assert(principal, action, ref)` call inside handlers — same call shape as today's `enforce_flow_scope`. State that explicitly so reviewers don't expect decorator-level enforcement that isn't possible.
- **`scope_enforcement_enabled` bypass** (`ai_builder_router.py:183`, `199`) is a soft-disable used somewhere (tests? a flag?). The unified policy must take a deliberate stance on it: keep, rename, or remove. Silently dropping it could mask a test-only path that's leaking into a prod code path.
- **List-endpoint semantics**: `list_sessions` (`ai_builder_router.py:418-446`) silently *filters* unauthorized sessions rather than denying. If the new policy treats every check as audit-loggable, list endpoints will spam denials. The policy contract needs a `list_filter` mode distinct from `assert`.
- **Service-key default**: `_ensure_required_tenant_permission` (`flow_api_common.py:179-193`) lets service keys through only for `view`/`run` *when `allow_service_key_principals=True` is set*. New endpoints can regress simply by forgetting to pass the flag. Inverting the default (deny-by-default for service keys, with an explicit `service_key_actions={...}` per route) is safer; the current opt-in pattern has bitten this exact codebase before — see `flow_permissions.py:48-56` where service-key denial had to be retrofitted with typed errors.
- **Pre-flow AI Builder sessions**: `target_kind == create` means `session.flow_id is None` until apply. Any policy action keyed on `flow_id` doesn't fit. The action surface needs a pre-flow variant (e.g., `flow.builder.use` on `space_ref`) so apply-time `flow.edit/manage` is the *second* gate, not the only one. This is exactly where AI Builder ownership "conflicts" with Flow policy: the create-path sessions are space-scoped; only the edit-path is flow-scoped.
- **Tenant-scoped API keys**: `_ensure_flow_scope_type_allowed` accepts both tenant and space. The current AI Builder helper effectively requires space-scope (it only enforces matches when scope_type=="space" and scope_id is UUID). If the unified policy adopts the more permissive flow-side behavior, tenant-scoped keys silently gain AI Builder reach. Pin: "tenant-scoped service keys cannot use AI Builder" (or whatever the deliberate decision is) as a test.
- **Negative migration tests missing from the PRD checklist**: explicit cases that should *fail* — `FLOWS` legacy alias does NOT grant `flow.review/resume/rerun`; `FLOWS_MANAGE` does NOT grant `flow.audit.view`; service-key with `view` does NOT grant any AI Builder action; tenant-scoped key does NOT grant `flow.builder.use`. The PRD lists positive matrix coverage in §"Testing Requirements" but the negative pins are what prevent silent expansion.
